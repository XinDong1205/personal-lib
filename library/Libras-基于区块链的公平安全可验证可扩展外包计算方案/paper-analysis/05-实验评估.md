# 5. 实验与评估

## 5.1 实验设计

### 实验目的
- 验证三个阶段的执行时间（Setup / Prove / Verify）随任务规模、任务数量、服务器数量的变化趋势
- 对比 Libras 与 FVP-EOC 在各阶段的计算开销
- 重点验证批量验证算法的效率优势

### 实验环境的评价

实验环境配置偏轻量：4GB RAM、1.80GHz 低压 CPU（i7-12700U 为移动端低压处理器）。这在一定程度上反映了边缘设备的真实条件，但也意味着：
- **优点**：贴近实际边缘部署场景（算力受限）
- **不足**：无法评估在服务器级别（高性能 CPU、大量 RAM）下的性能上限；低压 CPU 可能影响双线性配对这类密集计算操作的绝对时间

## 5.3 数据集/测试场景

### 两种测试计算类型

1. **矩阵乘法（Matrix Multiplication）**：
   - 30 个矩阵乘法任务
   - 不同矩阵维度（dimension）
   - 大矩阵被分块计算后按行/列拼接

2. **模幂运算（Modular Exponentiation）**：
   - 30 个模幂运算任务（形式 $x^a \bmod p$）
   - 指数 $p$ 的不同位长（length）
   - 指数转为二进制后切分为等长子序列

### 数据选择的合理性

两种计算类型覆盖了外包计算中最常见的场景：
- 矩阵乘法代表**线性代数**类任务（机器学习、图像处理中常见）
- 模幂运算代表**密码学**类任务（加密、签名、密钥交换中常见）

但两种任务类型在计算结构上类似（都被分解为可独立并行的子任务），缺乏对更复杂外包类型的覆盖（如非线性优化、图算法等）。

## 5.4 对比方案

### 唯一的量化对比：FVP-EOC [14]

论文选择 FVP-EOC 作为唯一量化对比对象，理由为：
- 架构相似：都是区块链上的边缘外包计算方案
- 任务类型相同：都模拟了矩阵乘法和模幂运算
- 其他方案（Dredas [32]、BPay [7]、Huang et al. [33]、OBFP [34]）的应用场景不同（外包存储审计、SHA-256 哈希求逆、离线字典猜测等），无法直接量化比较

### 对比公平性分析

| 维度 | 评价 |
|------|------|
| 任务类型一致 | ✓ 矩阵乘法和模幂运算 |
| 实现环境差异 | 未知：论文未提供 FVP-EOC 的实验环境参数 |
| 密码学原语差异 | Libras 用承诺+配对，FVP-EOC 用 ElGamal 加密——底层开销不同，比较的是"方案整体效率"而非"单个原语效率" |
| 验证时间比较方法 | ⚠ 用斜率比而非绝对值比（见下文详述） |

## 5.5 实验结果分析

### 图 6：单任务规模对各阶段时间的影响

**Fig. 6(a) - 矩阵乘法**：
- 随着矩阵维度增大，三阶段时间均增加
- **Task Calculation（Prove）耗时占比最大**——因为每个子任务都要生成证明 + 打包区块链交易
- Task Verification 波动最小——因为批量验证将 k 个证明聚合为一次配对验证，验证时间与子任务数几乎无关（常数级）

**Fig. 6(b) - 模幂运算**：
- 随指数 p 的位长增加，三阶段时间类似上升
- 同样的模式：Prove >> Setup > Verify

**分析**：两种任务类型的趋势一致，验证了批量验证的"常数时间"优势——这也是方案的核心卖点。

### 图 7(a) / 图 8(a)：任务数量对各阶段的影响

- 任务数量增加时，三阶段时间全部增加
- **Setup 时间显著增加**：论文解释为"任务分配阶段需要排序、切分、签名、支付押金"——但这里的"排序"只是 O(n log n)，真正耗时的是**区块链交易确认**（每个合约部署需要等待链上确认）
- Prove 时间增长最快——每个子任务都需要生成独立的证明并提交独立交易

### 图 7(b) / 图 8(b)：计算器数量对各阶段的影响

- **Setup 和 Verify 时间几乎不变**——它们只与任务数量相关（与服务器数量无关）
- **Prove 时间呈下降趋势**——更多服务器并行执行，总计算时间减少
- **绿色高亮部分（交易传输时间）不变**——因为交易数量由任务数决定（与服务器数量无关）

**值得注意**：论文特意放大了 8 和 10 计算器时的 Prove 时间条形图，突出显示了交易传输时间在总 Prove 时间中的占比。当服务器增多、单服务器计算时间缩短时，**区块链交易传输成为新的瓶颈**。

### 图 9：与 FVP-EOC 的验证时间对比

**Fig. 9(a) - 矩阵乘法验证时间对比**：
- 横坐标为 Task ID，纵坐标为验证时间
- **FVP-EOC**：任务从硬到易排序（Task ID 越大任务越简单）→ 验证时间递减
- **Libras**：任务从易到难排序 → 验证时间递增
- 为直观对比，论文将 Libras 曲线以 Task ID = 5.5 为对称轴翻折（橙色 → 绿色）
- Libras 的绿色曲线在 FVP-EOC 的蓝色曲线之下 → **Libras 验证时间更短**

**斜率分析**：
- Libras 斜率：-0.29（折线后）
- FVP-EOC 斜率：-0.35
- 斜率比 = 0.35/0.29 ≈ 1.2
- 论文声称此为"Libras 的验证时间为 FVP-EOC 的 1.2 倍"

**⚠️ 关键质疑："1.2×"的表述有问题**

论文 Abstract 中写道"the verification time is 1.2× that of FVP-EOC"，这在英文中通常意味着"Libras 的验证时间是 FVP-EOC 的 1.2 倍（即更慢）"。但图表显示 Libras 的验证时间明显**短于** FVP-EOC。这里存在表述问题——论文可能想表达"Libras 的验证效率是 FVP-EOC 的 1.2 倍"，但因措辞不精确造成了误导。

更合理的解释是：论文用**斜率比**来衡量"验证时间随任务难度增长的速度"。Libras 的斜率绝对值（0.29）小于 FVP-EOC（0.35），意味着随着任务难度增加，Libras 的验证时间增长更慢。斜率比为 0.35/0.29 ≈ 1.2，即 FVP-EOC 的时间增长速率是 Libras 的 1.2 倍。论文在结论部分应当更正为"FVP-EOC 的验证时间增长速度约为 Libras 的 1.2 倍"。

**Fig. 9(b) - 模幂运算验证时间对比**：
- 类似地，Libras 的验证时间普遍小于 FVP-EOC
- 趋势一致

### 表 III：计算开销理论比较

| 阶段 | FVP-EOC | Libras |
|------|---------|--------|
| 单结果生成 | $T_{me} + T_e + T_{mm}$ | $T_e$ |
| n 个结果生成 | $n(T_{me} + T_e + T_{mm})$ | $(n+1)T_e$ |
| 验证 | $n \cdot T_e$ | 2 pairings（常数级） |

- $T_{me}$：模幂运算时间
- $T_e$：幂运算时间
- $T_{mm}$：模乘运算时间

Libras 在证明生成阶段避免了 FVP-EOC 的加密操作（ElGamal 包含 1 次模幂 + 1 次模乘），仅在承诺上做一次幂操作。验证阶段从 O(n) 次模幂降为常数次配对。

## 5.6 实验评价

### 实验充分性评估

| 实验目的 | 是否验证 | 评价 |
|----------|---------|------|
| 各阶段耗时与任务规模的关系 | ✓ | 图 6, 7(a), 8(a) |
| 各阶段耗时与服务器数量的关系 | ✓ | 图 7(b), 8(b) |
| 与 FVP-EOC 的验证时间对比 | △ | 仅比较了验证时间，缺少全流程对比（Setup + Prove + Verify 总时间） |
| 批量验证的效率优势 | ✓ | 图 9 + Table III |
| 安全性实验 | ✗ | 仅有理论证明，无实验验证（如尝试伪造证明） |
| 公平性实验 | △ | 通过任务分配时间间接证明，但无直接度量（如各服务器获得的任务数量分布） |
| DAG 可扩展性实验 | △ | 仅通过"交易时间不变"间接证明，缺乏与传统链式区块链的 TPS/延迟对比 |

### 遗漏的实验
1. **缺乏端到端总时延对比**：仅比较验证时间，缺乏 Setup + Prove + Verify 的完整流程对比（虽然论文声称 Prove 阶段 Libras 也更快，但没有提供完整对比数据）
2. **缺乏与链式区块链的对比**：论文声称 DAG 比传统链式结构更快，但没有提供任何 DAG vs 传统链的延迟/TPS 数据
3. **缺乏大规模实验**：30 个任务、20 个节点对于区块链实验来说规模偏小
4. **缺乏容错性实验**：当部分服务器提交错误证明时，系统的行为如何？验证者能否正确区分？
5. **缺乏 deposit/gas 成本分析**：虽然论文提到"避免了海量链上数据导致的 gas 费"，但没有提供 gas 消耗的实际测量数据
