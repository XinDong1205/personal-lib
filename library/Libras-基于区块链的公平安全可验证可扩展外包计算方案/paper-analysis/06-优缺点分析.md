# 6. 优缺点与适用边界

## 6.1 核心优势

### 1. "四合一"的统一设计——系统级贡献

Libras 的最强优势在于将公平性、安全性、可验证性、可扩展性四个目标在一个统一框架中同时解决，而非独立处理。已有方案通常只解决其中 1-2 个目标（如 FVP-EOC 解决公平+可验证，但可扩展性差；OBFP [34] 解决公平+低开销，但可扩展性差）。这种"四合一"设计在论文发表时的文献中具有首创性。

### 2. 批量验证算法——工程上最优化的部分

使用商多项式聚合 + 单次双线性配对验证的批量验证方案，将验证时间从 O(k) 降为 O(1)（k 为子任务数），这是该方案中技术含金量最高的部分。与 FVP-EOC 的逐个解密验证相比，效率优势明显。

### 3. 轻量级任务分配策略

GCD + 轮询的任务分配策略在计算上极为简单——不需要迭代优化、不需要启发式搜索、不需要参数调优。对于资源受限的边缘设备来说，这种"粗粒度但低开销"的公平性方案比复杂的优化算法更实际。论文的认识是：在边缘场景下，"perfection is the enemy of good enough"。

### 4. 链上/链下协同的隐私保护思路

"结果链下存、证明链上存"的设计很简单但有效——它既保护了数据隐私（链上只存不可逆推原结果的群元素），又利用区块链的不可篡改性保证了可审计性。与复杂的同态加密或 ZKP 方案相比，这大大降低了参与方的计算负担。

### 5. DAG 适配的外包场景

在 DAG 中为外包计算设计"双维度链接"（实线 = 服务器维度，虚线 = 任务维度）是一个场景化的创新——它利用了 DAG 的图结构天然适合多维索引的特点，使得验证者可以沿虚线高效提取同任务的所有证明。

## 6.2 明显不足

### 性能方面

1. **区块链交易传输仍是瓶颈**
   - Fig. 7(b) 和 8(b) 的绿色高亮部分暴露了问题：当服务器数量足够多、本地计算时间缩短后，交易传输时间成为 Prove 阶段的绝对瓶颈。这个时间不随服务器数量增加而减少。
   - 方案没有解决"交易广播-打包-确认"的底层延迟问题——只是将链式换为 DAG，但链上传输的物理延迟无法消除。

2. **承诺生成的指数复杂度**
   - 公开参数 pp 包含 n+1 个群元素（$g_1, g_1^\tau, \ldots, g_1^{\tau^n}$），n 为多项式次数。对于高次多项式（复杂计算任务），pp 的大小和承诺 C 的计算量（需要 n+1 次群乘法和幂运算）可能很大。
   - 论文在表 III 中将 Libras 的证明生成为 $(n+1)T_e$，其中隐含的 n（多项式项数）可能在某些任务中很大。

3. **批量验证的前提要求**
   - 批量验证要求同一任务的所有子任务证明都已收集齐。如果某个服务器延迟或离线，整个验证流程被阻塞。

### 安全性方面

4. **秘密共享的传输安全性依赖不明确**
   - 论文使用秘密共享将 X 分发给服务器，但保证安全的前提是"每个诚实的服务器都获得 ≥t 个 share 来重构 X"。如果恶意服务器控制了超过 t 个 share，就可以恢复 X。论文没有明确说明谁获得了哪些 share——如果所有 share 都广播给所有服务器，那秘密共享形同虚设（任何人都可以重构）。

5. **τ（陷门）的托管问题**
   - KZG 承诺中的 τ 是一个"有毒废料"（toxic waste）——知道 τ 的人可以伪造任意证明/承诺。在 Libras 中，τ 由用户生成且保密。这假设用户不会利用 τ 作弊。但论文的威胁模型假设"用户也可能恶意"——如果恶意用户生成并公开 pp，是否存在不依赖 τ 可信性的验证方案？论文没有讨论。

6. **缺少对选择密文攻击（CCA）的考虑**
   - 安全性证明仅基于 ECDLP 的被动安全。没有考虑验证者或恶意服务器发起交互式攻击（如重放证明、选择输入攻击）的场景。

### 可扩展性方面

7. **DAG 缺乏独立的共识细节**
   - Libras 使用了 Conflux 的 DAG 底层，自身没有设计新的共识协议。论文声称 DAG 提高了可扩展性，但这实际上是 Conflux 的贡献而非 Libras 的贡献。
   - DAG 本身在拜占庭容错、确认最终性、双花防范等方面的分析和评估缺失。

8. **横向扩展的隐性限制**
   - 每增加一个服务器，就新增一个 TX Queue（增加带宽和存储压力）。验证者需要存储和遍历整个 DAG 来提取同任务证明。随着服务器和任务数量增加，DAG 的存储和遍历成本会增长。

### 实用性/部署方面

9. **仅支持多项式可表示的计算**
   - 承诺和验证机制的核心基于多项式恒等式 $F(\tau) = q(\tau) \cdot z(\tau) + p(\tau)$。这意味着计算任务 F(x) 必须是多项式（或可表示为多项式）。矩阵乘法和模幂运算满足此条件，但很多实际任务（如深度学习推理、数据库查询、图算法）不容易表出为多项式。

10. **缺乏公开可验证性（Public Verifiability）**
    - 虽然验证过程在链上执行，但验证者需要用户提供的 $g_T^{p(x)}$（由用户用 Lagrange 插值计算后发送给验证者）。这引入了验证者对用户的依赖——用户必须诚实地计算并发送正确的 $g_T^{p(x)}$。论文结论部分也承认了这一点，将此列为未来工作方向。

### 理论方面

11. **安全模型的假设过于简化**
    - 威胁模型将验证者假设为"诚实但好奇"，但没有考虑验证者本身被攻陷或部分验证者合谋的情况。
    - 缺乏对"cross-task contamination"的分析——不同任务的证明在 DAG 中交错存储，是否存在利用跨任务信息泄露的攻击向量？

12. **押金金额的设定问题**
    - 押金 Deposit 的设定在方案中是外生变量（由用户指定）。押金过低 → 不足以威慑恶意行为；押金过高 → 阻碍诚实的弱服务器参与。论文没有讨论押金金额的理论最优设定方法。

## 6.3 适用边界

### 最适用场景

| 场景 | 原因 |
|------|------|
| 轻量级 IoT 设备外包计算 | 终端无需执行复杂的 ZKP 或加密操作 |
| 可分解为独立子任务的批量计算 | 矩阵乘法、模幂运算等"可切片"计算 |
| 多方参与、互不信任的边缘网络 | 押金机制提供博弈论级别的安全保障 |
| 对实时性要求较高的外包应用 | DAG 提供比传统链更快的交易确认 |
| 需要可审计性的商业外包计算 | 链上证明提供不可篡改的审计记录 |

### 不适用场景

| 场景 | 原因 |
|------|------|
| 计算任务不可多项式表示 | 承诺和验证机制依赖多项式恒等式 |
| 超高安全要求的场景（如军事/金融核心系统） | ECDLP 在后量子时代有可能被攻破 |
| 单个大任务不可切分的外包 | 方案依赖于"任务→子任务"的切分 |
| 用户完全不可信的极端场景 | τ 由用户持有且用户可计算 $g_T^{p(x)}$，存在作弊可能 |
| 超大规模（千级节点）外包网络 | DAG 存储和遍历成本、每个服务器的独立队列维护成本 |
| 低延迟实时控制场景（毫秒级） | 即使是 DAG，区块链交易确认仍需数秒 |

## 6.4 隐藏的 Trade-off

### 1. 公平性 vs 效率

通过 GCD 切分保证每个服务器都有任务做（公平性），但切分本身引入了额外的协调开销。过细的切分（如所有 Deposit 的 GCD 为 1）会导致大量微小子任务，子任务太多反而会增加区块链交易数量和验证负担。

### 2. 安全性 vs 公开可验证性

将计算结果保存在链下保护了隐私（安全性↑），但也意味着验证者无法直接查看计算结果来进行独立验证，必须依赖用户提供的 $g_T^{p(x)}$（公开可验证性↓）。论文选择牺牲完全公开可验证性来换取隐私保护。

### 3. DAG 的交易确认速度 vs 全局一致性的保证

DAG 架构允许多队列并行出块，提供了"快速确认"（fast confirmation），但 DAG 的最终确认（finality）通常弱于单链的 PoW 最终性——存在重组/回滚风险。论文没有量化这种风险。

### 4. 聚合验证的"all-or-nothing"特性

批量验证要么"全部通过"要么"全部不通过"。如果 10 个服务器中只有 1 个提交了错误结果，整个 batch 验证失败——但验证者无法立即定位是哪个服务器作弊。这暗中将部分定位成本转移到了验证后的调试阶段。

### 5. 激励兼容 vs 押金机会成本

押金机制的博弈有效性依赖于押金金额设置合理。如果押金大于任务奖励，弱服务器没有参与动机（机会成本过高）。如果押金过小，作弊的预期收益（节省计算资源 + 可能的奖励）可能超过惩罚成本。论文没有给出押金设定的原则性方法。
