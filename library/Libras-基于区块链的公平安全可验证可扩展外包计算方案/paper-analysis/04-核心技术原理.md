## 4.1 任务分配策略：基于欧几里得算法的粒度均匀化

### 目的
在多任务-多服务器的外包场景中，解决算力强的服务器垄断所有高奖励任务、而算力弱的服务器长期"饥饿"的问题，实现任务分配的公平性。

### 核心思想
将所有任务的押金（Deposit）作为任务难度的代理指标，用 GCD 求出所有任务的最小公同单元，然后按此单元将任务切分为等粒度的子任务块，再让服务器按算力排序后轮询（Round-Robin）选择。

### 详细机制

1. **任务排序**：将所有任务按 Deposit 从小到大排序。高 Deposit ⟹ 高计算复杂度 ⟹ 高奖励。

2. **GCD 计算**：计算所有任务 Deposit 的最大公约数（Greatest Common Divisor）：
   $$gcd = \gcd(T_1.\text{Deposit}, T_2.\text{Deposit}, ..., T_n.\text{Deposit})$$

3. **任务切分**：每个任务 $T_i$ 被切分为 $\text{NumT}_i = T_i.\text{Deposit} / gcd$ 个子任务块。Deposit 越高的任务，子任务块越多（但每块粒度相同）。

4. **轮询分配**：
   - 第一轮：S₁（最强）→ 各任务的第 1 个子任务，S₂ → 第 2 个，S₃ → 第 3 个...
   - 第二轮：继续上述轮询
   - 当只有大任务的剩余子任务时，仍按计算能力排序轮流选择

5. **合约签订**：服务器选择子任务时必须签名并支付押金到智能合约地址。系统验证 `Ci_balance - Ci_lastBalance == Ti_Deposit` 后才批准分配。

### 创新点分析

- **与传统任务调度（如贪心、蚁群等）的区别**：传统调度以"全局最优"为目标（最短完工时间、最大吞吐量），计算复杂且不考虑弱服务器。Libras 以"公平"换"最优"，用极简的 GCD+轮询实现了O(n) 级别的任务分配——没有优化迭代，只有排序+除法+轮流。
- **粒度均匀化是巧妙之处**：使用 Deposit 的 GCD 作为最小单位，将异构任务统一为"同质化"的子任务块。这样弱服务器可以选择 Deposit 低的整任务或少量的高价子任务，强服务器选择多块，从而实现"按能力分配"的效果。
- **Deposit 作为难度代理的合理性**：在押金机制下，Deposit 由用户设定——任务越难、用户越愿意支付更高的 Deposit 来吸引服务器。因此 Deposit 实际上是一个市场化的任务难度信号。

### 潜在问题
- 如果 Deposit 之间存在较大的公因数（如所有 Deposit 都是素数），GCD 可能为 1，导致切分粒度过细、子任务数过多。
- Deposit 与计算复杂度之间的关系并非严格线性——用户可能低估或高估任务难度。

## 4.2 机密传输：基于多项式秘密共享的输入分发

### 目的
将用户的秘密输入 X 安全分发给多个服务器，使得：①每个服务器获得不同的份额（share）；②少于门限 t 个服务器合谋无法恢复 X；③服务器能够各自独立计算子任务的结果。

### 核心思想
使用 Shamir 秘密共享的变体——将秘密 X 编码为随机多项式 B(u) 的常数项，然后分发多项式上的 t 个不同点给服务器。服务器通过 Lagrange 插值重构多项式并代入 u = 0 恢复 X。

### 详细机制

1. **用户侧（分发）**：
   - 选择随机系数 $b_1, b_2, \ldots, b_{t-1} \leftarrow \mathbb{F}_q^*$
   - 构造多项式 $B(u) = X + b_1 u + b_2 u^2 + \cdots + b_{t-1} u^{t-1}$
   - 选择 t 个不同点 $u_1, u_2, \ldots, u_t$
   - 计算对应的 $B(u_1), B(u_2), \ldots, B(u_t)$
   - 将 t 个点 $(u_i, B(u_i))$ 分发给 k 个服务器

2. **服务器侧（重构）**：
   - 服务器集合通过 Lagrange 插值重构多项式 $B'(u) = \sum_{i=1}^t B(u_i) \prod_{1 \leq j \leq t, j \neq i} \frac{u - u_j}{u_i - u_j}$
   - 代入 $u = 0$ 得 $X = B'(0)$

### 安全性分析

**Theorem 1（等价于 Shamir 的门限性质）**：当最多 $t-1$ 个服务器合谋时：
- 它们只能得到 $t-1$ 个线性无关方程
- 系数矩阵不满秩（determinant = 0），无法唯一确定 $X = b_0$

**推导**：
$$\begin{pmatrix} 1 & u_1^1 & \cdots & u_1^{t-1} \\ \vdots & \vdots & & \vdots \\ 1 & u_t^1 & \cdots & u_t^{t-1} \end{pmatrix} \begin{pmatrix} b_0 \\ \vdots \\ b_{t-1} \end{pmatrix} = \begin{pmatrix} B(u_1) \\ \vdots \\ B(u_t) \end{pmatrix}$$

缺少最后一行时系数矩阵秩为 $t-1$（非满秩），无穷多解。

### 创新点分析

- 与标准 Shamir SS 的区别：此处秘密共享的目的是让每个服务器都能获得完整秘密 X（因为需要 X 作为输入来计算 F(x_i)），而非让各服务器持有不同子秘密。真正的作用是**防止传输过程中的窃听**——少于 t 人合谋无法恢复 X。
- 实际上这是一个"冗余传输"而非"门限共享"——每个合法服务器都应该能获得 t 份共享来重构 X。k 个服务器中哪些获得 share、如何保证每个服务器都有足够的 shares，论文没有清楚交代（这是实现细节的一个模糊之处）。

## 4.3 承诺机制：向量承诺与函数承诺

### 目的
使得用户可以生成对计算函数 F(x) 的简洁承诺 C，验证者在不接触计算结果明文的情况下，仅凭 C 和服务器提交的证明 ω_i 就能验证计算结果的正确性。

### 核心思想
将函数 F(x) 的系数编码到群元素中：用户秘密选取一个随机点 τ（trapdoor），公开 $g^{\tau^i}$ 作为公开参数 pp，计算 $C = g^{F(\tau)}$ 作为对函数的承诺。服务器通过多项式算术生成"商多项式"的承诺作为证明。

### 详细机制

**Setup**：
- 双线性群 $(G_1, G_2, G_T)$，生成元 $g_1, g_2, g_T = e(g_1, g_2)$
- 用户秘密选取 $\tau \leftarrow \mathbb{F}_q^*$（仅有用户知道）
- 公开参数 $pp = (g_1, g_1^\tau, g_1^{\tau^2}, \ldots, g_1^{\tau^n})$
- 对 $F(x) = a_0 + a_1 x + a_2 x^2 + \cdots + a_n x^n$ 的承诺：
  $$C = g_1^{F(\tau)} = g_1^{a_0 + a_1\tau + a_2\tau^2 + \cdots + a_n\tau^n} = \prod_{i=0}^{n} (g_1^{\tau^i})^{a_i}$$

**关键洞察**：给定 pp，任何人都可以在不知道 τ 的情况下用公开参数计算 $g_1^{F(\tau)}$——只需用 $g_1^{\tau^i}$ 作为系数 $a_i$ 的底数。

### 创新点分析

- 这本质上是 **KZG 多项式承诺（Kate-Zaverucha-Goldberg Commitment）** 的一个变体应用。KZG 承诺允许证明某个点上的多项式求值，而 Libras 将其用于"证明一组点上的求值结果整体正确"。
- 与传统向量承诺（VC）的关系：论文在 preliminaries 中引入了 VC 的抽象（Setup/Commit/Prove/Aggregate/Verify），但具体实现更接近 KZG 承诺——利用 $\tau$-powers 的 SRS（Structured Reference String）和双线性配对来验证。

## 4.4 证明生成：基于 Lagrange 插值 + 商多项式的 proof

### 目的
服务器在得到计算结果 $y_i = F(x_i)$ 后，需要生成一个简洁的、不可伪造的证明 ω_i，使得验证者可以确信 $(x_i, y_i)$ 确实在函数 F(x) 上。

### 核心思想
利用多项式恒等式 $F(x) = q(x) \cdot z(x) + p(x)$ 的核心性质：
- 如果 $y_i = F(x_i)$ 对所有 i 成立，则 $F(x) - \sum y_i I_i(x)$ 能被 $z(x) = \prod (x - x_i)$ 整除
- 服务器计算商多项式 $q_i(x)$ 并在 τ 点给出承诺，即构成 proof

### 详细机制

1. **计算累加器多项式（accumulator polynomial）**：
   $$z(x) = (x - x_1)(x - x_2) \cdots (x - x_k)$$
   其中 $x_i$ 是分配给各服务器的输入点。

2. **计算 Lagrange 基函数**：
   $$I_i(x) = \prod_{1 \leq j \leq k, j \neq i} \frac{x - x_j}{x_i - x_j}$$
   性质：$I_i(x_i) = 1$，$I_i(x_j) = 0$（当 $j \neq i$）。

3. **构造插值多项式**：
   $$p_i(x) = y_i \cdot I_i(x)$$
   这是仅通过 $(x_i, y_i)$ 一个点的"单点 Lagrange 插值"。

4. **计算商多项式**：
   $$q_i(x) = \frac{F(x)/k - p_i(x)}{z(x)} = \frac{F(x)/k - y_i \cdot I_i(x)}{z(x)}$$
   > 注：这里除以 k 是因为 k 个服务器各自对 F(x) 的结果做部分贡献——$F(x) = f_1(x) \oplus \cdots \oplus f_k(x)$。每个 server 计算完整 F(x_i)，但验证时每个 server 贡献 F(x)/k。

5. **生成证明**：
   $$\omega_i = g_1^{q_i(\tau)} = g_1^{q_0 + q_1\tau + q_2\tau^2 + \cdots + q_{n-k}\tau^{n-k}} = \prod_{j=0}^{n-k} (g_1^{\tau^j})^{q_j}$$

### 为什么这样设计有效？

核心数学恒等式：
$$F(x) = q(x) \cdot z(x) + p(x)$$
其中：
- $q(x) = \sum_{i=1}^k q_i(x)$（所有商多项式之和）
- $z(x) = \prod_{i=1}^k (x - x_i)$
- $p(x) = \sum_{i=1}^k y_i \cdot I_i(x)$（所有插值多项式之和）

当 $x = \tau$ 时验证配对方程：
$$e(C, g_2) = e(\omega, g_2^{z(x)}) \cdot g_T^{p(x)}$$
等价于验证 $F(\tau) = q(\tau) \cdot z(\tau) + p(\tau)$。

### 安全性分析（证明不可伪造性）

如果服务器伪造 $y_i^* \neq F(x_i)$，则：
$$q_i^*(\tau) = \frac{F(\tau)/k - y_i^* \cdot I_i(\tau)}{z(\tau)}$$

由于 $F(\tau)/k - y_i^* \cdot I_i(\tau) \neq F(\tau)/k - y_i \cdot I_i(\tau)$（除非 $y_i^* = y_i$），且分子不能被 $z(\tau)$ 整除，因此 $q_i^*(\tau) \neq q_i(\tau)$。

验证等式 $F(\tau) - p(\tau) = q(\tau)^* \cdot z(\tau)$ 不成立（因为右边的值不同），验证失败。实际上这是利用了多项式理论的**除数-余数唯一性**——如果商不同，整式等号不成立。

## 4.5 批量验证：证明聚合与单次配对验证

### 目的
将 k 个子任务的独立证明聚合为一条 batch proof，通过一次双线性配对验证所有 k 个结果的正确性——避免逐个验证带来的 O(k) 配对开销。

### 核心思想
将各服务器的商多项式求和：$q(x) = q_1(x) + q_2(x) + \cdots + q_k(x)$，将各证明做群乘法：$\omega = \prod \omega_i = g_1^{\sum q_i(\tau)}$。然后一条配对等式检验全局多项式恒等式。

### 详细机制

1. **证明聚合**：
   $$\omega = \prod_{i=1}^k \omega_i = \prod_{i=1}^k g_1^{q_i(\tau)} = g_1^{\sum_{i=1}^k q_i(\tau)} = g_1^{q(\tau)}$$

2. **计算全局插值多项式**：
   $$p(x) = \sum_{i=1}^k y_i \cdot I_i(x)$$
   $$g_T^{p(x)} = e(g_1, g_2)^{p(\tau)}$$

3. **批量验证等式**：
   $$e(C, g_2) \stackrel{?}{=} e(\omega, g_2^{z(x)}) \cdot g_T^{p(x)}$$

### 推导过程（完整）

代入 $C = g_1^{F(\tau)}$ 和 $\omega = g_1^{q(\tau)}$：

$$\begin{aligned}
e(g_1^{F(\tau)}, g_2) &= e(g_1^{q(\tau)}, g_2^{z(\tau)}) \cdot g_T^{p(\tau)} \\
e(g_1, g_2)^{F(\tau)} &= e(g_1, g_2)^{q(\tau) \cdot z(\tau)} \cdot e(g_1, g_2)^{p(\tau)} \\
e(g_1, g_2)^{F(\tau)} &= e(g_1, g_2)^{q(\tau) \cdot z(\tau) + p(\tau)} \\
F(\tau) &= q(\tau) \cdot z(\tau) + p(\tau) \quad \checkmark
\end{aligned}$$

最后一步使用了配对的双线性性质：
$$e(g_1^a, g_2^b) \cdot e(g_1^c, g_2^d) = e(g_1, g_2)^{ab + cd}$$

### 计算开销分析

| 操作 | FVP-EOC | Libras |
|------|---------|--------|
| 单个证明/加密 | $T_{me} + T_e + T_{mm}$ | $T_e$ |
| n 个结果总开销 | $n(T_{me} + T_e + T_{mm})$ | $(n+1)T_e$ |
| 验证（n 个结果） | $n T_e$（逐个解密） | 2 pairings + 1 exp（常数级） |

Libras 的验证时间为常数 O(1)（配对次数与 n 无关），而 FVP-EOC 为 O(n)。

### 创新点分析

- **批量验证的关键在于聚合的线性性**：商多项式 $q_i(x)$ 可以线性相加，因为配对的双线性保证了群元素的乘法对应于指数的加法。这是 KZG 承诺体系的标准技巧，但 Libras 将其用在了"多服务器-多子任务"的场景中。
- **与 Hyperproofs [37] 的关系**：论文引用了 Srinivasan et al. 的 Hyperproofs（向量承诺的证明聚合与维护），Libras 的聚合简化版本可以视为 Hyperproofs 在单一任务维度上的应用。

## 4.6 DAG 账本结构：多队列并行链

### 目的
解决传统链式区块链中孤块（orphan blocks）被浪费、交易确认慢、吞吐量低的问题。

### 核心思想
- 每个服务器拥有独立的交易队列（TX Queue），形成服务器维度的"链"
- 同任务的不同服务器结果用虚线链接，形成任务维度的"跨链"
- 连续的同任务交易打包到同一区块

### 详细机制

**交易标识格式**：$TX^k_{T^j_i}$
- $i$：任务编号（Task ID）
- $j$：子任务编号（sub-task ID）
- $k$：服务器编号（Server ID）

**链接规则**：

```
实线（Solid Line）：同队列内链接
  TX^1_{T^1_1} ─── TX^1_{T^1_2} ─── TX^1_{T^1_3}
  (服务器 S1 的连续交易形成 TX Queue 1)

虚线（Dashed Line）：跨队列、同任务链接
  TX^1_{T^1_2} - - - TX^2_{T^2_2} - - - TX^3_{T^3_2}
  (不同服务器对同一任务 T2 的计算结果交叉链接)

块打包：连续的同任务同队列交易打包为同一块
  [TX^1_{T^1_5}, TX^1_{T^4_5}, TX^1_{T^7_5}] → Block
```

**树形变换**：
将 DAG 顺时针旋转 45°，形成以 genesis block 为根的树。层次遍历（level-order traversal）第 ℓ 层即提取任务 Tℓ 的所有证明。

```
  DAG 视图:                    树形视图:
  TX1_T11 ─→ TX1_T12           ┌── root ──┐
   |    ╲       |    ╲          │    │     │
   |     ╲      |     ╲        T1   │     │
  TX2_T21    TX2_T22    ...    ├─ TX1  │     │
                               │  TX2  │     │
                              T2─TX1   │     │
                               │  TX2  │     │
                              ...
```

### 创新点分析

- **每个服务器独立队列消除了 fork 竞争**：传统 PoW 链中多个矿工竞争出块导致孤块。这里每个服务器的交易队列是独立的，非竞争关系。
- **双维度索引（服务器 × 任务）**：既可以按服务器追踪（实线），也可以按任务追踪（虚线），为验证者提供了灵活的数据提取方式。
- 但这部分的设计偏定性描述——缺乏对 DAG 共识算法具体细节（如冲突解决、安全假设、拜占庭容错等）的陈述。论文使用了 Conflux [13] 作为底层 DAG 平台，主要贡献在于将 DAG 结构适配到外包计算场景。

## 4.7 激励-惩罚机制：基于押金的博弈设计

### 目的
使诚实行为成为所有理性参与者的占优策略（dominant strategy）。

### 核心思想
- 用户和服务器都需要事先支付押金
- 诚实执行 → 退还押金 + 获得奖励
- 不良行为 → 没收押金

### 详细机制

```
  ┌─────────────┐                    ┌─────────────┐
  │    User     │                    │   Server    │
  │ (malicious) │                    │ (malicious) │
  └──────┬──────┘                    └──────┬──────┘
         │ 拒绝付款                          │ 提交错误结果
         ▼                                  ▼
  ┌──────────────┐                  ┌──────────────┐
  │ Deposit 没收  │                  │ Deposit 没收  │
  │ (给 Server)  │                  │ (给 User)    │
  └──────────────┘                  └──────────────┘

  ┌─────────────┐                    ┌─────────────┐
  │   User      │                    │   Server    │
  │ (honest)    │                    │ (honest)    │
  └──────┬──────┘                    └──────┬──────┘
         │ 正常付款                          │ 正确计算+通过验证
         ▼                                  ▼
  ┌──────────────┐                  ┌──────────────┐
  │ Deposit 退还  │                  │ Deposit 退还  │
  │ + 获得结果   │                  │ + 获得 Reward │
  └──────────────┘                  └──────────────┘
```

### 博弈论分析

论文声称方案具有"激励兼容性（Incentive Compatibility）"。判断是否成立：
- **对于服务器**：作弊 → 押金被没收 + 无奖励。诚实 → 押金退还 + 奖励。只要 Reward + Deposit > 作弊的期望收益（可能来自提交随机结果的"节省计算"），诚实就是占优策略。
- **对于用户**：拒绝付款 → 押金被没收 + 无结果。付款 → 获得结果。只要 Deposit > 结果价值 × 成功逃脱概率，付款就是占优策略。
- **前提假设**：验证者能够检测出所有作弊行为。这依赖于第 4.5 条中证明的不可伪造性。

```
  │              GCD 切分 + 轮询 ─┐                        │

  │  安全性 ←──── 秘密共享 (4.2) + 承诺 (4.3) + ECDLP     │

  │                              │                        │

  └────────────────────────────────────────────────────────┘
```

四个目标不是独立实现的，而是共享底层机制：
- 承诺机制同时服务于安全性（隐藏计算结果）和可验证性（为配对验证提供锚点）
- DAG 账本同时服务于可扩展性（快速确认）和可验证性（树形遍历便于提取证明）
- 押金机制同时服务于公平性（激励诚实行为）和安全性（提高攻击成本）
