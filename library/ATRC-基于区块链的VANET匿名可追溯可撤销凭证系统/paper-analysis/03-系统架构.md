## 3.2 参与实体与角色

| 实体 | 英文名称 | 角色与职责 |
|------|----------|------------|
| **车辆用户** | Vehicle User (OBU) | 系统的核心消费者。本地生成伪名（Pseudonym）和凭证（Credential），向 RSU 出示凭证以获取道路服务，进行 V2V 通信。 |
| **管理机构** | Management Authority (MA) | 系统的管理者，扮演群管理员角色。负责：系统初始化（Setup）、成员注册（Join）、恶意用户追溯（Trace/Open）、撤销操作（Revoke）。MA 是唯一持有主密钥 $msk$ 的实体，**被认为是可信的**。 |
| **路侧单元** | RSU (Road-Side Unit) | 系统的验证者。拥有实时道路信息，在与车辆交互前验证其凭证有效性和撤销状态。不存储车辆身份隐私信息。 |
| **区块链** | Blockchain | 分布式公告板。存储伪名、凭证、撤销 Merkle 树根哈希。其防篡改特性保证所有参与方数据一致性。论文未指定具体区块链平台——仅需基本的读写和防篡改能力。 |

## 3.3 模块划分与分工

系统由两大密码学模块构成，各自独立运行但通过同一个用户密钥 $e_i$ 绑定：

### 模块一：伪名模块（Pseudonym Module — PDN）

基于 Ateniese 等人 [11] 的群签名方案，提供：

| 算法 | 执行者 | 功能 |
|------|--------|------|
| `PDN.Setup` | MA | 生成群参数 $(n, a, a_0, g, h, y)$ 和主密钥 $(p', q', x)$ |
| `PDN.Join` | MA + 用户 | 用户获取私钥 $x_i$ 和证书 $(A_i, e_i)$ |
| `PDN.Gen` | 用户本地 | 生成伪名 $pdn_i = (T_1, T_2, T_3, \pi_p)$ |
| `PDN.Verf` | RSU / 任何人 | 验证伪名的有效性 |
| `PDN.Open` | MA | 从伪名追溯用户证书 $A_i$ |
| `PDN.Revoke` | MA | 从 Merkle 树中移除对应用户叶子节点 |

### 模块二：凭证模块（Credential Module — Cred）

基于 Garman 等人 [12] 的 DAC 框架，提供：

| 算法 | 执行者 | 功能 |
|------|--------|------|
| `Cred.Setup` | MA | 生成凭证系统的生成元 $g_0, g_1, \ldots, g_t$ |
| `Cred.Form` | 用户本地 | 生成凭证 $c = h^{w'} g^{e_i} \prod_{j=0}^{m} g_j^{attr_j}$ |
| `Cred.Verf` | 任何人 | 验证凭证与伪名的绑定关系 |
| `Cred.Show` | 用户 | 生成凭证出示证明 $\pi_s$ + Merkle 路径 |
| `ShowVerf` | RSU | 验证出示证明 + Merkle 路径的有效性 |

### 关键设计：两大模块的绑定

凭证和伪名通过同一个 $e_i$（用户的证书组成部分）实现**密码学绑定**。具体而言：
- 伪名中 $T_3 = g^{e_i}h^w$ 包含了 $e_i$
- 凭证中 $c = h^{w'}g^{e_i}\prod g_j^{attr_j}$ 也包含了 $e_i$
- $\pi_c$ 是 $T_3$ 和 $c$ 包含同一 $e_i$ 的知识签名

这保证了：**用户不能将一个合法伪名与另一个用户的凭证组合使用**。

## 3.4 整体交互流程

### 阶段一：准备阶段（Preparation Phase）

```
  MA                          Blockchain                Vehicle User
  │                               │                          │
  │── PDN.Setup + Cred.Setup ──▶ │                          │
  │   (一次性，系统初始化)         │                          │
  │                               │                          │
  │◀──── Registration Request ──────────────────────────────│
  │   (用户将身份 id 通过安全信道发送给 MA)                  │
  │                                                         │
  │── PDN.Join: 生成 (Ai, ei, xi) ────────────────────────▶│
  │   (MA 通过安全信道返回用户密钥)                          │
```

### 阶段二：铸币阶段（Mintage Phase）

```
  Vehicle User                                 Blockchain
  │                                               │
  │── PDN.Gen: 本地生成 pdn = (T1, T2, T3, πp)  │
  │── Cred.Form: 本地生成 c 和 πc                │
  │                                               │
  │── Upload (pdn, c, πc, {g^attri}, aux) ──────▶│
  │   (将伪名和凭证上传到区块链存储)                │
```

**注意**：此阶段完全由用户本地执行，MA 不参与。用户可以预生成大量伪名-凭证对储备使用，这是论文强调的"灵活性"体现。

### 阶段三：消费阶段（Consumption Phase）

```
  Vehicle User              RSU                  Blockchain
  │                          │                       │
  │                          │── Fetch pdn, c ──────▶│
  │                          │◀──── pdn, c ─────────│
  │                          │                       │
  │                          │── Fetch Merkle Root ─▶│
  │                          │◀─── Merkle Root ─────│
  │                          │                       │
  │── Cred.Show: 生成 πs ──▶│                       │
  │   + Merkle Path          │                       │
  │   + g^{ei}h^w            │                       │
  │   + {attr} \ {ra}        │                       │
  │                          │                       │
  │                          │── ShowVerf:           │
  │                          │   1. PDN.Verf         │
  │                          │   2. Cred.Verf        │
  │                          │   3. Check Merkle Path│
  │                          │   4. Cred.ShowVerf    │
  │                          │                       │
  │◀──── Road Information ───│                       │
  │   (验证通过后返回道路信息)  │                       │
```

### 阶段四：撤销阶段（Revocation Phase，独立于其他阶段）

```
  MA                              Blockchain
  │                                   │
  │── 1. PDN.Open: 从 pdn 追溯 Ai ───│
  │                                   │
  │── 2. 在 Merkle 树中定位 leaf_i ──│
  │     leaf_i = Hash(g^{ei}h^w || Version)
  │                                   │
  │── 3. 剪枝 leaf_i，重新计算树根 ──│
  │                                   │
  │── 4. Upload 新 Merkle Root ──────▶│
  │                                   │
  │  [撤销完成，被撤销用户无法再]
  │  [通过 Merkle 路径证明自己是合法成员]
```

## 3.5 安全/威胁模型

### 攻击者能力假设

论文采用了标准的 PPT（Probabilistic Polynomial-Time，概率多项式时间）敌手模型：

- **敌手类型**：恶意车辆用户的**合谋攻击（Coalition Attack）**——多个恶意车辆用户联合起来，尝试伪造一个新用户的合法密钥/证书
- **敌手能力**：多项式时间的计算能力；可进行最多 $q$ 次注册查询（RegQuery Oracle），每次可获取一个合法的 $(A_i, e_i)$ 对
- **攻击目标**：输出一个通过验证的伪造证书 $(x^*, A^*, e^*)$，且该证书不同于任何已查询过的证书

### 信任假设

- **MA 是可信第三方（Trusted Third Party）**：MA 不会主动泄露用户隐私、不会伪造证书、不会恶意撤销。论文明确说"the management authority is the trusted third party"。这是一个**较强的信任假设**，也是方案的主要局限之一。
- **安全信道**：用户与 MA 在 Join 阶段通过安全信道通信（确保 $x_i$ 和 $(A_i, e_i)$ 在传输中不被窃听）

### 安全目标的形式化定义

不可伪造性安全游戏 $\text{Exp}^{\text{UF}}_{\mathcal{A}}(K)$：

1. **Setup**：挑战者 $\mathcal{C}$ 执行 `System Setup`，生成 $pp$ 和 $msk$，将 $pp$ 发送给敌手 $\mathcal{A}$，保留 $msk$
2. **RegQuery**：$\mathcal{A}$ 可进行最多 $q$ 次注册查询。对于第 $i$ 次查询，$\mathcal{C}$ 生成 $(A_i, e_i)$ 并返回给 $\mathcal{A}$
3. **Forge**：$\mathcal{A}$ 输出 $(x^*, A^*, e^*) \neq (x_i, A_i, e_i)$。若该证书通过验证，则 $\mathcal{A}$ 获胜

安全定义：$\text{Adv}^{\text{UF}}_{\mathcal{A}}(K) = |\Pr[\text{Exp}^{\text{UF}}_{\mathcal{A}}(K) = 1]|$ 是可忽略的（negligible）。

### 未建模的安全属性

论文的威胁模型**只形式化了不可伪造性**。以下属性虽在论文中被声称但未给出形式化安全定义：
- **匿名性**：论文依赖群签名方案本身的匿名性，未证明在引入 Merkle 树撤销后匿名性是否仍然保持
- **可追溯性**：论文只描述了追溯操作 $A_i = T_1 / T_2^x$，未证明 MA 之外的人无法追溯
- **撤销可靠性**：未证明被撤销用户无法继续生成有效的 Merkle 路径证明

这些缺失的安全分析是论文的明显不足（详见第 6 章）。
