# 05 — 实验与评估

## 5.1 实验设计

论文的实验分为两个层面：

1. **密码学原语计算开销测试**：测量各核心算法（Setup、Join、Gen、Verf 等）的运行时间
2. **VANET 网络仿真**：用 ns2 模拟车辆与 RSU 之间的通信行为，测量延迟和丢包率

**实验要验证的核心假设**：
- ATRC 方案在 Show 阶段（用户生成证明）和 Revoke 阶段（MA 更新 Merkle 树）具有"可接受"的计算开销
- 随着 RSU 数量和车辆数量的变化，系统延迟和丢包率的变化趋势

## 5.2 实验环境

| 项目 | 配置 |
|------|------|
| **CPU** | Intel Core i7-7700 @ 3.60 GHz |
| **操作系统** | Windows 10 |
| **内存** | 8 GB |
| **密码学库** | MIRACL（Multiprecision Integer and Rational Arithmetic Cryptographic Library） |
| **安全级别** | 128-bit |
| **测试方式** | 每个运算执行 1000 次取平均值 |
| **网络仿真工具** | ns2 |

### 对环境配置的评论

- **MIRACL 库**：这是一个经典的大整数密码学库，支持本文所需的 RSA 模运算、大素数生成等。选择 MIRACL 是合理的——它比 PBC（Pairing-Based Cryptography）库更适合 RSA 型方案。
- **单机测试的局限**：密码学计算在单机上完成，未测试在真实车载硬件（如 OBU 资源受限设备）上的表现。
- **128-bit 安全级别**：论文未明确说明 RSA 模数长度。按照 NIST 标准，128-bit 安全对应 RSA-3072。但在强 RSA 假设下，模数 $n = pq$ 且 $p = 2p'+1, q = 2q'+1$ 意味着 $p', q'$ 也需满足一定长度。

## 5.3 数据集 / 测试场景

### ns2 仿真参数设置

| 参数 | 设定 |
|------|------|
| **车辆速度** | 30 km/h（城市低速场景） |
| **RSU 节点数** | 2, 4, 6, 8, 10, 12, 14, 16 |
| **车辆节点数** | 70, 80, 100, 120, 150, 180, 200, 250 |
| **度量指标** | 平均请求延迟（Average Delay）、丢包率（Loss Rate） |

### 测试分组

- **Group 1（RSU 变化测试）**：车辆固定 70 辆，速度 30 km/h，RSU 从 2 增加到 16，观察延迟和丢包率
- **Group 2（车辆变化测试）**：RSU 固定 16，速度 30 km/h，车辆从 70 增加到 250

### 场景选择的合理性

- **30 km/h 的低速城市场景**：代表车辆与单个 RSU 有较长的通信窗口时间。但论文仅测试了单一速度，未测试 60-120 km/h 的高速公路场景——这可能低估了高移动性下的丢包率。
- **最多 250 辆车 + 16 个 RSU**：这相对较小。真实城市交叉口可能有数百到数千辆车同时在线。实验并未充分展示系统在大规模部署时的表现。

## 5.4 对比方案

论文的实验部分**没有列出任何对比方案（Baseline）**。这是该论文实验部分的最大不足：

- 密码学计算开销测试中，只给出了 ATRC 各算法的绝对值（毫秒级），没有与 Derler 等人 [5]、Yang 等人 [4] 或其他群签名方案进行对比。
- 网络仿真中也没有与 Cui 等人 [25]、Das 等人 [28] 等其他区块链 VANET 方案的性能对比。

**为什么缺少对比是个严重问题**：论文声称的优势（"轻量级"、"更少的计算开销"）在没有对比的情况下是无法验证的。读者无法判断 10ms 的计算开销到底是"好"还是"差"。

## 5.5 实验结果分析

### 5.5.1 RSU 数量变化的影响（Fig. 10）

**Fig. 10(a) — 平均延迟 vs RSU 数量**：

> 论文描述："The average delay of vehicle nodes keeps on changing when RSU nodes are increased. The fluctuation range and specific values of the test results show that communication congestion is not the main factor affecting the delay when RSU nodes are increased."

**分析**：延迟随 RSU 增加而波动但无明显趋势，说明瓶颈不在 RSU 的通信带宽，而在**方案协议本身的处理时间**（即密码学验证的开销）。这是一个值得注意的发现——它暗示优化方向应该是降低密码学验证的计算量，而非增加 RSU 数量。

**Fig. 10(b) — 丢包率 vs RSU 数量**：

> 论文描述："The packet loss rate of RSU nodes holds a decreasing trend, which is consistent with the expectation."

**分析**：更多 RSU 分担了请求处理压力，丢包率下降。这是符合直觉的结果。

### 5.5.2 车辆数量变化的影响（Fig. 11）

**Fig. 11(a) — 平均延迟 vs 车辆数量**：

> 论文描述："The rising trend of the average request delay... the influence of communication queue on vehicle request delay is gradually increasing."

**分析**：随着车辆数增加，每辆车的等待延迟升高。这是因为 RSU 需要处理更多密码学验证请求，形成了计算队列。

**Fig. 11(b) — 丢包率 vs 车辆数量**：

这是最值得关注的实验结果：

> 论文描述："When the vehicle node reaches 250, even if the RSU node almost covers the entire simulation map, the vehicle packet loss rate is close to 40%, and the RSU packet loss rate is 55%."

**关键发现 — 120 辆车的瓶颈**：

> 论文指出："When the number of vehicle nodes is above 120, each evaluation index increases significantly. In view of this phenomenon, the communication intensity may exceed the bottleneck of the system when the vehicle node is at 120."

在 16 个 RSU、30 km/h 的条件下，系统在 **120 辆车左右达到饱和状态**。超过这个阈值后，性能急剧恶化。当达到 250 辆车时：
- 车辆丢包率接近 40%
- RSU 丢包率高达 55%

这意味着**超过一半的请求得不到响应**——对于 VANET 这种安全关键系统，这是不可接受的。

## 5.6 实验评价

### 实验的不足

1. **没有对比方案**：前后文多次声称方案"轻量级"（lightweight），但始终没有与任何 Baseline 做计算开销对比。这是最关键的缺陷。

2. **密码学计算时间未公布**：论文提到了"the running time is an average value of 1000 times execution in 128-bit security level"，但正文中**没有给出任何具体数值**（没有表格列出 Setup、Join、Gen、Verf、Show 等各阶段的毫秒数）。这使读者无法评估"轻量级"声明的可信度。

3. **网络仿真参数不够多样**：仅测试了一种速度（30 km/h），未覆盖高速公路场景（60-120 km/h）。高速移动意味着更短的通信窗口，可能加剧丢包问题。

4. **车辆数量上限偏低**：250 辆车的最大规模远小于真实城市交叉口的车辆密度。120 辆就达到瓶颈这一事实表明，系统在大规模部署时面临严重的可扩展性问题。

5. **未测试 Merkle 树大小对性能的影响**：未报告不同成员数量下 Merkle 路径长度、验证时间的变化。

6. **未测试撤销操作延迟**：论文声称撤销高效，但未给出从 MA 执行 PDN.Open 到新 Merkle 根上链的端到端时间。VANET 中的窗口时间是以秒甚至毫秒为单位的——这个数据缺失使得"快速撤销"的主张缺乏支撑。

### 实验的可复现性

论文未公开源代码和测试数据。MIRACL 库是开源可获取的，但具体的参数选择（如 RSA 模数长度、素数位数）需要读者自行推断。ns2 仿真场景的配置文件也未提供。

### 总体实验质量评估

实验部分是该论文**最薄弱的环节**。核心计算开销数据缺失（可能是篇幅限制导致被删除），网络仿真覆盖的场景有限且缺乏对比。如果作为一篇系统实现类论文的标准来衡量，实验部分是不充分的。
