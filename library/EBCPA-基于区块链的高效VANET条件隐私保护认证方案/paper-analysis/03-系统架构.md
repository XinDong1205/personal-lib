## 3.2 参与实体与角色

| 实体 | 信任假设 | 核心职责 | 持有秘密 |
|------|---------|---------|---------|
| **CA (Certificate Authority)** | 完全可信 | 颁发和管理车辆/RSU 的长期公钥证书 | - |
| **Manager** | 完全可信 | 注册车辆的匿名公钥至智能合约；追溯恶意车辆真实身份；仅 Manager 可调用 Submit 和 Revoke | `lskm`（长期私钥，用于追溯和派生匿名公钥） |
| **Vehicle** | 半可信（可能恶意） | 派生匿名公私钥、签名并广播交通消息、验证接收消息 | `lski`（长期私钥）、`askj_i`（第 j 个匿名私钥）、`pdij_i`（第 j 个派生信息）、`pseed`（私有种子的哈希值） |
| **RSU (Road Side Unit)** | 完全可信 | 作为区块链全节点存储交易数据；提供 `tx_rtv`（检索交易）和 `eth_calls`（调用智能合约）的 API | - |
| **Blockchain** | 去信任（由共识保证） | 去中心化存储车辆匿名公钥；智能合约执行公钥的提交、检查、撤销逻辑 | - |

### 关键信任关系分析

- **CA ↔ Manager 的分工**：CA 管理**长期身份**（真实公钥证书），Manager 管理**匿名身份**（一次性公钥的授权与撤销）。两者职责分离，CA 不参与日常认证。
- **Manager 的权力集中**：Manager 拥有 `lskm`，这是系统中唯一能执行追溯和提交匿名公钥的密钥。这是一个**中心化信任点**，论文假设 Manager 是可信的。
- **RSU 的辅助角色**：RSU 提供区块链的接入 API，论文假设 RSU 不会提供虚假 API，即不讨论恶意 RSU 的威胁。

## 3.3 模块划分与分工

### 模块 1：密钥派生模块（KeyDer / Reconstructed Key Derivation）

- **功能**：基于 BIP32（比特币分层确定性钱包）思想，使车辆和 Manager 在仅初始化交互一次后，可各自独立派生出链式的匿名密钥对
- **包含算法**：
  - `KDGen(pseed)`：车辆由私有种子的哈希生成根匿名私钥和根派生信息
  - `PriKD(ask^{j-1}_i, pdi^{j-1}_i, j)`：车辆派生出第 j 个匿名私钥
  - `PubKD(APK^{j-1,1}_i, pdi^{j-1}_i, j, LPK_i, lskm)`：Manager 派生第 j 个匿名公钥

### 模块 2：知识签名模块（SoK / Signatures of Knowledge）

- **功能**：车辆生成零知识证明以认证消息，证明方知道 `(aski, lski, LPKi)` 满足关系：`APK1 = ask * P ∧ APK2 = LPK + ask * LPKm ∧ LPK = lsk * P`，同时不泄露私钥本身
- **包含算法**：
  - `PASK-GenProof`：单消息签名生成
  - `PASK-VerfProof`：单消息签名验证
  - `PASK-BVerfProof`：批量消息签名验证（使用随机向量防止恶意注入）

### 模块 3：智能合约模块（Smart Contract / APKList）

- **功能**：部署在区块链上管理匿名公钥的生命周期
- **包含算法**：
  - `Submit(APK1, APK2)`：仅 Manager 可调用，将匿名公钥写入链上
  - `Check(APK1, APK2)`：任何人可调用，检查某匿名公钥是否已授权且未被撤销
  - `Revoke(APK1, APK2)`：仅 Manager 可调用，撤销（逻辑删除）某匿名公钥

## 3.4 整体交互流程

```
 时间轴：系统启动 ──────────────────────────────────────────────►

 Phase 1: 系统初始化 (System Setup) —— 仅执行一次/离线

 │Vehicle│     │  CA   │     │ Manager  │     │ Blockchain │

    │                             │                  │

    │  PriKD(ask^{j-1}, pdi^{j-1}, j)│  PubKD(...)   │
    │                             │────Submit(APKj)─►│ ←约240个/2天

 Phase 3: 消息签名 (Message Signing) —— 实时
    │  Va: 派生匿名密钥对          │                  │
    │  生成签名: σ=PASK-GenProof  │                  │
    │═══广播 (msg, σ=(c,z1,z2,R1,R2), ts, APK1, APK2)═══► Vb

 Phase 4: 消息验证 (Message Verification) —— 实时
                                                      ┌──Vb──┐
    Vb:  ① Check(APK1, APK2) ─────────────────────────►│ BC   │
         ② 如果授权且未撤销:      ◄─── true/false ─────│      │
         ③ PASK-VerfProof(msg, σ, ts) → accept/reject  └──────┘

 Phase 5: 追溯 (Trace) —— 仅在检测到恶意行为时
                              ┌──────────┐
    Manager收到恶意(APK1,APK2)│ Manager  │
    LPKi = APK2 - lskm·APK1   │   追溯   │
    → 定位到真实车辆身份       └──────────┘
```

### 关键流程要点

1. **初始化阶段（Phase 1）**：车辆与 Manager 之间仅在注册时交互一次。之后所有匿名密钥派生都是**双方独立、非交互**的。这是方案"高效"的核心设计。
2. **实时签名（Phase 3）**：需要 2 次标量乘法计算 `Ri,1` 和 `Ri,2`，2 次模乘和 2 次模减法计算 `zi,1` 和 `zi,2`，1 次哈希计算 `ci`。整个签名仅涉及椭圆曲线群上操作，无需配对。
3. **实时验证（Phase 4）**：单个验证只需验证一次等式 `R1+R2 = (z1+z2)P + z1·LPKm + c(APK1+APK2)`，包含 3 次标量乘法和若干点加法。链上 Check 操作本质是一次 mapping 查找。
4. **批量验证**：n 个消息的批量验证使用小随机向量 `v_i ∈ [1, 2^t]` 防止攻击者注入互为负数的无效签名对。

## 3.5 安全/威胁模型

### 攻击者能力假设

- 攻击者是**概率多项式时间（PPT）**的
- 攻击者可以截获、篡改、删除无线信道中的传输数据
- 攻击者可以作为合法车辆参与网络（内部攻击者）
- 攻击者可以尝试破解椭圆曲线离散对数问题（ECDLP）

### 信任边界

- **可信实体**：CA、Manager、RSU
- **不可信实体**：部分车辆可能恶意、无线信道不可信
- **去信任依赖**：区块链的共识安全（抗 51% 攻击、抗生日碰撞、抗交易劫持）

### 安全目标

论文列出了 7 项安全要求：
1. **消息认证**（Message Authentication）：消息完整性和身份真实性
2. **条件隐私保护**（Conditional Privacy-Preserving）：仅 Manager 可追溯
3. **不可链接性**（Unlinkability）：同一车辆的两条消息无法被关联
4. **抗生日碰撞**（Resilient to Birthday Collision）：区块链不会同时链接两个相同哈希的区块
5. **抗劫持**（Resilient to Hijacking）：有效交易不会被恶意阻止上链
6. **抗 51% 攻击**（Resilient to 51% Attacks）：依赖底层区块链的共识安全
7. **抗其他攻击**：包括冒充、修改、DDoS、重放、中间人、验证表窃取、侧信道等常见攻击

> **注意**：第 4、5、6 项安全要求实际上是由底层区块链系统（Ethereum/Hyperledger）保证的，而非 EBCPA 协议本身的贡献。论文在这一点上存在"借用底层系统安全性"的情况，将在第 6 章讨论。
