# 5. 实验与评估

## 5.1 实验设计

实验的核心目标是验证 EBCPA 在实际环境中的**效率优势**，覆盖以下维度：

1. **链上成本**：在 Ethereum 测试网（Rinkeby）上部署智能合约，测量各函数的 Gas 消耗
2. **链上性能**：在 Hyperledger 测试网上测量 Submit/Check/Revoke 的延迟和吞吐量
3. **密码学计算开销**：理论分析（按操作数量）和实测（Miracl 库）对比各方案在各阶段的耗时
4. **通信开销**：签名/密文长度对比
5. **VANETs 场景仿真**：在 VanetMobiSim + NS-2 平台上模拟真实道路场景，测量消息认证延迟（APD）和丢包率（PLR）

## 5.3 对比方案

| 方案 | 核心技术 | 选择理由 |
|------|---------|---------|
| **CertCoin [18]** | 门限环签名 | 最早的区块链+VANETs CPPA 方案之一，代表性对比基准 |
| **BCPPA [14]** | 密钥派生 + 区块链 | 同一作者的前期工作，最直接的对比对象（EBCPA 是对它的改进） |
| **BPAS [20]** | 属性基加密 (ABE) + 区块链 | 较新的区块链 CPPA 方案，采用截然不同的密码学路径 |

## 5.4 实验结果分析

### 5.4.1 Gas 成本（Ethereum Rinkeby）

| 操作 | 交易成本 (USD) | 执行成本 (USD) | 备注 |
|------|---------------|---------------|------|
| 部署智能合约 | $0.5414 | $0.2229 | 仅执行一次 |
| Submit | < $0.10 | < $0.08 | 周期性批量执行（~240 次/2 天） |
| Check | $0.0159 | $0.0012 | 每次验证都要调用 |
| Revoke | < $0.01 | - | 仅在检测到恶意行为时调用 |

**分析**：
- Check 的操作成本极低（$0.0159），这对于高频率的验证操作至关重要
- 最昂贵的部署操作仅执行一次，可以被摊销
- 按照论文的批量提交策略（240 个/2 天 ≈ 120 个/天），每日的 Submit 成本约 $0.08 × 120 = $9.6（可接受）

### 5.4.2 延迟与吞吐量（Hyperledger）

| 算法 | 成功率 | 平均延迟 (s) | 吞吐量 (TPS) | 请求率 (TPS) | 完成率 |
|------|--------|-------------|-------------|-------------|--------|
| Submit | 500/500 | 0.25 | 22.8 | 25.1 | 90.8% |
| Check | 500/500 | 0.01 | 314.5 | 315.3 | 99.7% |
| Revoke | 500/500 | 0.01 | 335.8 | 336.7 | 99.7% |

**分析**：
- Check 的极低延迟（10ms）和极高吞吐量（314.5 TPS）是关键指标——验证操作是 VANETs 中最高频的操作
- Submit 延迟较高（250ms）但这是离线/周期性操作，不影响实时通信
- Hyperledger 的完成率均超过 90%，满足实际应用需求

### 5.4.3 计算开销（理论分析）

| 阶段 | EBCPA | CertCoin [18] | BCPPA [14] | BPAS [20] |
|------|-------|--------------|-----------|----------|
| **消息签名** | `4Tsm + 3Tmm + Th` | 依赖于 `(r, t, u)` | `3Tsm + 2Tmm + 3Tpa + Th` | `3Tpa + Tme + Tmm + TAEnc` |
| **单消息验证** | `3Tsm + Tpa + Th` | 依赖于 `(r, t, u)` | `3Tsm + 3Tpa + Th` | `4Tpa + Tme + TADec` |
| **追溯** | **`Tsm + Tpa`** (常数) | - | `k(Tsm + Th)` (线性) | `Tsm + Tpa` (但常数较大) |

### 5.4.4 实测计算耗时

| 操作 | CertCoin | BCPPA | BPAS | EBCPA | EBCPA 优势 |
|------|---------|-------|------|-------|-----------|
| 消息签名 | 196.11 ms | 32.84 ms | 401.41 ms | **31.85 ms** | 节省 3%-92% |
| 单次验证 | 391.14 ms | 42.05 ms | 98.11 ms | **24.30 ms** | 节省 42%-94% |
| 追溯 | 21.12 ms | 106.01 ms (`k=10`) | 87.56 ms | **10.78 ms** | 节省 49%-90% |

**通信开销**：

| 方案 | 通信开销 (bytes) |
|------|-----------------|
| CertCoin | `168r + 40`（随环大小线性增长） |
| BCPPA | 264（最小） |
| BPAS | `128l + 64`（随属性数量线性增长） |
| EBCPA | **392**（常数） |

**分析**：
- EBCPA 的通信开销（392 bytes）虽然不是最小，但比 BCPPA 的 264 bytes 仅多 128 bytes（约 48% 增长），换来的是追溯效率从 `O(k)` 降至 `O(1)` 和验证效率提升 42% 以上，这个 trade-off 是合理的
- 与 CertCoin 和 BPAS 相比，EBCPA 在所有维度（签名、验证、追溯、通信开销）都有显著优势

### 5.4.5 n-消息批量验证

- 所有方案的批量验证耗时均随 n 线性增长
- EBCPA 的增长率（斜率）最低——每增加一个消息，EBCPA 仅增加约 2 次标量乘法 + 若干点加法，而 CertCoin 的门限环签名、BPAS 的 ABE 解密均随参数增长更快

### 5.4.6 VANETs 仿真结果

**车辆密度的影响（Fig. 7）**：
- 密度 ≤ 50 辆时：APD 变化很小（< 10ms 波动），表现稳定
- 密度 > 50 辆时：APD 快速增加（信道竞争加剧），PLR 增长率放缓（因大量数据包因冲突而非距离被丢弃）

**车辆速度的影响（Fig. 8）**：
- PLR 几乎不变（~18.1%），因为丢包主要由距离决定——只有超出通信范围的数据包才被丢弃
- APD 波动较大（但 < 36ms 波动范围），因为速度变化导致车辆间距不可预测

## 5.5 实验评价

### 实验的充分性

| 维度 | 评价 |
|------|------|
| **区块链平台覆盖** | ✅ 充分。同时测试了公有链（Ethereum）和许可链（Hyperledger） |
| **对比方案选择** | ✅ 合理。涵盖了同方向的最新工作 |
| **仿真场景** | ⚠️ 一般。仅 4 RSU、最大 100 辆车的小规模场景。实际城市可能有数万辆车辆，未讨论可扩展性 |
| **参数设定** | ⚠️ 部分关键参数未明确说明。如 BCPPA 对比中 `k=10` 的选择依据（实际场景中 k 可能远大于 10） |

### 实验的不足

1. **缺乏攻击实验**：仅测试了正常场景下的性能，没有模拟恶意节点或攻击场景下的协议行为
2. **未讨论 Check 操作的网络延迟**：理论分析中省略了 `tx_rtv` 和 `eth_calls` 的时间，但实际场景中区块链检索延迟可能不可忽略
3. **Hyperledger 节点数过少**：仅 2 个组织各 1 个 peer（共 2 节点），不能代表实际生产环境的共识延迟
4. **BN 曲线的选择令人困惑**：EBCPA 使用配对友好曲线 BN256 但未使用任何配对操作。这可能是为了与使用配对的方案做"公平"比较
5. **仿真时长过短**：仅 100 秒的仿真时长对于 VANETs 场景偏短，不足以观察长期运行中的缓存、密钥管理等问题
