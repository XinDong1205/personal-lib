# 4. 核心技术原理深度拆解

## 4.1 重构密钥派生方案（Reconstructed KeyDer）

### 目的
使车辆和 Manager 在仅初始化交互一次后，能各自独立、无交互地派生出同一公钥对应的链式匿名密钥对，同时保证只有 Manager 能从任意匿名公钥恢复真实身份。

### 核心思想
基于 BIP32（比特币分层确定性钱包）的思想，用哈希链生成密钥序列。关键创新在于：匿名公钥的第二个分量 `APK2` 中嵌入了 `LPK_i + lskm * APK1` 的关系式，使 Manager 的 `lskm` 天然具备追溯能力。

### 详细机制

**1) 初始化 — `KDGen(pseed)`**

车辆选择一个私有种子的哈希值 `H(pseed)`，将其拆分为两部分：
- 高半部分 `hl` → 根匿名私钥 `ask_root = hl (mod q)`
- 低半部分 `hr` → 根派生信息 `pdi_root = hr (mod q)`

计算根匿名公钥对：
- `APK_root,1 = ask_root * P`
- `APK_root,2 = LPK_i + ask_root * LPK_m`

> **关键设计**：`APK_root,2` 中的 `ask_root * LPK_m` 项是追溯的关键。因为 `LPK_m = lskm * P`，Manager 可通过 `APK_root,2 - lskm * APK_root,1 = LPK_i` 直接恢复真实公钥。

**2) 私钥派生 — `PriKD(ask^{j-1}_i, pdi^{j-1}_i, j)`**

```
APK^{j-1,1}_i = ask^{j-1}_i · P
hl || hr = H(APK^{j-1,1}_i || j, pdi^{j-1}_i)
ask^j_i = ask^{j-1}_i · hl (mod q)
pdi^j_i = hr (mod q)
```

- 每一步派生都是**乘法更新**（而非加法），因为 `hl` 和 `pdi^{j-1}_i` 都是之前哈希的产物，提供了前向安全性

**3) 公钥派生 — `PubKD(APK^{j-1,1}_i, pdi^{j-1}_i, j, LPK_i, lskm)`**

```
hl || hr = H(APK^{j-1,1}_i || j, pdi_root_i)
APK^{j,1}_i = hl · APK^{j-1,1}_i
pdi^j_i = hr (mod q)
APK^{j,2}_i = LPK_i + lskm · APK^{j,1}_i
```

- Manager 不需要知道 `ask^j_i`，只需用 `hl` 乘以已知的上一次公钥即可得到新公钥 `APK^{j,1}_i`
- `APK^{j,2}_i` 的构造保证了每一级的匿名公钥都可以被 Manager 追溯

### 安全性分析

该密钥派生方案的安全性可归约到**离散对数假设（DLP）**：
- 给定 `APK^{j,1}_i`，攻击者无法逆推出 `APK^{j-1,1}_i` 或根公钥 `APK_root,1_i`，因为这需要求解 DLP 或逆转安全哈希
- `pdi_root_i`（根派生信息）仅由车辆和 Manager 知晓，攻击者无法独立计算派生因子

### 创新点分析

- **与传统 BIP32 的区别**：BIP32 使用加法链，而 EBCPA 使用乘法链（`hl · APK^{j-1,1}`），保证了椭圆曲线群上的运算封闭性
- **追溯的内嵌性**：追溯逻辑直接编码在匿名公钥的代数结构中（`APK2 = LPK + lskm * APK1`），而不是通过额外的索引或映射表实现

## 4.2 知识签名方案（Signatures of Knowledge, SoK）

### 目的
使签名者以零知识方式证明其拥有对应于某个已授权匿名公钥的私钥，同时将消息和时戳绑定到证明中（作为数字签名），且不泄露任何私钥信息。

### 核心思想
将三个离散对数关系（`APK1 = ask·P`, `LPK = lsk·P`, `APK2 = LPK + ask·LPKm`）打包成一个 Σ-协议，利用其中两个关系的证明者承诺值 `Ri,1 = ri,1·P` 和 `Ri,2 = ri,2·P + ri,1·LPKm` 的巧妙构造，确保验证等式 `R1+R2 = (z1+z2)P + z1·LPKm + c(APK1+APK2)` 对诚实证明者始终成立。

### 详细机制

**1) 证明关系定义**

SoK 证明以下知识的零知识证明：

$$SoK\{(lsk_i, ask^j_i, LPK_i) : APK^{j,1}_i = ask^j_i \cdot P \land APK^{j,2}_i = LPK_i + ask^j_i \cdot LPK_m \land LPK_i = lsk_i \cdot P\}(msg, ts)$$

**2) 签名生成 — `PASK-GenProof`**

```
输入: xi = (P, APK1, APK2, LPKm), wi = (ask, lsk, LPK), msgi, tsi

① 随机选择 ri,1, ri,2 ∈ Z*_q
② 计算承诺:
   Ri,1 = ri,1 · P
   Ri,2 = ri,2 · P + ri,1 · LPKm
③ 计算挑战（Fiat-Shamir 启发式）:
   ci = H(xi || msgi || tsi || P || APK1 || APK2 || LPKm || Ri,1 || Ri,2)
④ 计算响应:
   zi,1 = ri,1 - ask · ci (mod q)
   zi,2 = ri,2 - lsk · ci (mod q)
⑤ 输出: σi = (ci, zi,1, zi,2, Ri,1, Ri,2)
```

**3) 单签名验证 — `PASK-VerfProof`**

```
输入: xi, (msgi, σi, tsi)

① 解析 σi = (ci, zi,1, zi,2, Ri,1, Ri,2)
② 重新计算 ci' = H(xi || msgi || tsi || P || APK1 || APK2 || LPKm || Ri,1 || Ri,2)
③ 验证等式:
   Ri,1 + Ri,2 ≟ (zi,1 + zi,2) · P + zi,1 · LPKm + ci · (APK1 + APK2)
④ 如果相等则输出 1 (接受)，否则输出 0 (拒绝)
```

**验证等式正确性推导**：

右键 = `(zi,1 + zi,2)P + zi,1·LPKm + ci(APK1+APK2)`

展开代入 `zi,1 = ri,1 - ask·ci`, `zi,2 = ri,2 - lsk·ci`：

`= (ri,1 - ask·ci + ri,2 - lsk·ci)P + (ri,1 - ask·ci)LPKm + ci(ask·P + LPK + ask·LPKm)`

`= (ri,1 + ri,2)P - ci(ask + lsk)P + ri,1·LPKm - ask·ci·LPKm + ci·ask·P + ci·LPK + ci·ask·LPKm`

消去 `-ci(ask+lsk)P` 和 `+ci·ask·P + ci·LPK`（注意 `LPK = lsk·P`）：

`= (ri,1 + ri,2)P + ri,1·LPKm - ask·ci·LPKm + ci·ask·LPKm`

`= ri,1·P + ri,2·P + ri,1·LPKm = Ri,1 + Ri,2` ✓

**4) 批量验证 — `PASK-BVerfProof`**

核心是为每个消息引入一个小随机数 `vi ∈ [1, 2^t]`：

$$ \sum_{i=1}^{n} [v_i (R_{i,1} + R_{i,2})] \stackrel{?}{=} \left( \sum_{i=1}^{n} v_i (z_{i,1} + z_{i,2}) \right) P + \left( \sum_{i=1}^{n} v_i z_{i,1} \right) LPK_m + \sum_{i=1}^{n} [v_i c_i (APK^{j,1}_i + APK^{j,2}_i)] $$

随机向量 `vi` 的引入是为了防止攻击者注入互为负数的无效签名对（两个无效签名组合后恰好满足聚合等式）。这是批量验证中的标准防护技术（small exponent test）。

### 安全性证明（Theorem 1）

论文证明了 SoK 方案在随机预言机模型下满足以下三个性质：

**1) 完美完备性（Perfect Completeness）**
任何由 `PASK-GenProof` 诚实生成的签名必定通过 `PASK-VerfProof` 和 `PASK-BVerfProof` 的验证。上述展开推导证明了这一点，且概率恰好为 1（"perfect"）。

**2) 可靠性（Soundness）**
通过构造知识提取器（Extractor）来证明：如果存在 PPT 证明者 `P*` 能以不可忽略概率生成有效签名，则 Extractor 可以利用回退（rewinding）技术获得两个有效签名 `(c, z1, z2)` 和 `(ĉ, ẑ1, ẑ2)`，然后计算：

```
ask = (z1 - ẑ1) · (ĉ - c)^{-1} (mod q)
lsk = (z2 - ẑ2) · (ĉ - c)^{-1} (mod q)
```

这直接提取出全部私钥，证明了知识的存在性。

**3) 零知识性（Zero-Knowledge）**
论文构造了模拟器 `Sim`（Algorithm 2），其策略是"先选挑战再填承诺"的经典方法：

```
① 随机选 ĉ, ẑ1, ẑ2
② 反推承诺:
   Ŕ1 = ẑ1·P + ĉ·APK1
   Ŕ2 = ẑ2·P + ẑ1·LPKm + ĉ·APK2
③ 编程随机预言机: OH(x||msg||ts||...||Ŕ1||Ŕ2) = ĉ
```

模拟产生的 transcript 与真实交互产生的 transcript 具有相同的分布，且 Sim 不涉及任何秘密信息。

### 创新点分析

- **三合一关系打包**：传统 SoK 通常仅证明一个关系，EBCPA 的 SoK 同时证明了三个相关关系（ask、lsk、LPK 之间的约束），且用一个简洁的验证等式统一验证
- **Ri,2 的巧妙构造**：`Ri,2 = ri,2·P + ri,1·LPKm` 中的 `ri,1·LPKm` 项是消去验证中等式交叉项的关键——这利用了 `LPKm` 为公开参数的性质，将两个随机数 `ri,1, ri,2` 的承诺编码进了两个群元素中

## 4.3 智能合约设计

### 数据结构

```
struct APK {
    APK1;  // uint256[2], 椭圆曲线点坐标
    APK2;  // uint256[2], 椭圆曲线点坐标
}
mapping(uint256 => APK) apk;  // H(APK1, APK2) 作为索引
```

### 三个核心函数

| 函数 | 调用权限 | Gas 成本 | 功能 |
|------|---------|---------|------|
| `Submit(APK1, APK2)` | 仅 Manager | ~$0.08 | 将匿名公钥写入 mapping |
| `Check(APK1, APK2)` | 任何人 | ~$0.016 | 检查匿名公钥是否已授权 |
| `Revoke(APK1, APK2)` | 仅 Manager | ~$0.01 | 将匿名公钥置为 NULL（逻辑删除） |

### 设计要点

- **索引机制**：使用 `H(APK1, APK2)` 作为 mapping 的键，使得 Check 操作为 `O(1)` 的哈希查找
- **逻辑删除**：Revoke 将对应位置设为 NULL 而非物理删除，这是因为区块链的不可篡改性
- **无 Gas 优化**：Check 函数标记为 `view`，不修改状态，因此在 Ethereum 中作为 `eth_call` 执行时不消耗 Gas

## 4.4 EBCPA 协议的完整安全性分析

### 匿名性证明（Theorem 2 + Definition 1）

**形式化定义**：对于 PPT 敌手 `A = (A1, A2)`，考虑实验 `EXP^b_an`：
1. 生成 Manager 密钥对 `(LPKm, lskm)`
2. `A1` 选择两个挑战长期公钥对 `(LPK0, lsk0)` 和 `(LPK1, lsk1)`
3. 根据 `b ∈ {0,1}`，使用 `lsk_b` 生成匿名密钥和消息签名 `(m, σb, ts)`
4. `A2` 获得 `(m, σb, ts)`，输出猜测 `b'`

如果 `|Pr[EXP^0 = 1] - Pr[EXP^1 = 1]| ≤ negl(λ)`，则 EBCPA 具有匿名性。

**证明策略**：通过三个混合实验（Hybrid Experiments）从 `EXP^0` 逐步过渡到 `EXP^1`，每次过渡的可区分优势均为 `negl(λ)`（归约到 SoK 的零知识性）。

### 可追溯性分析

追溯的核心公式：

$$LPK_i = APK^{j,2}_i - lskm \cdot APK^{j,1}_i$$

**正确性验证**：
```
APK2 - lskm·APK1 = (LPK + ask·LPKm) - lskm·(ask·P)
                  = LPK + ask·(lskm·P) - lskm·ask·P
                  = LPK + ask·lskm·P - lskm·ask·P
                  = LPK ✓
```

追溯的时间复杂度为 `O(1)`（1 次标量乘法 + 1 次点减法），这是 EBCPA 相比 BCPPA [14] 在线性搜索 `O(k)` 下最显著的改进。

### 不可链接性分析

每次通信使用全新的匿名公钥（由 KeyDer 的哈希链保证），且 SoK 的零知识性保证了签名本身不泄露任何可供链接的信息。证明通过 SoK 的零知识性直接归约：如果敌手能链接两个消息，则可破坏 SoK 的零知识性。
