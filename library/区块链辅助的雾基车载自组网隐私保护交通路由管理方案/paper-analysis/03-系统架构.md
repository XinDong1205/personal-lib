## 3.2 参与实体与角色

| 实体 | 缩写 | 信任假设 | 核心职责 |
|------|------|----------|----------|
| 可信机构 | TA | 完全可信、不可妥协 | 系统初始化、车辆/雾节点注册、恶意行为追溯、公钥链上管理 |
| 雾节点 | FN | 半诚实（Honest-but-Curious），不主动泄露信息 | 广播路由请求、验证车辆签名（支持批量）、同态聚合加密路线、转发给 TMC |
| 车辆 | $V_i$ | 不可信（需认证），计算能力有限 | 加密并签名上报行驶路线、接收交通导引 |
| 交通管理中心 | TMC | 可信（持有 Paillier 私钥） | 生成同态加密密钥、解密聚合路线、交通调度决策 |
| 区块链 | BC | 防篡改的去中心化账本 | 通过智能合约存储和管理车辆公钥表（VPKT） |

**信任边界的几个关键点**：

- TA 是系统的信任锚点，一旦妥协整个系统沦陷。论文承认这一点但未深入讨论风险缓解措施。
- 雾节点是半诚实的：它执行协议但可能对个体路线好奇。同态加密确保它"不能"看到明文路线（只能看到聚合结果），这是一个技术性隐私保证（而非仅靠信任假设）。
- 车辆是不可信的：它们可能发送虚假路线、冒充其他车辆、或恶意重复发送。ECC 签名 + 区块链公钥查询用于认证；智能合约投票机制用于撤销恶意车辆。
- TMC 持有 Paillier 私钥，可以解密聚合密文，但它获得的是聚合值而非个体路线——这个隐私保证依赖于"聚合足够多车辆后个体信息被掩盖"。

## 3.3 模块划分与分工

系统可以划分为以下功能模块：

### 模块 A：密码学基础设施模块

| 子模块 | 负责实体 | 核心技术 |
|--------|----------|----------|
| ECC 参数生成 | TA | secp160r1 椭圆曲线群 $G$，生成元 $P$，阶 $q$ |
| 签名算法 | 车辆 / 雾节点 | Schnorr 类签名：$\sigma = sk + d \cdot \beta \mod q$ |
| 签名验证（单个/批量） | 雾节点 / TMC | $\sigma \cdot P = VPK + D \cdot \beta$；批量：$\sum (u_i \cdot \sigma_i) \cdot P = \sum (u_i \cdot VPK_i) + \sum (u_i \cdot D_i \cdot \beta_i)$ |
| 同态密钥生成 | TMC | Paillier: $n=p \cdot q$，公钥 $(n,g)$，私钥 $(\lambda, \mu)$ |
| 路线加密 | 车辆 | $C = g^{F(i)} \cdot r^n \mod n^2$ |
| 路线聚合 | 雾节点 | $\phi_{sum} = \prod \phi_i \mod n^2$（密文乘法） |
| 聚合解密 | TMC | $M = L(C^\lambda \mod n^2) \cdot \mu \mod n$ |

### 模块 B：身份与密钥管理模块

| 子模块 | 负责实体 | 机制 |
|--------|----------|------|
| 车辆注册 | TA → 车辆 | 安全信道下发 $sk_i$、$PID_i$、VPK |
| 雾节点注册 | TA → 雾节点 | 下发 $sk_j$、$PK_j$ |
| 链上公钥存储 | TA → 区块链 | `updatePK(PID, VPK)` 写入智能合约 |
| 链上公钥查询 | 雾节点 → 区块链 | `queryPK(PID)` → 返回 VPK |
| 恶意投票 | 雾节点 → 区块链 | `VoteUser(PID)` 触发计数器 |
| 公钥删除 | TA → 区块链 | `deletePK(PID)` 当 VoteCount ≥ 阈值 |

### 模块 C：路线隐私保护与交通调度模块

| 子模块 | 输入 | 输出 | 隐私保证 |
|--------|------|------|----------|
| 路线编码 | 行驶路段选择 | 二进制向量 $\{F_1(V),...,F_m(V)\}$ | — |
| 路线加密 | 二进制向量 | $\phi_i$ (Paillier 密文) | 雾节点不可解密 |
| 同态聚合 | $\{\phi_1,...,\phi_k\}$ | $\phi_{sum}$ | 聚合在密文上进行 |
| 聚合解密 | $\phi_{sum}$ | $RI = \sum F_0(i) \|\| ... \|\| \sum F_m(i)$ | TMC 仅见聚合值 |
| 交通调度 | 各路段车辆数 | 导引消息 → 车辆 | — |

## 3.5 安全/威胁模型

### 攻击者能力假设

论文采用标准的安全模型（Random Oracle Model 下可证明安全），攻击者类型 $A$ 的能力如下：

| 能力类型 | 描述 |
|----------|------|
| 信道控制 | $A$ 可以修改、拦截和伪造通信消息（Dolev-Yao 网络模型） |
| 密码学能力 | $A$ 可以在多项式时间内进行任意密码学操作，但不能以不可忽略概率破解 ECDLP |
| 哈希查询 | $A$ 可以向随机预言机（Random Oracle）$h_2$、$h_5$ 发起查询 |
| 签名查询 | $A$ 可以自适应地请求任意消息的签名（Adaptive Chosen Message Attack） |

### 安全目标

| 目标 | 形式化要求 | 实现机制 |
|------|------------|----------|
| EUF-CMA 安全性 | $A$ 对未签名过的消息生成有效签名的概率可忽略 | ECDLP 归约 + Forking Lemma |
| 不可链接性 (Unlinkability) | 被动敌手无法关联同一车辆的多条消息 | 假名动态更新 + 随机数 |
| 相互认证 | 通信实体间能验证彼此身份和消息完整性 | ECC 签名双向验证 |
| 身份隐私 | 敌手无法从假名反推真实身份 | 假名 = ID ⊕ 哈希（需系统私钥恢复） |
| 可追溯性 | TA 能唯一恢复恶意车辆的真实身份 | TA 利用系统私钥 s 计算 ID |
| 抗重放攻击 | 过期消息被拒绝 | 时间戳 + 新鲜度检查 $\|t - t_{cur}\| \leq \Delta t$ |
| 抗中间人攻击 | 敌手无法成功篡改/伪造消息 | ECDLP 困难性保证 |
| 抗离线密码猜测 | 即使 TA 数据库被攻破也无法恢复密码 | 密码哈希加密存储 $UPW = h_1(UID\|PW)$ |
| 抗修改攻击 | 修改后的消息无法通过签名验证 | 哈希函数抗碰撞性 + ECDLP |
| 抗冒充攻击 | 敌手无法生成有效的车辆或雾节点签名 | 缺少 $sk_i$/$sk_j$ 信息 |

### 信任边界的核心矛盾与折衷

值得注意的一个设计选择：**TA 拥有追溯能力**（能从假名恢复真实身份），这意味着 TA 必须持有系统主私钥 $s$。这在功能上是必要的（Conditional Privacy 要求），但 TA 单点安全假设很强——一旦 $s$ 泄露，所有车辆的身份隐私全部暴露。论文的"完全可信且不可妥协"假设在实践中需要通过硬件安全模块（HSM）或门限秘密共享来加固，但论文未讨论这一点。
