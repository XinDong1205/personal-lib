## 4.1 ECC 签名方案：Schnorr 类单签名 + 批量验证

### 目的
实现对车辆和雾节点消息的轻量级认证，避免双线性配对的高计算开销，同时支持雾节点同时验证多条车辆消息（批量验证）。

### 核心思想
采用 ECC 上的 Schnorr 类签名结构 $\sigma = sk + d \cdot \beta \mod q$，签名验证仅需两次标量乘法和一次点加法。批量验证利用小指数测试（Small Exponent Test）技术，将 $n$ 次验证合并为一次验证，将复杂度从 $O(n)$ 次标量乘法降到约 $O(n)$ 次但常数显著更小。

### 详细机制

#### 单个签名生成（车辆侧）

1. 车辆 $V_i$ 拥有 TA 签发的私钥 $sk_i = h_2(ID_i\|s\|k_i)$，其中 $s$ 是系统主私钥
2. 车辆选择随机数 $d_i \in Z_q^*$，计算 $D_i = d_i \cdot P$
3. 计算哈希 $\beta_i = h_5(PID_i\|D_i\|\phi_i\|T_{i1})$，将消息绑定到当前时间戳
4. 生成签名：$\sigma_{Vi} = sk_i + d_i \cdot \beta_i \mod q$
5. 发送消息 $M_{vi} = \{\sigma_{Vi}, \phi_i, D_i, PID_i, T_{i1}\}$

#### 单个签名验证（雾节点侧）

验证者检查等式：

$$\sigma_{Vi} \cdot P = VPK_i + D_i \cdot \beta_i$$

正确性推导：

$$\sigma_{Vi} \cdot P = (sk_i + d_i \cdot \beta_i) \cdot P = sk_i \cdot P + d_i \cdot \beta_i \cdot P = VPK_i + D_i \cdot \beta_i$$

验证者需要从区块链查询 $VPK_i$（通过 `queryPK(PID_i)`）。签名长度的优势在于仅需一个群元素 $D_i$（40 bytes）加一个标量 $\sigma_{Vi}$（20 bytes）。

#### 批量签名验证

当雾节点收到 $n$ 条消息 $\{M_{v1}, M_{v2}, ..., M_{vn}\}$ 时：

1. 首先逐一检查每个消息的时间戳 $T_{i1}$ 是否新鲜，丢弃过期的
2. 选择随机向量 $\mathbf{u} = \{u_1, u_2, ..., u_n\}$，其中 $u_i \in [1, 2^t]$ 且 $t$ 为小整数
3. 对每条消息从链上查询 $VPK_i$，计算 $\beta_i = h_5(PID_i\|D_i\|\phi_i\|T_{i1})$
4. 验证以下等式（而非逐一验证 $n$ 个等式）：

$$\left(\sum_{i=1}^{n} u_i \cdot \sigma_{Vi}\right) \cdot P = \sum_{i=1}^{n} (u_i \cdot VPK_i) + \sum_{i=1}^{n} (u_i \cdot D_i \cdot \beta_i)$$

**小指数测试（Small Exponent Test）的作用**：如果不加随机向量 $\mathbf{u}$，攻击者可以构造两个消息 $(M_{v1}, M_{v2})$ 使得它们各自的签名都无效，但组合后恰好满足批量验证方程（消去误差项），从而绕过验证。随机向量 $\mathbf{u}$ 使得这种攻击的成功概率降至 $2^{-t}$，$t = 80$ 时可忽略不计。

**计算量对比**：
- 逐个验证：$2n$ 次标量乘法 + $n$ 次点加法
- 批量验证：$n+1$ 次标量乘法 + $n$ 次点加法 + $n$ 次小整数乘法（便宜）

当 $n$ 很大时，批量验证约节省一半的标量乘法。

### 创新点分析

与标准 Schnorr 签名（$\sigma = sk + H(M\|R) \cdot r$）的区别在于：

- 标准 Schnorr 中私钥 $sk$ 和随机数 $r$ 对签名有对称影响；本方案中 $sk_i$ 由 TA 签发（关联到系统主私钥 $s$），这是实现"条件可追溯"的关键——TA 掌握 $s$，能通过 $VPK_i = sk_i \cdot P$ 和 $sk_i = h_2(ID_i\|s\|k_i)$ 反向追溯
- 批量验证的正确性完全基于 ECC 点加法的交换性和标量乘法的分配律，无需额外的密码学假设

## 4.2 Paillier 同态加密实现路线隐私保护

### 目的

让雾节点能聚合所有车辆的路线密文，而不需要（也不应该）解密任何个体的路线；TMC 解密后仅获取每个路段的车辆总数。

### 核心思想

利用 Paillier 密码系统的**加法同态性**：$E(m_1) \cdot E(m_2) = E(m_1 + m_2) \mod n^2$。但注意这里的"加法"不是直接在加密值上做加法——而是利用路线编码的二进制位分离技术，将多路段的聚合映射到同一条密文的乘法操作上。

### 详细机制

#### 步骤 1：路线编码（二进制位分离）

假设一个区域有 $m$ 个路段，每个路段用 $nbits$ 位表示。车辆 $V_i$ 的路线被编码为一个二进制向量：

$$\{F_0(V_i), F_1(V_i), ..., F_m(V_i)\}$$

其中 $F_j(V_i)$ 的位宽为 $nbits$，$nbits = \lceil \log_2(\text{最大车辆数}) \rceil$。

**示例**（$m=5$, $nbits=3$）：路线 `{001, 000, 001, 000, 000}` 表示该车将在第 1 和第 3 路段行驶，其余路段不行驶。

这里的编码技巧在于：将 $F_0 \| F_1 \| ... \| F_m$（位拼接）视为一个大整数进行加密。

#### 步骤 2：单车辆加密（Paillier 加密）

车辆选择随机数 $r_i \in Z_n^*$，加密拼接后的路线：

$$\phi_i = g^{F_0(i) \| F_1(i) \| ... \| F_m(i)} \cdot r_i^n \mod n^2$$

其中 $(n, g)$ 是 TMC 的公钥。

#### 步骤 3：雾节点同态聚合（密文乘法）

雾节点将所有接收到的 $\phi_i$ 相乘：

$$\phi_{sum} = \prod_{i=0}^{k} \phi_i \mod n^2$$

展开推导（核心步骤）：

$$\phi_{sum} = \prod_{i=0}^{k} g^{F_0(i)\|...\|F_m(i)} \cdot r_i^n \mod n^2$$

$$= g^{\sum_{i=0}^{k} (F_0(i)\|...\|F_m(i))} \cdot \left(\prod_{i=0}^{k} r_i\right)^n \mod n^2$$

由于二进制编码的位分离性质，和的位拼接与位拼接的和在无进位时等价：

$$g^{\sum_{i=0}^{k} (F_0(i)\|...\|F_m(i))} = g^{\left(\sum_{i=0}^{k} F_0(i)\right) \| \left(\sum_{i=0}^{k} F_1(i)\right) \| ... \| \left(\sum_{i=0}^{k} F_m(i)\right)}$$

**前提条件**：每个路段的聚合值不超过 $2^{nbits} - 1$，否则发生进位破坏位隔离。$nbits$ 必须选得足够大。

#### 步骤 4：TMC 解密聚合值

TMC 使用 Paillier 私钥 $(\lambda, \mu)$ 解密：

$$RI = D(\phi_{sum}) = L(\phi_{sum}^\lambda \mod n^2) \cdot \mu \mod n$$

其中 $L(x) = (x-1)/n$。

解密得到的 $RI$ 是一个大整数，按 $nbits$ 分组即可读出每个路段的车辆总数。

**实例验证**（来自论文 Table II）：假设 6 辆车，5 个路段：
- V1: 001 000 001 000 000（路段 1 和 3）
- V2: 001 001 001 000 001（路段 1, 2, 3, 5）
- ...（其余车辆上报类似数据）

聚合结果：$\sum F_1 = 2$, $\sum F_2 = 3$, $\sum F_3 = 5$, $\sum F_4 = 2$, $\sum F_5 = 6$

TMC 知道路段 5 有 6 辆车（最拥挤），路段 1 仅有 2 辆——可以引导车辆避开路段 5。

### 创新点分析

这个方案的关键创新在于**路线编码的位分离技术**：

1. 传统思路：对每个路段的计数分别加密 → $m$ 个 Paillier 密文 → 通信开销 $O(m)$
2. 本方案：将所有路段的路线拼接为一个大整数，一次加密 → 1 个 Paillier 密文 → 通信开销 $O(1)$（128 bytes）

代价是 $nbits$ 必须足够大以防止进位溢出。以 $nbits = 10$（支持最多 1023 辆车）和 $m = 20$ 个路段计算，需要 200 位，远小于 Paillier 模数 $n$（1024 位），所以单次加密可行。

### 安全性/正确性分析

- **隐私保证**：Paillier 密码系统在 Decisional Composite Residuosity Assumption (DCRA) 下是 IND-CPA 安全的。雾节点只看到语义安全的密文，无法区分任何两条路线。
- **聚合可信性**：雾节点在密文层面做乘法，无法篡改聚合结果而不被发现（一旦篡改，解密将得到错误结果，但无法"选择性"篡改某个特定路段的值）。
- **弱点**：雾节点可以丢弃某些车辆的密文而不聚合（Denial of Service），但这属于可用性问题而非隐私问题。论文未讨论这一攻击向量。

## 4.3 区块链智能合约实现公钥管理

### 目的

用去中心化的方式管理车辆公钥（VPK）的全生命周期——注册、查询、投票撤销、删除——消除对 TA 在线性的依赖，利用区块链的不可篡改性和智能合约的自动执行特性。

### 核心思想

将车辆公钥表（VPKT）存储在以太坊智能合约中。公钥与车辆假名（PID）绑定，雾节点在验证签名时查询合约获取 VPK；恶意行为的投票撤销机制由多个雾节点的共识触发。

### 详细机制：四个智能合约函数

#### Algorithm 1: updatePK（公钥注册/更新，仅 TA 可调用）

```
Input:  address user, uint256 txid
Output: bool result

1: require(SC.status is True);
2: if msg.sender is not TA then throw;
3: if Exist(VPKT[i].VPK == VPK) then
4:     VPKT[i].VPK = newVPK;
5:     return True;
6: else
7:     return false;
```

**机制分析**：`msg.sender` 检查确保只有 TA 可以更新公钥，防止车辆自行注册任意公钥。`txid` 参数用于映射车辆身份到交易 ID（实现身份与链上地址的解耦）。

#### Algorithm 2: queryPK（公钥查询，任意节点可调用）

```
Input:  address user
Output: bool result

1: require(SC.status is True);
2: if Exist(VPKT[i].VPK == VPK) then
3:     return True;
4: else
5:     return false;
```

**机制分析**：注意这里返回的是 `bool`（存在/不存在）而非 VPK 值本身。实际上，查询者需要从合约存储中读取 `VPKT[i].VPK` 的值（Solidity 的 public mapping 自动生成 getter）。论文中的伪代码有所简化。

#### Algorithm 3: VoteUser（恶意投票，仅雾节点可调用）

```
Input:  address user
Output: bool result

1: require(SC.status is True);
2: if msg.sender is not fog node then throw;
3: if user is null then return false;
4: else
5:     VoteCount += 1;
6:     return True;
```

**机制分析**：雾节点发现车辆行为异常时发起投票。`VoteCount` 是全局计数器。这里的一个设计细节是：同一雾节点对同一车辆能否重复投票？论文伪代码中未做去重检查——这是一个潜在的缺陷：恶意雾节点可单方面刷票触发撤销。

#### Algorithm 4: deletePK（公钥删除，TA 触发 + 阈值检查）

```
Input:  address target
Output: bool result

1: require(SC.status is True);
2: if msg.sender is not TA then throw;
3: if target is null then return false;
4: else if (VoteCount >= Thre) then
5:     delete VPKT[i].VPK;
6:     return True;
```

**机制分析**：删除操作需要两个条件同时满足：(1) 由 TA 发起；(2) `VoteCount` 达到阈值 `Thre`。这是一个双重门控机制——雾节点提供行为证据（投票），TA 充当最终执行者。这避免了雾节点的权力过大，但也意味着 TA 仍然是撤销流程的瓶颈。

### 创新点分析

1. **密钥管理的生命期自动化**：传统方案依赖 TA 维护 CRL，需要持续在线和周期性广播；本方案将增删改查全部编程到智能合约中，一旦部署即自动运行。

2. **链上查询不写入**：认证过程中，雾节点从链上**读取**公钥（这是只读操作，不产生 Gas 费用），只有密钥更新/撤销时才写入（产生 Gas 费用）。这种"读多写少"的模式贴合实际使用场景。

3. **投票阈值设计**：基于群体共识的撤销机制避免了单点误判。但阈值的选择是一个关键参数——太低则容易被恶意雾节点滥用，太高则恶意车辆可以被容忍太久。

## 4.4 车辆注册与登录的双因子保护

### 目的

防止车辆 OBU 被盗用——即使攻击者物理获取了 OBU，也无法通过登录阶段使用车辆的身份进行签名。

### 详细机制

#### 注册阶段

1. 用户选择密码 $PW_i$ 和身份 $UID_i$
2. 计算 $UPW_i = h_1(UID_i\|PW_i)$ 后发送 $\{ID_i, UPW_i\}$ 给 TA
3. TA 生成随机数 $k_i$，计算：
   - 私钥 $sk_i = h_2(ID_i\|s\|k_i)$
   - 假名 $PID_i = ID_i \oplus h_3(sk_i \cdot P_{pub} \| t_i)$
   - $VPK_i = sk_i \cdot P$
   - $A_i = k_i \cdot P$
   - $B_i = A_i \oplus h_4(ID_i)$
   - $C_i = h_3(A_i\|UPW_i)$
4. TA 下发 $\{B_i, C_i, sk_i, PID_i, (n,g)\}$ 给车辆

#### 登录阶段（每次使用前）

1. 用户输入 $ID_i, PW_i, UID_i$
2. 车辆计算：
   - $UPW_i = h_1(UID_i\|PW_i)$
   - $A_i = B_i \oplus h_4(ID_i)$
   - 验证 $C_i =^? h_3(A_i\|UPW_i)$
3. 若验证通过，登录成功；否则拒绝。

### 安全性分析

这个设计的巧妙之处在于：

- **外部存储不存明文密码**：TA 不存储 $PW_i$，只存 $UPW_i$（哈希值）。这意味着即使 TA 数据库泄露，攻击者也不能直接获取密码明文。
- **OBU 内不存 $A_i$ 明文**：存储 $B_i = A_i \oplus h_4(ID_i)$，需要 $ID_i$ 才能恢复 $A_i$。即使 OBU 被物理攻击获取 $B_i$ 和 $C_i$，攻击者仍需知道 $ID_i$ 和 $PW_i$ 两个因子。
- **离线验证**：密码验证完全在 OBU 本地完成，不需要与 TA 交互，避免了在线密码猜测攻击。
- **自由修改密码**：用户可随时更改密码，系统重新计算 $C_i^* = h_3(A_i\|h_1(UID_i\|PW_i^{new}))$。

**残留风险**：如果攻击者同时窃取了用户的 $ID_i$ 和 OBU 存储的 $\{B_i, C_i\}$，仍需暴力破解 $PW_i$。由于 $PW_i$ 通常是低熵的人类记忆密码，其安全性依赖于 $h_1$ 的计算成本——而论文仅使用普通哈希，没有使用 password-based key derivation function (如 PBKDF2 或 Argon2)，在离线暴力破解下可能不够稳健。

## 4.5 形式化安全证明（Random Oracle Model）

### 目的

证明签名方案在自适应选择消息攻击下具有存在性不可伪造性（EUF-CMA），并将其安全性归约到 ECDLP 困难问题。

### 证明结构（Game-Based Reduction）

#### 定理陈述

若 ECDLP 在群 $G$ 中是 $(\tau', \epsilon')$-困难的，则签名方案在 Random Oracle Model 下是 $(\tau, \epsilon)$-存在性不可伪造的，满足：

$$\epsilon' \geq \epsilon_1 \cdot \left(\frac{\epsilon_1}{q_{h2} + q_{h5}} + \frac{1}{q}\right)$$

$$\tau' \leq 2\tau + (4t_s + 2t_a)$$

其中 $\epsilon_1 = \epsilon - \frac{q_s(q_{h2}+q_{h5}+q_s)}{q}$，$t_s$ 和 $t_a$ 分别为标量乘法和点加法时间。

#### 模拟过程

Challenger $C$ 持有 ECDLP 实例 $(P, X = xP)$，目标是求解 $x$。

**Setup-query**：$C$ 生成 ECC 参数，将公钥 $P_{pub} = s \cdot P$ 发送给敌手 $A$（注意 $C$ 自己选择了 $s$，因为 $C$ 需要知道私钥以回答签名查询——这与标准 Schnorr 证明中 $C$ 将 $P_{pub}$ 设为 ECDLP 挑战实例 $X$ 的做法不同。论文的证明策略是"通过 Forking Lemma 从两个有效伪造签名中提取 $sk_i$"）。

**$h_2$-query / $h_5$-query**：$C$ 维护两个哈希列表，对未见过的查询返回随机值，对已查询过的返回一致值。

**Sign-query**：这是关键步骤。$C$ 随机选择 $\sigma_{Vi}, d_i$，通过重新排列验证方程计算 $D_i = [\sigma_{Vi} \cdot P - h_2 \cdot P] \cdot \beta_i^{-1}$（即"先选择签名，再反算承诺值"）。如果对应的哈希项已被查询过，$C$ 中止（`bad ← true`）。

**Forgery**：$A$ 输出一个有效伪造 $(\sigma_{Vi}, D_i)$ 在消息 $(PID_i, D_i, \phi_i, T_{i1})$ 上，且该消息未被 Sign-query 查询过。

#### Forking Lemma 应用

$C$ 运行 $A$ 两次（相同随机带，不同的 $h_5$ 响应），获得两个有效伪造：

$$\sigma_{Vi} = sk_i + d_i \cdot h_5 \mod q$$

$$\sigma'_{Vi} = sk_i + d_i \cdot h'_5 \mod q$$

两式相减消去 $sk_i$：

$$sk_i = \frac{h'_5 \cdot \sigma_{Vi} - h_5 \cdot \sigma'_{Vi}}{h'_5 - h_5} \mod q$$

成功求得 $sk_i$，进而解决 ECDLP（因为 $sk_i$ 是由 $s$ 派生的，但注意这个"解决 ECDLP"实际上指的是从签名伪造中提取了用户私钥，而非直接求解系统主私钥 $s$——这是证明的一个微妙之处）。

### 证明的评估

**优点**：
- 证明框架严谨，采用标准的 Bellare-Neven Forking Lemma
- 安全界明确，常数因子清楚

**待商榷之处**：
- 证明将签名伪造归约到 ECDLP 的"提取用户私钥"而非提取系统主私钥 $s$。提取 $sk_i$ 当然破坏了单用户安全性；但要破坏整个系统的安全性（如追溯能力），需要提取 $s$。这一点论文的证明框架并未直接覆盖。
- 证明中的 $C$ 自己选择 $s$（而非设 $P_{pub}$ 为挑战 $X$），这意味着 $C$ 可以回答所有与 $s$ 相关的查询。归约实际上依赖于 Forking Lemma 从伪造中提取 $sk_i$，而非直接求解 $s$。这个设计的正确性在技术上没有问题，但安全归约的意义被弱化为"攻击者无法伪造签名"而非"攻击者无法获得系统主私钥"。
