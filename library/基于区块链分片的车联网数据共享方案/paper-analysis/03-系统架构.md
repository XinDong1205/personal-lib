## 3.2 参与实体与角色

| 实体 | 物理对应 | 区块链角色 | 核心职责 |
|------|---------|-----------|---------|
| **Trusted Authority (TA)** | 政府/权威机构服务器 | **Master Node** | (1) 验证并授权车辆和 RSU 身份；(2) 发放数字证书；(3) 执行分片算法和代理选择算法；(4) 发布数据收集任务；(5) 监管全局节点行为 |
| **Roadside Units (RSU)** | 路侧基础设施 | **Global Node** | (1) 与 TA 有线通信；(2) 验证分片区块链数据；(3) 同步并存储所有分片的区块链数据；(4) 参与全局共识（global consensus） |
| **Vehicles** | 普通车辆 | **Proxy Node** 或 **Validator Node** | (1) 收集、训练、签署数据模型；(2) 代理节点生成微块并驱动 BLS-PBFT 共识；(3) 验证节点验证数据合规性并签名；(4) 监控代理节点行为并上报异常 |

**关键设计思想**：TA 和 RSU 之间为有线通信链路，保证了骨干网络的低延迟和高可靠性。车辆与 RSU 之间、车辆之间为 V2X 无线通信。这种分层通信架构将安全敏感的管控功能放在有线骨干网上，将数据产生和初始验证放在车辆层。

## 3.3 模块划分与分工

系统可划分为四大功能模块：

### 模块 A：身份管理与注册模块
- **功能**：公钥基础设施（PKI），生成密钥对、签发数字证书、节点身份注册
- **执行者**：TA
- **输出**：每个节点获得唯一 $ID_{v_i} = hash(pk_{v_i})$ 和数字证书 $C_{v_i}$

### 模块 B：分片管理模块
- **功能**：CS 分数计算、代理节点选择、分片形成、分片健康监控
- **核心算法**：Beta 分布信誉评估、DRL 分片决策、FS 分片加入评估
- **执行者**：TA（决策层）+ 代理节点（执行层）

### 模块 C：共识模块 (BLS-PBFT)
- **功能**：分片内数据模型验证、签名聚合、区块生成、异常上报
- **核心流程**：7 步 BLS-PBFT 协议（详见第 4 章）
- **执行者**：代理节点 + 验证节点 + RSU

### 模块 D：全局同步模块
- **功能**：跨分片全局共识、分片区块链同步、最终确认
- **执行者**：所有 RSU (Global Nodes)

### 各步骤详解

| 步骤 | 操作 | 输入 | 输出 |
|------|------|------|------|
| (1) | TA 根据 ITS 需求发布数据采集任务 | ITS 需求 | 任务描述 |
| (2) | 车辆收集数据并本地训练模型 | 传感器数据 | 预训练数据模型 |
| (3) | 车辆用私钥签名数据模型，发送给代理节点 | 数据模型 + $sk_{v_i}$ | 签名后的数据集 |
| (4) | 代理节点收集模型，打包生成微块（DataSet） | 多个签名数据模型 | DataSet |
| (5) | 执行 BLS-PBFT 分片内共识 | DataSet | DataDecMap |
| (6) | 代理节点将验证结果提交给 RSU | DataDecMap | — |
| (7) | RSU 检查 DataDecSet 数量是否达标（$\kappa$），达标则追加到分片区块链 | DataDecMap | 新区块 |
| (8) | RSU 之间执行全局共识，同步分片链 | 分片区块 | 全局确认 |

## 3.5 安全/威胁模型

### 攻击者能力假设

1. **恶意车辆节点**：可能伪造身份（Sybil 攻击）、提供虚假数据、与其它恶意节点合谋（collusion attack）、尝试隔离诚实节点（eclipse attack）
2. **网络层面的攻击**：恶意节点可监听无线通信、重放消息、篡改中转数据（虽文中未显式建模，但安全设计暗含此假设）
3. **对 PBFT 共识的攻击**：恶意节点可能作为代理节点故意延迟或拒绝打包、伪造签名、在回复阶段提供虚假验证结果

### 信任边界

```
  信任域 ────────────────────────────────────────────
  │                                                    │
  │   TA (完全可信)                                     │
  │    │                                               │
  │    ▼                                               │
  │   RSU (可信，有线通信 protected)                     │
  │    │                                               │
  │    │◄════ 信任边界 ════════►                        │
  │    │                                               │
  │    ▼                                               │
  │   Vehicles (不可信，可能恶意)                        │
  │                                                    │
  └────────────────────────────────────────────────────
```

### 安全目标

| 目标 | 实现机制 |
|------|---------|
| **身份认证** | PKI + 数字证书，所有节点需通过 TA 注册 |
| **数据完整性** | 签名 + 区块链不可篡改性 |
| **抗 Sybil 攻击** | 基于 CS 的节点准入 + BLS 签名（短期、易验证） |
| **抗合谋攻击** | 共识阈值 $\kappa$ 随 CS 方差动态调整；低方差（可能合谋）→ 提高 $\kappa$ |
| **抗 Eclipse 攻击** | 位置中心性 LC 纳入节点选择，地理位置分散 |
| **代理节点问责** | 验证节点监控代理节点行为，异常上报 TA |
