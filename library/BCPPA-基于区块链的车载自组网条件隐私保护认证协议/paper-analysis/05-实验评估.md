# 5. 实验与评估

## 5.1 实验设计

论文的实验分为三个层次，验证了协议的不同方面：

| 层次 | 实验内容 | 验证目标 |
|------|---------|---------|
| **Layer 1：区块链实现** | 在 Rinkeby 测试网上部署智能合约，测试部署/`update`/`get`/`deletetx` 的 gas 消耗和美元成本 | 验证方案的经济可行性 |
| **Layer 2：密码学微基准** | 测量 KD（Key Derivation）、ECDSA Sign、ECDSA Verify 的 CPU 时间 | 验证密码学操作的计算成本 |
| **Layer 3：网络仿真** | 使用 VanetMobiSim + NS-2 模拟多车辆场景下的消息延迟和丢包率 | 验证协议在真实交通场景中的网络性能 |

## 5.3 数据集/测试场景

论文的测试场景较为简单（$1 \times 1 \text{ km}^2$ 的正方形区域，4 个 RSU），这比真实城市环境简化了很多：

- **地图规模过小**：$1 \text{ km}^2$ 的区域对于 VANET 研究来说是一个相对小的场景。典型的 VANET 研究常使用城市级别的拓扑（如通过 SUMO 导入真实城市地图）。
- **车辆数量上限低**：最大仅 100 辆车，相当于每平方公里 100 辆。在真实城市高峰时段，密度可以远超此值。
- **仿真时间短**：每次仅 100 秒，对于分析长时间运行的稳定性不足。

不过，考虑到论文的重点是**协议层的认证机制**而非交通流分析，这些简化在一定程度上是可以接受的。

## 5.4 对比方案

### 5.4.1 Gas 成本对比

论文在 Table I 中对智能合约各操作进行了成本测试（无对比方案，仅自评）：

| 操作 | Gas 消耗 | 美元成本（1 Ether = 188 USD） |
|------|---------|------------------------------|
| `deploy`（合约部署） | 408,494 | $0.1536 |
| `update`（更新映射） | 72,610 | $0.0273 |
| `get`（查询映射） | 24,777 | $0.0093 |
| `deletetx`（删除映射） | 34,175 | $0.0129 |

**分析**：
- 部署合约是最昂贵的操作（约 $0.15），但仅需执行一次。
- `get`（view 函数）虽然显示有 gas 对应值，但在实际使用中，`eth_call`（本地执行）**不消耗实际 gas**，不产生交易费用。论文的标注可能指"如果此操作以交易形式执行"的等效气体量。实际上，车辆调用 `get` 应该是零成本的（不发起链上交易）。
- 每次认证中车辆仅需零成本的 `get` 调用——这使得方案的日常运营成本极小。仅 CA 在预签发证书时需要支付 `update` 的 gas 费。

### 5.4.2 密码学时间成本对比

Table II 给出了各密码学原语的微基准测试结果（单位：秒）：

| 算法 | 平均执行时间 |
|------|------------|
| KD（密钥派生） | ~0.0015s（约 1.5ms） |
| ECDSA Sign | ~0.0012s（约 1.2ms） |
| ECDSA Verify | ~0.0025s（约 2.5ms） |

**分析**：
- 单个密码学操作的时间均在毫秒级，这对 VANET 的实时性要求是可接受的。
- Sign 和 Verify 的时间之和约为 3.7ms（单次签名+验证），加上 KD 的 1.5ms，合计约 5.2ms。
- **但这是单条消息的成本**。在 VANET 中（每 100ms 可能收到数十条消息），如果不使用批量验证，验证延迟将线性增长。这也是论文强调"可用批量验证签名替换 ECDSA"的动机所在。

**实验的不足**：论文没有实际测试批量验证方案的性能——仅声称"可以替换"，但没有演示替换后的实际性能提升。这使得批量验证的优势停留在理论层面。

### 5.4.3 与传统 PKI 方案的对比

Table III 将 BCPPA 与传统 ECDSA-based VANET 认证方案 [41][42] 进行对比：

| 指标 | 传统 ECDSA [41][42] | BCPPA |
|------|---------------------|-------|
| 签名操作 | $1 \times \text{Sign}$ | $1 \times \text{Sign}$ |
| 验证操作 | $2 \times \text{Verify}$ | $2 \times \text{Verify} + \text{eth\_calls} + \text{tx\_retrieval}$ |
| 通信开销 | $168$ bytes | $264$ bytes |
| 匿名性 | ✗ | ✓ |
| 可追踪性 | ✗ | ✓ |

**分析**：
- BCPPA 的通信开销增加 96 bytes（约 57%），换取的是匿名性和可追踪性。
- `eth_calls` 和 `tx_retrieval` 的时间成本被论文认为"如果不考虑传输延迟，可以忽略"——但这依赖于 RSU 的响应速度和网络延迟。在 RSU 信号不好的区域（如隧道或偏远地区），这一假设可能不成立。
- 论文没有与任何 ID-based 方案或现有 BCPPA 方案进行定量的性能对比，这是一个明显的遗漏。

## 5.5 实验结果分析

### 5.5.1 区块链实现验证（Figures 5-9）

论文在 Rinkeby 上执行了完整的认证流程，展示了：

1. **证书签发**（Figure 5）：CA 将证书嵌入交易，Rinkeby 返回交易哈希。
2. **智能合约部署**（Figure 6）：通过 Remix 部署合约，获得合约地址 `0x0fb5739f30d47a3c7edce10f2631288b42cb6ead`。
3. **update 执行**（Figure 7）：CA 调用 `update` 将公钥与交易 ID 映射写入合约。
4. **get 查询**（Figure 8）：Vehicle1 调用 `get` 获取交易 ID（十进制），需转换为十六进制再用于检索交易数据。
5. **交易数据检索**（Figure 9）：Vehicle2 根据交易 ID 从 Rinkeby 获取证书数据。

这些截图证明协议在真实区块链上可以工作，属于**概念验证**（Proof of Concept）。

### 5.5.2 网络仿真结果

**实验结果一：车辆密度对延迟和丢包率的影响（Figure 11）**

| 密度范围 | 平均数据包延迟 (APD) | 丢包率 (PLR) |
|----------|---------------------|-------------|
| < 70 辆车 | 约 40 ms（几乎恒定） | 接近 0%，缓慢上升 |
| > 70 辆车 | 急剧增长 | 继续上升但增速趋缓 |

**分析**：
- 当车辆密度较低时（≤70），APD 保持约 40ms。这个延迟对于 VANET 是**可接受**的（100-300ms 的消息广播周期意味着 40ms 的认证延迟不会成为瓶颈）。
- 密度超过 70 后 APD 急剧增长，说明网络容量开始饱和。这是 802.11 MAC 层（CSMA/CA）在高竞争环境下的典型行为，与 BCPPA 协议本身的安全机制无关。
- PLR 的增速在密度 >70 后放缓，可能的原因是碰撞概率已经足够高，使得额外的车辆加入不会再显著改变丢包行为。

**实验结果二：车辆速度对延迟和丢包率的影响（Figure 12）**

| 速度变化 | 观察结果 |
|----------|---------|
| PLR | 几乎恒定（速度变化对 PLR 基本无影响） |
| APD | 波动，但不超 60ms |

**分析**：
- PLR 对速度不敏感是合理的——丢包主要由通信范围内的冲突引起，与车辆绝对速度关系不大（在相同密度下，相对速度变化确实只影响瞬时拓扑，不改变冲突概率的期望值）。
- APD 的波动（但不超过 60ms）可能是由于不同速度导致车辆间距离的不可预测变化，从而影响多跳路由的稳定性。论文将此归因于"不同平均速度导致车辆间距离的不可预测变化"。

## 5.6 实验评价：充分性分析

### 实验验证了什么

| ✅ 已验证 | ❌ 未充分验证 |
|-----------|-------------|
| 协议在真实区块链上的可行性 | 批量验证方案的实际性能（仅声称可替换） |
| 密码学原语的微基准性能 | 与 ID-based 方案的定量对比 |
| 网络层延迟和丢包率的基本特征 | 与现有 BCPPA 方案的定量对比 |
| Gas 成本的经济可接受性 | 大规模的长期仿真（如 10,000+ 辆车） |
| 证书管理效率在理论上的改善 | 真实场景下的区块链数据检索延迟（实验在本地 RSU 节点执行 `eth_call`，未考虑网络延迟） |
| — | 智能合约的安全性审计或形式化验证 |
| — | 密钥派生在实际 OBU 硬件上的性能（实验在 PC 上进行） |

### 关键缺失

1. **缺乏与竞争方案的定量对比**：Table III 仅对比了传统 ECDSA 方案，但没有与 Lu et al. [13] 或 Zheng et al. [14] 等 BCPPA 方案进行性能对比。这一遗漏使得"我们的方案更好"的声称缺乏直接证据。

2. **批量验证未实测**：论文反复强调 ECDSA 可替换为批量验证方案，但从未测试替换后的实际性能。如果批量验证是方案的核心性能优势，就应该实际测试。

3. **安全实验缺失**：所有的"安全分析"（Section VI）都是理论论证，没有实施任何攻击实验来验证方案的抵抗能力（如尝试侧信道攻击、尝试链接攻击等）。

4. **真实 OBU 硬件缺失**：密码学微基准测试在 PC（i7-6700, 3.4GHz）上进行。真实的车辆 OBU 通常使用嵌入式处理器（如 ARM Cortex 系列），性能可能相差 10-100 倍。以 PC 性能声称"毫秒级"是常见的学术研究局限性，但在实际部署中可能不成立。
