## 3.2 参与实体与角色

系统包含四个核心实体，每个实体的角色和信任假设如下：

### 实体一：证书权威（Certificate Authority, CA）

| 属性 | 描述 |
|------|------|
| **信任假设** | **完全可信**（Fully Trusted） |
| **核心职责** | ① 管理车辆和 RSU 的公钥证书；② 用其私钥 $sk_{CA}$ 签发证书 $S_{ij} = Sign(sk_{CA}, pk_{ij})$；③ 将证书嵌入 Ethereum 交易并发布到区块链；④ 部署和调用智能合约（`update`、`deletetx`）；⑤ 执行公钥派生（public type derivation）以预签发未来证书；⑥ 条件隐私追踪——是唯一可以从截获消息中恢复车辆真实身份的实体 |
| **资源假设** | 拥有足够的计算和存储资源 |

**设计要点**：CA 持有车辆的根公钥 $pk_{root}$ 和链码 $chain_{root}$，因此可以利用 BIP32 的公钥派生能力**预计算**车辆未来将使用的所有公钥，并提前将它们对应的证书签发上链。这是协议能够消除频繁交互的关键——CA 可以一次性为车辆预签发多天的证书（如 240 个/每两天）。

### 实体二：路侧单元（Roadside Unit, RSU）

| 属性 | 描述 |
|------|------|
| **信任假设** | **完全可信**（Fully Trusted），不会提供伪 API |
| **核心职责** | ① 作为 Ethereum 区块链的**全节点**（Full Node），存储所有交易数据；② 使用 DSRC 协议与车辆 OBU 通信；③ 为附近车辆提供区块链数据检索 API（即提供对交易的访问和智能合约的调用）；④ 作为 V2R 通信的服务端 |
| **额外说明** | RSU 同时也是区块链网络的矿工/验证者节点，参与区块链共识 |

**设计要点**：RSU 是"桥梁"角色——它既是传统 VANET 的路侧通信设施，又是区块链网络的全节点。这种设计使得车辆无需自己成为区块链节点（对 OBU 来说不现实，因为存储和带宽要求太高），而是通过 V2R 通信间接访问区块链数据。基于信任假设，RSU 不会提供伪造的区块数据。

### 实体三：车辆（Vehicle）

| 属性 | 描述 |
|------|------|
| **信任假设** | **不可信**（Untrusted）——可能是恶意攻击者 |
| **核心职责** | ① 通过 OBU 执行私钥派生（private type derivation），生成一次性私钥 $sk_{ij}$；② 通过 RSU 触发智能合约的 `get` 函数获取证书对应的交易 ID；③ 对交通消息 $M$ 签名并广播 $(S, M, T, TxID_{ij})$；④ 接收并验证其他车辆的消息 |
| **OBU 属性** | 现实的防篡改设备（realistic tamper-proof device），存储的秘密（根种子 $sk_{root}$ 和 $chain_{root}$）可周期性更新 |
| **资源约束** | 存储和计算资源有限（这也是设计需要尽可能减少 OBU 存储和计算开销的原因） |

### 实体四：区块链网络（Blockchain Network, BN）

| 属性 | 描述 |
|------|------|
| **类型** | 公有区块链（Public Blockchain）——具体采用 Ethereum |
| **信任假设** | 分布式信任——不需要信任单个节点，信任来自于共识机制和经济激励 |
| **核心功能** | ① 不可篡改地存储交易数据（证书嵌入其中）；② 通过智能合约维护 `(公钥 → 交易ID)` 的映射关系；③ 通过共识机制（PoW/PoS）保证数据一致性和防分叉；④ 提供交易和合约调用的全局可验证性 |

## 3.3 模块划分与分工

系统可以划分为四个功能模块：

### 模块一：密钥管理模块（Key Management Module）

```
┌───────────────────────────────────────────┐
│           密钥管理模块 (BIP32)              │
├───────────────────────────────────────────┤
│  Vehicle 端（私钥派生）：                    │
│    seed → sk_root, chain_root             │
│    (sk_root, chain_root) → sk_i, chain_i  │
│                                           │
│  CA 端（公钥派生）：                         │
│    (pk_root, chain_root) → pk_i, chain_i  │
│                                           │
│  一致性保证：pk_i = sk_i · G               │
└───────────────────────────────────────────┘
```

- 负责密钥的派生与管理
- 车辆和 CA 独立派生，无需交互
- 输出一次性公私钥对用于签名和验证

### 模块二：证书管理模块（Certificate Management Module）

```
┌───────────────────────────────────────────┐
│         证书管理模块 (Smart Contract)        │
├───────────────────────────────────────────┤
│  CA 操作：                                 │
│    1. 派生 pk_ij                           │
│    2. S_ij = Sign(sk_CA, pk_ij)           │
│    3. 嵌入交易 → 上链 → 获得 TxID_ij        │
│    4. update(pk_ij, TxID_ij)              │
│                                           │
│  Vehicle 操作：                             │
│    get() → TxID_ij                        │
│                                           │
│  吊销操作：                                 │
│    deletetx(pk_ij) → 删除映射               │
└───────────────────────────────────────────┘
```

- CA 负责证书的生成、上链和智能合约更新
- 车辆通过 `get` 函数检索（无需 gas 费的 view 类型函数）
- 吊销通过 `deletetx` 删除映射即时生效

### 模块三：消息认证模块（Message Authentication Module）

- 签名算法：$S = Sign(sk_{ij}, M, T, TxID_{ij})$
- 验证算法：两阶段验证
  - 阶段一：$\text{Verify}(pk_{CA}, pk_{ij}, S_{ij}) \stackrel{?}{=} 1$（验证 CA 对车辆公钥的证书）
  - 阶段二：$\text{Verify}(pk_{ij}, M, T, TxID_{ij}, S) \stackrel{?}{=} 1$（验证车辆对消息的签名）
- 支持将 ECDSA 替换为批量验证方案

### 模块四：区块链交互模块（Blockchain Interaction Module）

- CA 通过 C2B 通信发布交易
- 车辆通过 V2R 通信间接访问区块链（通过 RSU 的 API）
- 涉及操作：部署合约、触发 `update`/`get`/`deletetx`、检索交易数据

## 3.4 整体交互流程（三阶段协议）

### 阶段一：系统初始化（System Initialization Phase）

```
Vehicle (Vi)                            CA                          Blockchain/RSU
    │                                    │                              │
    │  1. 选择随机种子(seed)              │                              │
    │  2. 生成 sk_root, chain_root        │                              │
    │  3. 计算 pk_root = sk_root·G        │                              │
    │                                    │                              │
    │── 4. 传输 (pk_root, chain_root) ──►│                              │
    │                                    │                              │
    │                                    │  5. 部署智能合约              │
    │                                    │─────────────────────────────►│
    │                                    │  6. 获得 SC_ID               │
    │◄──────── 7. 回复 SC_ID ───────────│                              │
    │                                    │                              │
    │                                    │  8. 对每个索引 j:             │
    │                                    │     a) 公钥派生 → pk_ij      │
    │                                    │     b) S_ij = Sign(sk_CA,   │
    │                                    │        pk_ij)               │
    │                                    │     c) 交易上链 → TxID_ij   │
    │                                    │     d) update(pk_ij,TxID_ij)│
    │                                    │─────────────────────────────►│
    │                                    │                              │
    │  (OBU预存储: sk_root, chain_root,  │  (CA存储: pk_root, chain_root│
    │   SC_ID, 索引j)                    │   和派生历史记录)              │
```

### 阶段二：消息签名（Message Signing Phase）

```
Vehicle Vi (发送方)                     RSU/Blockchain
    │                                       │
    │  8. 私钥派生: (sk_root, chain_root)    │
    │     → sk_ij                            │
    │  9. 计算 pk_ij = sk_ij·G              │
    │                                       │
    │  10. get() 调用 ──────────────────────►│
    │      (查询 pk_ij 对应的 TxID_ij)       │
    │◄─────────── 返回 TxID_ij ────────────│
    │                                       │
    │  11. S = Sign(sk_ij, M, T, TxID_ij)   │
    │                                       │
    │  12. 广播 (S, M, T, TxID_ij)          │
    │──────────────────────────────────────────► 其他车辆
```

### 阶段三：消息验证（Message Verification Phase）

```
Vehicle Vj (接收方)                     RSU/Blockchain
    │                                       │
    │  收到 (S, M, T, TxID_ij)              │
    │                                       │
    │  13. 根据 TxID_ij 检索交易数据 ────────►│
    │◄─────────── 返回 S_ij (证书) ─────────│
    │                                       │
    │  14. 验证证书:                         │
    │     Verify(pk_CA, pk_ij, S_ij) ?= 1   │
    │                                       │
    │  15. 验证消息:                         │
    │     Verify(pk_ij, M, T, TxID_ij, S)   │
    │     ?= 1                              │
    │                                       │
    │  若均通过 → 接受消息 M                  │
    │  否则     → 丢弃消息                    │
```

## 3.5 安全/威胁模型

### 3.5.1 攻击者能力假设

论文采用隐式的概率多项式时间（Probabilistic Polynomial Time, PPT）敌手模型：

- **网络控制**：攻击者可以完全控制无线信道——拦截、修改、重放、删除所有 V2V 通信消息。
- **密码学能力**：攻击者不能以不可忽略的概率破解底层密码学原语（ECDSA 的不可伪造性，离散对数假设的困难性）。
- **节点攻陷**：攻击者可以控制部分恶意车辆（拥有合法的 OBU 和派生密钥）。
- **CA 安全性**：CA 自身不可被攻陷（若 CA 被攻陷，条件隐私的"条件"将失效，这是方案的信任基础）。
- **RSU 安全性**：RSU 完全可信，不会提供伪 API（这是较强的假设，论文在 3.1 节明确声明）。
- **OBU 物理安全**：OBU 是防篡改的（tamper-proof），但仅需"现实"级别的防篡改——即存储的秘密可以周期性更新，使得侧信道攻击的难度增加。
- **区块链安全**：诚实的区块链节点占多数（抵抗 51% 攻击），共识机制正常工作。

### 3.5.2 信任边界

```
  可信域                    半可信域                  不可信域
┌─────────────┐    ┌─────────────────────┐    ┌─────────────────┐
│    CA       │    │  Blockchain Network │    │   Vehicles      │
│  (完全可信)   │    │  (分布式信任)         │    │  (不可信)        │
│             │    │                     │    │                 │
│    RSU      │    │  · 不可篡改存储       │    │  · 可能是攻击者   │
│  (完全可信)   │    │  · 共识保证一致性     │    │  · 可能发送虚假   │
│             │    │  · 经济激励防作恶     │    │    消息         │
└─────────────┘    └─────────────────────┘    └─────────────────┘
         │                    │                       │
         └────────────────────┼───────────────────────┘
                              │
                    信任边界：V2V 通信
                   （不安全的无线信道）
```

### 3.5.3 安全目标

论文在 Section III-B 定义了七项安全需求：

1. **消息认证（Message Authentication）**：任何对消息的篡改均可被检测。
2. **条件隐私保护（Conditional Privacy Preservation）**：仅 CA 可追踪车辆真实身份。
3. **不可链接性（Unlinkability）**：同一车辆的两条消息不可被关联。
4. **生日碰撞抵抗（Birthday Collision Resilience）**：最小化同时生成两个相同区块的概率（防分叉）。
5. **劫持抵抗（Hijacking Resilience）**：攻击者不能劫持交易（transaction）。
6. **51% 攻击抵抗（51% Attack Resilience）**：防止攻击者通过控制多数算力重写历史。
7. **其他攻击抵抗**：包括假冒攻击、篡改攻击、DDoS、重放攻击、中间人攻击、验证表窃取攻击、侧信道攻击。

**批评性分析**：安全需求 4-6（生日碰撞、劫持、51% 攻击）并非 BCPPA 协议本身的安全性保证，而是继承自底层 Ethereum 区块链的安全性。将它们列为协议的安全需求有"搭便车"之嫌。协议本身在密码学层面的核心安全需求应当聚焦于需求 1-3 和需求 7 中的密码学相关攻击。
