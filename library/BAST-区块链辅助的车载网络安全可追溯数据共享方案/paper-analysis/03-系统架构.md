## 3.2 参与实体与角色

| 实体 | 信任假设 | 核心职责 |
|------|---------|---------|
| **TA（信任权威）** | 完全可信，不可攻破 | 生成系统参数；为 ES/RSU/车辆生成加密材料（公私钥对、证书）；部署智能合约；离线注册服务 |
| **ES（边缘服务器）** | 可能恶意或被攻破（数量受限） | 缓存 ASP 服务内容；协同签名广播消息；响应车辆查询 |
| **RSU（路侧单元）** | 诚实但好奇（Honest-but-Curious） | 控制辖区内多个 ES；聚合 ES 签名份额生成聚合签名 σ；转发聚合签名和消息给车辆 |
| **Vehicle（车辆）** | OBU 敏感材料不可攻破 | 验证聚合签名和消息的合法性；消费服务数据；验证失败时向区块链发起恶意签名追溯请求 |
| **Blockchain（区块链）** | 全节点（BS）完全可信 | 存储追踪密钥 $sk_t$；执行 Schnorr 验证和 ElGamal 解密以追溯恶意签名者；记录恶意签名者集合 |

### 关键角色说明

- **RSU 的"诚实但好奇"假设**：RSU 会正确执行聚合签名协议，但可能试图从签名信息中推断额外的隐私信息。论文通过 Σ-协议保证 RSU 无法获取签名私钥的任何知识。
- **ES 的"有限恶意"假设**：攻击者只能攻陷有限数量的 ES（数量 < 门限 t），这是门限签名方案安全性的基本前提。
- **区块链全节点（BS）**：论文建议由基站（BS）作为完全可信的全节点加入区块链网络，为附近的 RSU 和车辆提供区块链服务。BS 不提供伪 API，确保查询结果可信。

## 3.3 模块划分与分工

### 模块 1：系统初始化模块（System Initialization）
- **负责方**：TA
- **功能**：执行 KeyGen 算法，生成所有实体的公私钥对、ElGamal 加密参数、聚合密钥 $sk_{ag}$ 和追踪密钥 $sk_t$
- **输出**：
  - $pk = \{pk^*, pkt, pk_{rs}, vk_{TA}, T_0, T_1\}$（公开参数）
  - 每个 ES 的签名私钥 $sk_i$
  - RSU 的组合密钥 $sk_{ag} = \{pk, sk_{rs}, t, \omega\}$
  - 区块链的追踪密钥 $sk_t = \{pk, sk_e, t\}$
  - 车辆的 $\{vid_i, k_{vid_i}, Cert_{vid_i}\}$

### 模块 2：ES 签名生成模块（ES Signature Generation）
- **负责方**：各参与 ES
- **功能**：多个 ES 独立对头 ES 广播的消息 m 生成签名份额 $\sigma_i = (R_i, z_i)$
- **核心操作**：Schnorr 型签名份额：$R_i = g^{r_i}$, $z_i = r_i + sk_i \cdot c$, 其中 $c = H(pk, R, m)$

### 模块 3：RSU 聚合签名模块（RSU Aggregate Signature）
- **负责方**：RSU
- **功能**：聚合 t 个 ES 的签名份额，生成完整聚合签名 σ，并生成 Σ-协议知识证明 π
- **核心操作**：
  - 聚合：$R = \prod_{i \in C} R_i$, $z = \sum_{i \in C} z_i$
  - ElGamal 加密 z：$ct_1 = g^\rho$, $ct_2 = g^z pk_t^\rho$
  - 生成 Σ-协议证明 π 以证明 R 和加密 z 的有效性
  - RSU 用自己的私钥 $sk_{rs}$ 对 $(m, R, ct_1, ct_2, \pi)$ 签名生成 $tg$

### 模块 4：车辆验证模块（Vehicle Verification）
- **负责方**：车辆
- **功能**：验证聚合签名的完整性和消息的合法性
- **核心验证**：
  - 时间戳新鲜性检查：$TS_c \leq TS_{exp}$
  - Schnorr 验证：$\text{Verify}(pk_{rs}, (m, R, ct, \pi), tg) = 1$
  - Σ-协议验证方程（约 10 个等式检查）

### 模块 5：区块链追溯模块（Blockchain Trace）
- **负责方**：区块链（智能合约 + 全节点）
- **功能**：验证车辆身份合法性；解密追踪密钥；识别恶意签名者集合 C
- **核心操作**：
  - 验证车辆身份：$\text{Verify}_{vk_{TA}}(Cert_{vid_i}, vid_i) = \text{true}$
  - ElGamal 解密：$g^{z^*} = ct_2 / ct_1^{sk_e}$
  - 枚举验证：找到 $C \subseteq [n]$, $|C| = t$, 满足 $g^{z^*} = R \cdot (pk_C)^c$

## 3.5 安全模型与威胁假设

### 3.5.1 攻击者能力假设

| 攻击能力 | 假设 | 说明 |
|---------|------|------|
| 攻陷 ES | 可攻陷有限数量（< t）的 ES | 门限 t 由系统参数决定 |
| 攻陷 RSU | RSU 诚实但好奇，不可被完全攻陷 | RSU 正确执行协议但可能试图推断私钥信息 |
| 窃听信道 | 可以 | V2I 通信使用开放无线信道 |
| 注入/修改/重放消息 | 可以 | 标准主动攻击者模型 |
| 攻陷 TA | 不可以 | TA 完全可信 |
| 攻陷车辆 OBU | 不可以 | OBU 敏感材料不可攻破 |
| 51% 攻击 | 区块链记录节点可信且抗攻击 | 通过选择可信全节点（BS）来防御 |
| 合谋攻击 | ES 可与 RSU 合谋；多个 ES 可合谋 | 但合谋方总数必须 < t |

### 3.5.2 安全目标（详列）

论文基于对现有方案的调研 [3][6][10][25][26][32][35][37]，提出了 BAST 协议的 7 项安全需求：

1. **消息认证（Message Authentication）**：任何被篡改或非法的消息无法通过认证
2. **恶意 ES 可追溯性（Malicious ES Traceability）**：区块链能够识别出参与恶意签名的 ES 集合
3. **抗 51% 攻击**：假设区块链的记录节点可信，攻击者无法控制多数算力
4. **抗合谋攻击（Resistance to Collusion Attacks）**：ES 与 RSU 合谋无法生成有效欺诈签名；多个 ES 合谋无法在低于门限时生成有效签名
5. **抗篡改攻击（Resistance to Modification Attacks）**：接收方必须拒绝与签名不一致的消息
6. **抗车辆冒充攻击（Resistance to Impersonation Attacks of Vehicle）**：攻击者无法使用合法车辆身份向区块链发起追溯请求
7. **抗重放攻击（Resistance to Replay Attacks）**：过期的签名消息无法被重放使用

### 3.5.3 密码学假设

- **离散对数假设（DL Assumption）**：给定 $g, g^\beta \in \mathbb{G}$，计算 $\beta \in \mathbb{Z}_p^*$ 的概率可忽略
- **判定性 Diffie-Hellman 假设（DDH Assumption）**：区分 $(g^\alpha, g^\beta, g^{\alpha\beta})$ 和 $(g^\alpha, g^\beta, g^r)$ 的概率优势可忽略
