# 6. 优缺点与适用边界

## 6.1 核心优势

### 优势 1：巧妙地消除了对 ES 的理想化信任假设
BAST 最大的贡献在于其安全模型——不再假设 ES 完全可信。通过 (t, n) 门限签名，将信任从"单个 ES"分散到"至少 t 个 ES 的集体"。这是一个**更贴近实际部署场景的安全模型**。ES 部署在路边，物理安全难以保障，单个 ES 被攻陷的概率不低，但同时攻陷 t 个 ES 的难度呈指数级增长。

### 优势 2：门限签名与可追溯性的一体化设计
BAST 不是简单地将门限签名和区块链可追溯性拼接在一起，而是通过 ElGamal 加密的嵌入实现了两者的一体化。具体来说：
- 聚合签名中的 z 值同时服务于两个目的：Schnorr 验证（证明签名有效）和 ElGamal 解密追溯（识别签名者）
- Σ-协议同时证明签名的正确性和加密的正确性

这种设计避免了"两个独立方案叠加"带来的双倍开销，实现了紧凑性。

### 优势 3：避免双线性对操作
BAST 的密码学构造完全基于离散对数假设（Schnorr 签名 + ElGamal 加密），没有使用双线性对（Bilinear Pairing）。这与 [3] 等方案形成鲜明对比。双线性对在 Raspberry Pi 上的计算时间高达 144 ms 级别，而 BAST 使用的指数运算（$T_{ebp}$）为 78 ms，标量乘运算（$T_{ecm}$）为 15 ms。这个设计选择直接带来了签名生成阶段 85-94% 的计算开销降低。

### 优势 4：Σ-协议与 Fiat-Shamir 变换的非交互式设计
BAST 将交互式 Σ-协议（需要 3 轮交互）转换为非交互式证明（单次消息），使得车辆只需要接收一个聚合签名消息即可完成所有验证。这对于高移动性的车辆非常关键——车辆在 RSU 覆盖范围内停留时间有限，减少交互轮次直接提升了方案的实用性。

### 优势 5：真实区块链环境验证
许多区块链+车载网络的论文仅给出理论设计或模拟实验。BAST 在 Goerli 测试网上实际部署了智能合约并测量了 Gas 消耗，提供了真实世界可行性的证据。这一点提升了论文的实践可信度。

## 6.2 明显不足

### 6.2.1 性能方面

**车辆端签名验证开销偏高**：
当 t = 20, n = 30 时，车辆（RPi3）完成一次完整验证需要约 3.86 秒。论文将此与 [3] 的验证过程对比时存在不公平——[3] 的验证由算力更强的 EN 执行。考虑到车载应用对延迟的敏感性（车辆以 100 km/h 行驶时每秒移动约 28 米），3.86 秒的验证延迟可能导致车辆在验证完成前已经离开 RSU 的服务范围。

**通信开销高于多数对比方案**：
BAST 的签名通信量（7596 bytes, t = 20）高于 5 个对比方案中的 3 个。对于无线信道来说，更大的消息意味着更长的传输时间和更高的丢包风险。论文的辩护（RSU-ES 之间是有线连接）确实减轻了部分担忧，但RSU到车辆的无线传输仍然是瓶颈。

**枚举追溯的计算复杂度**：
区块链追溯过程需要枚举 $\binom{n}{t}$ 种可能的签名者组合来验证。当 $n = 1.5t$ 时，$\binom{1.5t}{t}$ 随 t 增长极快（例如 t=20 时约为 3000 万种组合）。论文未讨论这个组合枚举在实际区块链环境中的 Gas 成本和计算时间。

### 6.2.2 安全性方面

**门限与安全性的定量关系不明确**：
论文未讨论 t 的选择如何影响实际安全性。例如，如果部署区域有 15 个 ES，门限设为 10，攻击者只需要攻陷 10 个 ES 即可伪造签名。论文假设"攻击者只能攻陷有限数量"，但未给出这个假设在实际部署中的合理性论证。

**可追溯性的局限性**：
虽然区块链可以追溯到恶意签名者集合 C，但不能精确到集合中的单个恶意 ES。如果 C 中包含 t 个 ES，其中只有 k < t 个是真正恶意的，区块链将标记所有 t 个 ES——包括无辜方。这是一个**集体追责**模式，可能导致合法 ES 被错误标记。

**RSU 诚实但好奇假设的实际风险**：
如果 RSU 被攻陷，攻击者可以：
- 选择性地丢弃合法 ES 的签名份额
- 向车辆发送任意（但格式正确）的消息
- 虽然不能单独伪造有效聚合签名（需要 t 个 ES 的私钥），但可以执行拒绝服务攻击

**随机预言机模型的依赖**：
Fiat-Shamir 变换的安全性在随机预言机模型下成立，但在标准模型下不必然成立。使用具体哈希函数（如 SHA-256）实例化时，可能存在与 ROM 理想化假设之间的差距。

**缺乏隐私保护**：
论文未涉及车辆的隐私保护（如位置隐私、身份隐私）。虽然在 SIG 层面车辆使用 TA 颁发的匿名凭证，但证书 $Cert_{vid_i}$ 与唯一标识 $vid_i$ 绑定，可能导致车辆被追踪。

### 6.2.3 可扩展性方面

**线性增长的 Σ-协议验证复杂度**：
车辆端验证涉及 $(3n + t + 4)$ 次指数运算和 $(2n + 3)$ 次标量乘运算，随 n 和 t 线性增长。在大规模部署中（n 很大），验证开销可能变得不可接受。

**区块链共识延迟**：
论文未讨论区块链交易的确认时间如何影响系统可用性。在以太坊上，交易确认通常需要 12-15 秒（多个区块确认），而车辆在 RSU 覆盖范围内的有效通信窗口可能只有几秒到几十秒。

**智能合约的 Gas 限制**：
追溯操作涉及 $\binom{n}{t}$ 枚举，随着 n 和 t 增长，可能超出以太坊的 Gas 限制（~30M gas/block），导致追溯操作无法在单笔交易中完成。

### 6.2.4 实用性/部署方面

**TA 的单点信任风险**：
虽然 BAST 消除了对 ES 的信任，但 TA 仍然是单点信任根。如果 TA 被攻陷，系统所有密钥材料将泄露。论文未讨论如何减轻 TA 的单点风险（如使用分布式密钥生成）。

**密钥管理复杂性**：
系统中存在多种密钥类型（sk、sk_ag、sk_t、sk_rs、sk_e 等），且需要在多个实体间安全分发。密钥更新、吊销等生命周期管理操作在论文中未被讨论。

**对区块链全节点的依赖**：
论文要求 BS 作为完全可信的全节点，这在公共区块链（如以太坊）上是一个相当强的假设。

### 6.2.5 理论方面

**Game 序列的安全性证明存在跳跃**：
从 Game 0 到 Game 1 的过渡中，论文声称引入知识提取器后概率关系为 $\Pr[W_1] \geq (\Pr[W_0] - \varepsilon)/q$。但论文未严格证明 Ext 在 BAST 具体构造中的运行时间和成功率。此外，证明中"同时处理多个会话"的复杂性（因为 Ext 需要回滚到特定哈希查询点）未被充分讨论。

**门限 t 在安全性证明中的角色模糊**：
在 Game 序列的安全性证明中，门限 t 的角色未得到形式化处理——证明似乎假设任何 t 都安全，但直觉上 t 越小越容易遭受攻击（因为需要攻陷的 ES 越少）。

## 6.3 适用边界

### 最适合的场景

1. **城市主干道/高速公路场景**：ES 沿路密集部署（n 较大），门限 t 可以设置得足够高以提供强安全保证
2. **非超低延迟应用**：导航地图更新、娱乐内容缓存等延迟容忍度相对较高的服务（秒级可接受）
3. **对数据可靠性要求极高的场景**：交通安全警告、事故通报等不能容忍虚假信息的应用
4. **有区块链基础设施的智慧城市**：已经部署了区块链节点的城市交通系统

### 不适合的场景

1. **超低延迟安全应用**：碰撞预警、紧急制动等毫秒级延迟要求的应用（3.86 秒验证太慢）
2. **ES 部署稀疏的乡村道路**：ES 数量少（n 小），门限 t 难以设置得足够高
3. **没有区块链基础设施的环境**：方案依赖区块链全节点，在没有 BS 部署的区域不可用
4. **车辆密度极高的场景**（如大型停车场、交通拥堵）：RSU 需要同时处理大量车辆请求，聚合签名的产生速率可能成为瓶颈
5. **对隐私有极高要求的场景**：方案未提供位置隐私和强匿名性保护

## 6.4 隐藏的 Trade-off

### Trade-off 1：门限 t 的选择——可靠性与性能
- t 越大 → 需要越多的 ES 参与签名 → 恶意方伪造签名越困难 → 安全性越高
- t 越大 → 车辆验证开销越大（O(t)）→ 性能越差
- 论文未讨论这个最优 t 的选择方法

### Trade-off 2：可追溯性 vs 精确追责
- 区块链可以追溯到参与签名的 t 个 ES 的集合，但不能精确识别其中哪些是恶意方
- 这是一种"为安全牺牲精确性"的设计——宁可误标记无辜 ES，也不能让恶意 ES 逃脱
- 实际影响：合法 ES 如果与恶意 ES 在同一集合中参与签名，可能被"连坐"

### Trade-off 3：非交互性 vs 安全模型
- Fiat-Shamir 变换将交互式协议转为非交互式，获得效率
- 但安全性证明从标准模型降级到随机预言机模型
- 协议失去了交互式版本的"在线可提取性"优势

### Trade-off 4：RSU 的聚合角色——效率 vs 信任
- RSU 聚合签名减少了车辆的计算负担
- 但引入了对 RSU 的信任依赖（诚实但好奇），增加了攻击面

### Trade-off 5：通信开销 vs 安全信息丰富度
- BAST 签名包含 π、tg、ct₁、ct₂ 等额外安全信息 → 通信量更大
- 但这些信息是实现可追溯性和非交互验证的必要代价
