# 整体架构与系统设计

## 3.1 系统总览

DBCPA 系统采用**三层网络模型**，结合**双区块链架构**，形成去中心化的条件隐私保护认证体系。

```
                        ┌─────────────────────────┐
                        │     Trusted Authority    │
                        │         (TA)             │
                        │  - 系统初始化            │
                        │  - 车辆注册              │
                        │  - 智能合约部署          │
                        │  - 恶意车辆追踪          │
                        └───────────┬─────────────┘
                                    │ 管理
                                    ▼
           ┌────────────────────────────────────────────┐
           │          私有区块链 (Private Blockchain)    │  ← 上层
           │  共识: PBFT | 矿工: TA | 共识节点: 受信RSU │
           │  ┌─────────────────────────────────────┐   │
           │  │     EPIT (实体私密信息表)             │   │
           │  │  VIDᵢ-PIDᵢ-Vpkᵢ-skᵢ-tᵢ 映射关系    │   │
           │  │  智能合约: insert, update, query,     │   │
           │  │           delete, complaint,          │   │
           │  │           threshold, revoke           │   │
           │  └─────────────────────────────────────┘   │
           └──────────────┬─────────────────────────────┘
                          │ 查询权限（受信RSU节点）
                          ▼
           ┌────────────────────────────────────────────┐
           │          受信 RSU（私有区块链节点）          │  ← 中间层
           │  - 定期更新车辆假名身份                     │
           │  - 调用私有区块链智能合约                   │
           │  - 查询 EPIT                                │
           └──────────────┬─────────────────────────────┘
                          │
                          ▼
           ┌────────────────────────────────────────────┐
           │        联盟区块链 (Consortium Blockchain)   │  ← 下层
           │  共识: PBFT | 矿工: RSU | 轻节点: 车辆       │
           │  ┌─────────────────────────────────────┐   │
           │  │    EPPKT (实体假名公钥表)             │   │
           │  │  PIDᵢ-Vpkᵢ 映射关系                   │   │
           │  │  聚合 V2V 和 V2I 交易                 │   │
           │  └─────────────────────────────────────┘   │
           └──────────────┬─────────────────────────────┘
                          │ 查询公钥
                          ▼
           ┌────────────────────────────────────────────┐
           │          普通 RSU（联盟区块链矿工）         │  ← 中间层
           │  - 消息聚合与转发                           │
           │  - 区块打包                                 │
           │  - 消息验证                                 │
           └──────────────┬─────────────────────────────┘
                          │ V2I 通信
                          ▼
           ┌────────────────────────────────────────────┐
           │       车辆 OBU（联盟区块链轻节点）          │  ← 下层
           │  - 消息签名与广播                           │
           │  - 消息验证（存储区块头）                   │
           │  - 定期更新假名                             │
           └────────────────────────────────────────────┘
```

### 双区块链数据流

```
   私有区块链 (Private)              联盟区块链 (Consortium)
   ┌──────────────────┐             ┌──────────────────┐
   │ 存储:             │             │ 存储:             │
   │  VIDᵢ ↔ PIDᵢ     │   TA部署    │  PIDᵢ ↔ Vpkᵢ    │
   │  Vpkᵢ, skᵢ, tᵢ  │ ◄─────────► │  交易记录         │
   │                  │  交互       │                  │
   │ 访问控制:         │             │ 访问控制:         │
   │  仅TA+受信RSU   │             │  许可节点即可    │
   └──────────────────┘             └──────────────────┘
        隐私层                           服务层
```

## 3.2 参与实体与角色

### 实体 1：可信权威（TA）

| 属性 | 描述 |
|------|------|
| **信任级别** | 完全可信 |
| **计算能力** | 强大 |
| **主要职责** | 系统初始化、实体注册、智能合约部署、私有区块链维护、恶意车辆追踪与撤销 |
| **在线要求** | 仅在系统初始化和注册阶段需要在线的离线实体；认证阶段不参与 |
| **关键数据** | 持有系统私钥 $s$ 和注册私钥 $x$ |

### 实体 2：车辆（Vehicle/OBU）

| 属性 | 描述 |
|------|------|
| **信任级别** | 不可信 |
| **计算能力** | 中等（配备防篡改处理单元） |
| **主要职责** | 作为联盟区块链的轻量级验证节点，仅存储区块头；广播签名消息；验证接收消息 |
| **关键数据** | 持有假名身份 $PID_i$、私钥 $sk_i$、公钥 $Vpk_i$、注册凭证 $\{C_i, D_i, e_i\}$ |

### 实体 3：路边单元（RSU）

RSU 分为两种角色：

| 角色 | 类型 | 信任级别 | 职责 |
|------|------|----------|------|
| **私有区块链 RSU** | 预选的受信 RSU | 半可信 | 私有区块链共识节点；查询 EPIT；定期为车辆更新假名；发起恶意车辆投诉 |
| **联盟区块链 RSU** | 普通 RSU | 不可信 | 联盟区块链矿工节点；聚合 V2V/V2I 通信；存储完整区块数据；消息验证 |

## 3.3 模块划分与分工

### 模块 1：系统初始化模块
- **执行者**：TA
- **功能**：生成 ECC 参数 $ECC_{params} = \{q, a, b, n, P, P_{pub}, H_1, H_2\}$；生成系统秘钥 $s$ 和注册秘钥 $x$；初始化双区块链

### 模块 2：智能合约模块
- **部署位置**：私有区块链
- **基本功能**：
  - `insertEPIT()`：插入车辆私密信息
  - `updateEPIT()`：更新车辆安全数据
  - `queryEPIT()`：查询车辆信息
  - `deleteEPIT()`：删除车辆记录
- **高级功能**：
  - `ThresholdSet()`：动态设置撤销阈值
  - `complaint()`：添加恶意车辆投诉记录
  - `judgeThreshold()`：判断投诉是否达阈值并自动撤销

### 模块 3：车辆注册模块
- **执行者**：TA + 车辆
- **功能**：生成假名集合 $PID_i$、计算认证因子 $C_i, D_i$、预装载 OBU
- **关键算法**：$PID_i = VID_i \oplus H_1(sk_i \cdot P_{pub})$

### 模块 4：登录与认证模块
- **执行者**：车辆 + RSU
- **功能**：车辆登录验证、消息签名生成、消息签名验证、公钥查询（EPPKT）
- **关键验证式**：$u_i \cdot P = R_i + a_i' \cdot Vpk_i$

### 模块 5：假名更新模块
- **执行者**：受信 RSU + 车辆
- **功能**：定期从私有区块链获取新假名及密钥对；加密签名后发送给车辆；车辆验证后更新 OBU

### 模块 6：车辆撤销模块
- **执行者**：TA + RSU + 智能合约
- **两种模式**：
  - **直接撤销**：TA 主动终止恶意车辆状态
  - **阈值撤销**：投诉数达阈值后智能合约自动执行

### 模块 7：密码变更模块
- **执行者**：车辆 OBU
- **功能**：用户本地更新登录密码，更新存储元组

### 认证阶段核心验证流程（详细）

```
  发送方车辆 Vᵢ                    接收方（RSU/车辆）
  ──────────────                   ──────────────
  1. 本地认证:
     Bᵢ* = H₀(pw || bᵢ)
     Aᵢ* = Cᵢ ⊕ Bᵢ*
     Dᵢ* = H₀(VIDᵢ || Bᵢ* || Aᵢ*)
     检验 Dᵢ* ≟ Dᵢ

  2. 签名生成:
     选取随机数 rᵢ ∈ Zₙ*
     Rᵢ = rᵢ · P
     aᵢ = H₂(PIDᵢ || Rᵢ || Mᵢ || Tᵢ)
     uᵢ = rᵢ + aᵢ · skᵢ mod n

  3. 广播:                     4. 验证:
  {PIDᵢ, Mᵢ, Rᵢ, Tᵢ, uᵢ} ──►  检验 Tᵢ 新鲜性
                                查询联盟区块链 EPPKT:
                                  通过 PIDᵢ 获取 Vpkᵢ
                                计算 aᵢ' = H₂(PIDᵢ || Rᵢ || Mᵢ || Tᵢ)
                                检验 uᵢ·P ≟ Rᵢ + aᵢ'·Vpkᵢ

                              正确性:
                              uᵢ·P = (rᵢ + aᵢ·skᵢ)·P
                                   = rᵢ·P + aᵢ·skᵢ·P
                                   = Rᵢ + aᵢ·Vpkᵢ ✓
```

## 3.5 安全/威胁模型

### 信任假设

| 实体 | 信任级别 | 说明 |
|------|----------|------|
| **根 TA** | 完全可信 | 不会与其他方合谋；具有强大的计算、通信和存储能力 |
| **私有区块链 RSU** | 半可信 | 可查询区块链信息，但需遵守预设的访问控制 |
| **联盟区块链 RSU** | 不可信 | 可能被对手控制或本身就是攻击者 |
| **车辆（OBU）** | 不可信 | 任何车辆都可能是攻击者 |

### 攻击者能力假设

论文将攻击者分为两类：

1. **被动攻击者（Passive Attacker）**：
   - 持续监听 VANET 通信信道
   - 目标：追踪车辆轨迹、破解消息机密性
   - 无法修改或注入消息

2. **主动攻击者（Active Attacker）**：
   - 可以修改或伪造通信消息
   - 可以冒充合法车辆广播消息
   - 可以发起重放攻击（Replay Attack）
   - 可以尝试离线密码猜测攻击
   - 可以发动 DDoS 攻击

### 安全目标（8 项）

| # | 安全需求 | 含义 |
|---|----------|------|
| 1 | 单次注册 | 车辆仅需注册一次即可持续使用 |
| 2 | 消息认证 | 接收方能验证消息发送者身份和消息完整性 |
| 3 | 隐私保护 | 任何实体无法从通信中获取车辆真实身份 |
| 4 | 可追踪性 | TA 在必要时可还原恶意车辆真实身份 |
| 5 | 无在线注册中心 | 认证阶段不需要 TA 在线参与 |
| 6 | 不可链接性 | 无法将两条消息关联到同一车辆 |
| 7 | 抗网络攻击 | 抵抗离线密码猜测、重放、假冒、DDoS 攻击 |
| 8 | 条件隐私保护 | 正常情况隐私受保护，异常情况可追溯 |

### 安全边界分析

关键在于**信任边界**的划分：私有区块链与联盟区块链之间的**信息隔离**是安全的核心设计原则。

- 联盟区块链中的 EPPKT 仅存储 `{PID_i, Vpk_i}`，**不包含任何可追溯到真实身份的信息**
- 私有区块链中的 EPIT 存储 `{VID_i, PID_i, Vpk_i, sk_i, t_i}` 完整映射，但访问仅限 TA 和受信 RSU
- 攻击者即使控制了联盟区块链节点或车辆，也只能获得假名-公钥映射，无法还原真实身份
