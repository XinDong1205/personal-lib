# 3. 整体架构与系统设计

## 3.1 系统总览

APA 协议系统分为两个主要阶段：**注册阶段（Registration Phase）** 和**事故报告生成阶段（Accident Report Generation Phase）**。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                          区块链（Hyperledger Fabric）                      │
│  ┌──────────────────────────┐    ┌──────────────────────────────────┐   │
│  │  注册信息（Registration）  │    │   签名事故报告（Signed Reports）    │   │
│  │  {PIDi, PKVi, VaIi}      │    │  {cij, PKVi, PKVj, AC1, AC2,    │   │
│  │  {RIDt, PKRt}            │    │   Dij, T1, PIDi, T2, PIDj,       │   │
│  │  写入权限: RC             │    │   VaIi, VaIj, RIDt, PKRt,        │   │
│  │  读取权限: 授权实体        │    │   T4, ct, Dt}                    │   │
│  └──────────────────────────┘    │  写入权限: RSU                    │   │
│                                  │  读取权限: 车辆/交警/保险公司       │   │
│                                  └──────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────────┘
         ▲         ▲         │                      ▲          │
         │         │         │                      │          │
    ⑥写入注册   ⑦⑧读取    ⑩读取注册              ⑫写入报告    │
      信息      注册信息     信息                               │
         │         │         │                      │          │
         ▼         ▼         ▼                      ▼          ▼
   ┌─────────┐ ┌──────────────────────────┐  ┌──────────┐  ┌──────────┐
   │   RC    │ │    事故车辆 Vi, Vj        │  │   RSU    │  │交警/保险  │
   │(注册中心)│ │                          │  │ (路边单元)│  │(只读用户) │
   └────┬────┘ │  ① 相互认证 (V2V)        │  └────┬─────┘  └──────────┘
```

**消息流说明**：

| 消息流 | 内容 | 阶段 |
|--------|------|------|
| ① | 车辆向 RC 提交注册请求 {VIDi, PKvi, VaIi} | 注册阶段 |
| ② | RC 颁发认证参数 {PIDi, ri} | 注册阶段 |
| ③ | 驾驶员输入生物特征 Bioi | 注册阶段 |
| ④ | 加密参数存入 OBU | 注册阶段 |
| ⑤ | RSU 从 RC 获取认证参数 | 注册阶段 |
| ⑥ | RC 将注册信息写入区块链 | 注册阶段 |
| ⑦⑧ | 事故车辆从区块链读取对方注册信息 | 事故报告生成 |
| ⑨ | V2V 相互认证与联合签名 | 事故报告生成 |
| ⑩ | RSU 从区块链读取自身注册信息 | 事故报告上传 |
| ⑪ | V2R 认证与报告上传 | 事故报告上传 |
| ⑫ | RSU 将签名报告写入区块链 | 事故报告上传 |

## 3.2 参与实体与角色

| 实体 | 标识符 | 职责 | 权限 |
|------|--------|------|------|
| **RC（Registration Center）** | — | 系统初始化、车辆与 RSU 注册、伪身份生成与更新、恶意车辆追踪 | 区块链写入（注册信息）；持有主密钥 $KTA$ |
| **车辆（Vehicle）** | $V_i$（真实身份 $VID_i$） | 参与 V2V 认证、联合签名事故报告、发起 V2R 认证、定期更新伪身份 | 载有 OBU，存储认证参数和生物特征参数 |
| **RSU（Roadside Unit）** | $R_t$（身份 $RID_t$） | 广播自身身份、验证事故报告签名、将签名报告写入区块链 | 区块链写入（事故报告）；配备 PUF 保护私钥 |
| **驾驶员（Driver）** | — | 提供生物特征（如指纹/虹膜）用于双因素认证 | — |
| **交警/保险公司** | — | 读取区块链上的事故报告进行事故处理 | 区块链只读 |

## 3.3 模块划分与分工

### 模块 1：系统初始化模块
- 负责椭圆曲线参数选择、哈希函数确定、对称加密方案选择、模糊提取器（Fuzzy Extractor）初始化
- 输出全局公开参数 $Para = \{P, E(F_p), SE(\cdot), h(\cdot), Gen(\cdot), Rep(\cdot)\}$

### 模块 2：注册模块
- **车辆注册**：验证车辆身份 → 生成伪身份 PID → 加密存储认证参数到 OBU
- **RSU 注册**：生成 RSU 密钥对 → 使用 PUF 保护私钥 → 存储认证参数
- **区块链写入**：RC 将车辆和 RSU 的注册信息写入区块链

### 模块 3：V2V 认证与签名模块
- 两轮交互协议：第一轮交换事故数据与部分签名，第二轮生成聚合签名
- 双因素认证：生物特征验证 + OBU 存储参数验证
- 输出联合签名 $c_{ij}$ 和聚合公钥参数 $D_{ij}$

### 模块 4：V2R 认证与上传模块
- 车辆向 RSU 提交已签名的事故报告
- RSU 验证签名 → 生成自身签名 → 将完整数据包写入区块链

### 模块 5：伪身份更新模块
- 车辆发起更新请求 → RC 验证 → 生成新伪身份 $PID_i^*$ → 更新区块链 → 车辆更新 OBU

| RA2 | $R_t$ 写入链 | 完整交易数据包 | 永久存证 |

## 3.5 安全/威胁模型

### 攻击者能力假设

APA 协议考虑了以下五类攻击能力（由弱到强）：

| 能力级别 | 描述 | 攻击类型 |
|---------|------|---------|
| **C1** | 窃听公共信道上的任何消息 | 被动攻击 |
| **C2** | 插入、删除、修改、重放公共信道上的任何消息 | 主动攻击 |
| **C3** | 腐化车辆或 RSU 的私钥 | 内部攻击者 |
| **C4** | 窃取 OBU 中的存储数据 | 物理攻击（因子1） |
| **C5** | 伪造驾驶员的生物特征 | 生物特征攻击（因子2） |

### 信任边界

```
  ┌──────────────────────────────────────────────────────────┐
  │                    可信域（Trusted）                       │
  │  ┌─────────┐                                             │
  │  │   RC    │  完全可信，不会主动作恶                       │
  │  └─────────┘                                             │
  └──────────────────────────────────────────────────────────┘

  ┌──────────────────────────────────────────────────────────┐
  │                  半可信域（Semi-trusted）                   │
  │  ┌──────────┐  ┌──────────┐                              │
  │  │   RSU    │  │  车辆     │  可以协议执行，但可能被俘获/被攻击│
  │  └──────────┘  └──────────┘                              │
  └──────────────────────────────────────────────────────────┘

  ┌──────────────────────────────────────────────────────────┐
  │                    不可信域（Untrusted）                    │
  │              公共无线信道（Public Channel）                 │
  │         攻击者可执行 C1~C5 中的所有操作                     │
  └──────────────────────────────────────────────────────────┘
```

### 安全目标

基于以上威胁模型，APA 协议需要满足三个核心安全属性：

1. **正确性（Correctness）**：合法的交易数据必须满足两个验证等式
   - $c_{ij} \cdot P = PK_{Vj} + PK_{Vi} + h(AC_1\|AC_2\|D_{ij}\|T_1\|PID_i\|T_2\|PID_j\|VaI_i\|VaI_j) \cdot D_{ij}$
   - $c_t \cdot P = PK_{Rt} + h(c_{ij}\|T_4\|D_t) \cdot D_t$

2. **存在性不可伪造性（Existential Unforgeability）**：攻击者不能在没有参与协议执行、未腐化私钥、未同时获得 OBU 和生物特征的情况下，伪造有效的交易数据

3. **匿名性（Anonymity）**：攻击者无法区分伪身份对应的真实车辆身份（在未获得 RC 主密钥 $KTA$ 的前提下）
