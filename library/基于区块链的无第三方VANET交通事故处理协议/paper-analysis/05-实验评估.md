# 05 — 实验与评估

## 5.1 实验设计

论文的实验设计围绕两个维度展开：

1. **安全性对比**（定性）：将 APA 协议与 5 个相关方案（[5], [10], [12], [16], [17]）在 13 种安全属性和攻击抵抗力上进行逐一对比。

2. **性能对比**（定量）：在统一硬件平台上模拟签名生成和验证操作的时间开销，并分析 V2V 和 V2R 的通信开销及延迟。

实验目标可以概括为验证贡献声明中的第 4 点——"我们的方案在保证更高安全性的同时保持更低的开销"。

---

## 5.2 实验环境

| 项目 | 配置 |
|------|------|
| **硬件平台** | Raspberry Pi 4B（四核 64 位 ARM Cortex-A72） |
| **CPU 频率** | 1.5 GHz |
| **内存** | 2 GB LPDDR4 SDRAM |
| **区块链平台** | Hyperledger Fabric |
| **集成框架** | gRPC（用于 VANETs 与区块链的通信集成） |
| **共识机制** | 基于 Kafka 的模块化共识（可调优缩短交易确认时间） |
| **块大小策略** | 动态调整机制（根据网络状况自适应） |
| **哈希函数** | SHA-256 |
| **对称加密** | AES-128 |
| **身份/时间戳大小** | 32 bits |
| **随机数大小** | 256 bits |

### 关于硬件选择的评价

选择 Raspberry Pi 4B 作为测试平台是合理的——论文指出 Raspberry Pi 已被广泛用作 VANETs 车辆的控制核心，具有轻量级、可扩展、兼容多种无线通信模式等优点。使用与实际部署环境接近的硬件进行性能评估，得出的数据比在高性能服务器上跑更有说服力。但 2 GB 内存对于未来可能需要在 OBU 上运行更复杂计算的场景可能略显不足。

## 5.3 单次操作的时间基准

论文通过实验测量了各基础操作在 Raspberry Pi 4B 上的运行时间：

| 符号 | 操作 | 时间 (ms) |
|------|------|-----------|
| $T_{exp}$ | 模幂运算 | 5.026 |
| $T_h$ | 哈希运算 | 0.019 |
| $T_{mul}$ | 模乘法 | 0.023 |
| $T_{ecc}$ | ECC 点乘 | 2.610 |
| $T_{bp}$ | 双线性对运算 | 44.517 |
| $T_{ead}$ | ECC 点加 | 0.017 |
| $T_{ECE\_SV}$ | EC-Elgamal 签名/验证 | 7.849 |
| $T_{HE\_SV}$ | Paillier 签名/验证 | 11.024 |
| $T_{HE\_ED}$ | Paillier 加/解密 | 10.173 |
| $T_{SED}$ | 对称加/解密 | 0.560 |

关键观察：
- ECC 点乘（$T_{ecc} = 2.610$ ms）是主导开销的操作
- 双线性对（$T_{bp} = 44.517$ ms）极其昂贵——避免使用 pairings 是本方案高效的主要原因之一
- 哈希（$T_h = 0.019$ ms）和对称加密（$T_{SED} = 0.560$ ms）几乎可以忽略不计

## 5.4 对比方案

| 方案 | 发表于 | 核心特征 |
|------|--------|---------|
| Liu et al. [5] | IEEE JIoT 2020 | 区块链信任管理 + 条件隐私保护的公告方案 |
| Cheng et al. [10] | IEEE T-ITS 2022 | 同态加密 + 车辆反馈的隐私保护协议 |
| Chen et al. [12] | IEEE JIoT 2022 | 多重签名 + 紧急事件报告方案 |
| Li et al. [16] | IEEE TVT 2021 | 同态加密 + 区块链 V2R/V2V 认证 |
| Zhang & Xu [17] | Connect. Sci. 2022 | 区块链匿名认证 + 交通报告 |

### 对比方案的选择合理性

这 5 个方案代表了 2020-2022 年间 VANETs 事故/报告认证方向的主要技术路线：
- [5] [12] 属于"目击车辆签名"路线
- [10] 属于"同态加密 + 隐私反馈"路线
- [16] [17] 属于"区块链 + 认证"路线

覆盖了论文试图替代的主要竞争方案，选择基本合理。但缺少与 2023-2024 年最新工作的对比（如 Wei et al. [23] 的多 TA 模型等）。

## 5.5 实验结果分析

### 5.5.1 安全性对比（Table III）

论文对比了 13 个维度：

| 安全属性 | APA | [5] | [10] | [12] | [16] | [17] |
|---------|-----|-----|------|------|------|------|
| 抵抗特权内部攻击 | ✓ | ✗ | — | — | — | — |
| 抵抗离线口令猜测 | ✓ | — | — | — | — | — |
| 抵抗冒充攻击 | ✓ | ✗ | ✗ | ✗ | ✓ | ✗ |
| 抵抗重放攻击 | ✓ | ✗ | ✓ | ✗ | ✓ | ✓ |
| 抵抗中间人攻击 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| 抵抗 OBU 入侵攻击 | ✓ | ✗ | ✗ | ✗ | ✓ | ✗ |
| 抵抗 RSU 捕获攻击 | ✓ | ✗ | ✗ | ✗ | ✗ | ✓ |
| 抵抗更新异步攻击 | ✓ | — | — | — | — | — |
| 身份匿名性 | ✓ | ✗ | ✗ | ✓ | ✓ | ✗ |
| 双向认证 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| 批验证 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| 恶意消息追踪 | ✓ | ✓ | ✓ | ✗ | ✓ | ✓ |
| 不可链接性 | ✓ | ✗ | ✗ | ✓ | ✓ | ✗ |

**分析**：

1. **APA 是唯一全项通过的方案**——这是论文安全对比的核心 selling point。
2. **RSU 捕获攻击**是最普遍的安全漏洞——6 个方案中仅 APA 和 [17] 抵抗（APA 用 PUF、[17] 无 RSU 中心化角色）。这说明大多数方案将过多信任置于 RSU 上。
3. **OBU 入侵攻击**仅 APA 和 [16] 抵抗——其他方案将密钥以明文或弱保护形式存储在 OBU 中，APA 通过生物特征加密双因子保护解决。
4. **不可链接性**仅 APA 和 [16] 同时满足——说明 APA 的伪身份设计在隐私保护上具备竞争力。
5. 关于 [5] 的重放攻击脆弱性：论文指出 [5] 的接收方无法识别重放消息——这是一个严重的协议设计缺陷。

### 5.5.2 计算开销对比（Table IV）

| 方案 | 签名 (单车辆, ms) | 验证 (ms) | 批验证 ($n$ 车辆, ms) | 总开销 (签名+验证, ms) |
|------|-------------------|-----------|----------------------|----------------------|
| [5] | — | 35.164 | $(102.023 + 1.057n)$ | — |
| [10] | 44.00 | — | — | — |
| [12] | 20.215 | — | — | — |
| [16] | — | 127.607 | $(565.323 + 550.646n)$ | V2V: 400.907 |
| [17] | 102.023 | — | — | — |
| **APA** | **21.146** | **—** | **$(16.263 + 4.319n)$** | **—** |
| **APA (更新)** | 3.806 | — | — | — |

**关键数据分析**：

1. **单签名开销**：APA（21.146 ms）与 [12]（20.215 ms）基本持平，远低于 [17]（102.023 ms）和 [10]（44.00 ms）。这说明 APA 在保证更高安全性的同时，签名生成效率并未降低。
   - APA 签名需 $4T_{ecc} + 4T_h \approx 4 \times 2.610 + 4 \times 0.019 = 10.516$ ms（理论值），与实测 21.146 ms 有差距——可能包含通信等待和其他系统开销。

2. **批验证优势**：APA 的批验证系数为 $(16.263 + 4.319n)$ ms，远优于 [16] 的 $(565.323 + 550.646n)$ ms 和 [5] 的 $(102.023 + 1.057n)$ ms。这意味着当 $n=50$ 时：
   - APA：$16.263 + 4.319 \times 50 \approx 232$ ms
   - [16]：$565.323 + 550.646 \times 50 \approx 28,098$ ms
   - APA 快约 120 倍

3. **消除 RSU 签名开销**：APA 中 RSU 不参与事故报告的签名生成（仅做验证和上链），这与 [5] 的架构类似，是显著的效率优势。

4. **身份更新开销**：$3.806$ ms（车辆端）+ $2.24$ ms（RC 端），在整体开销中几乎可忽略。

### 5.5.3 通信开销与延迟对比（Table V）

| 方案 | V2V 开销 | V2V 延迟 | V2R 开销 | V2R 延迟 |
|------|---------|---------|---------|---------|
| [5] | $2208L$ bits | $> 27$ ms | $869M$ bits | $> 36$ ms |
| [10] | — | — | $1376M+832$ bits | $> 44$ ms |
| [12] | $512W$ bits | $> 31$ ms | $512V+512W+1024$ complex bits | $> 21$ ms |
| [16] | $2976$ bits | $71$ ms | $832$ bits | $128$ ms |
| [17] | — | — | $1152+577M$ bits | $> 102$ ms |
| **APA** | **2240 bits** | **16 ms** | **704 bits** | **22 ms** |

**关键发现**：

1. **APA 的通信开销绝对最小**：V2V 仅 2240 bits（280 bytes），V2R 仅 704 bits（88 bytes）。相比之下，[5] 的 V2V 开销为 $2208L$ bits——$L$ 是身份集合的基数，随着参与车辆增多而线性增长。APA 的开销是**常数级**的，与参与车辆数无关。

2. **延迟不随规模增长**：论文明确指出"我们的协议的延迟不受车辆数和传输消息数的影响"。这一特性来自于 APA 的协议设计中事故报告仅由当事车辆生成——没有广播-收集-验证的等外循环。对比 [5] 需要 $> 27$ ms（且随 $L$ 增长），APA 的 16 ms 是显著优势。

3. **与 [12] 的比较需要谨慎**：[12] 的 V2R 开销含 $V$（周围车辆数）和 $W$（目击车辆数）两个变量，在最简单情况（$V=W=1$）下约为 2048 bits，但实际场景中这两个参数远大于 1。

### 5.5.4 关于区块链平台性能

论文未提供 Hyperledger Fabric 的详细性能指标（交易吞吐量 TPS、确认延迟、块生成时间等），这是一个**明显的实验缺失**。虽然论文提到了采用 Kafka 共识、动态块大小调整等优化措施，但没有给出任何量化数据来证明这些措施在实际 VANET 环境中的有效性。

## 5.6 实验评价

### 充分验证的部分

1. **安全性对比全面**：13 个维度的定性对比覆盖了 VANETs 认证协议的主要安全需求
2. **计算开销分析细致**：区分了签名、验证、批验证、身份更新等各子操作的开销
3. **对比方案合理**：涵盖 2020-2022 年间的主要相关工作

### 实验的不足与缺失

1. **无真实网络环境模拟**：所有通信延迟数据均为"理论最小值"（基于消息大小和带宽），未在真实/模拟的 VANET 网络环境（如 NS-3、SUMO、Veins 等）中测试。VANET 的移动性、信号衰减、网络拓扑动态变化等关键因素完全未被考虑。

2. **无双线性对方案的公平比较**：对比方案中 [16] 使用双线性对（$T_{bp} \approx 44.5$ ms），而 APA 使用普通 ECC——pairing-based 方案天然比 ECC-based 方案慢 10-20 倍。如果与另一基于 ECC 的方案（如 [14] Xie et al. 自己的 T-ITS 2023 工作）在相同条件下对比，优势可能不会如此显著。

3. **区块链性能数据缺失**：未提供 Fabric 的交易吞吐量、确认延迟等指标。对于一篇声称"利用区块链实现"的论文，这是不应遗漏的部分。

4. **批验证的 batch size 影响分析缺失**：虽然给出了批验证的公式，但未分析不同 $n$ 值下验证错误率与随机权重之间的关系。

5. **PUF 的实际误差率未讨论**：PUF 在温度变化、老化等情况下的误码率（bit error rate）会影响 $SK_{Rt} = PUF(Cha_t) \oplus RSK_{Rt}$ 的正确恢复。论文未给出任何 PUF 可靠性数据。

6. **模糊提取器的性能数据缺失**：生物特征认证（Gen/Rep 操作）的实际时间开销和错误拒绝率（FRR）/错误接受率（FAR）没有提供。

### 总体评价

实验部分在"纸上对比"层面是充分的，足以支撑论文的核心宣称（"比相关方案更安全且开销更低"）。但对于一个声称面向真实 VANET 部署的协议，实验缺乏网络级别的模拟验证和区块链性能的实证数据——这使得从"安全可行"到"工程可用"之间存在一个尚未填补的鸿沟。
