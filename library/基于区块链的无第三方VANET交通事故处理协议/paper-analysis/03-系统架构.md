# 03 — 整体架构与系统设计

## 3.1 系统总览

```
┌──────────────────────────────────────────────────────────────────────┐
│                         区块链 (Hyperledger Fabric)                     │
│  ┌──────────────────────────┐   ┌──────────────────────────────────┐  │
│  │  车辆注册信息             │   │  事故报告                        │  │
│  │  {PID_i, PK_Vi, VaI_i}   │   │  {cij, PK_Vi, PK_Vj, AC1, AC2,  │  │
│  │  {RID_t, PK_Rt}          │   │   Dij, T1, PIDi, T2, PIDj, ... } │  │
│  └──────────────────────────┘   └──────────────────────────────────┘  │
│       ▲ ⑥写入          ▲ ⑩读取          ▲ ⑫写入            ▲ ⑦⑧读取   │
└───────┼────────────────┼─────────────────┼──────────────────┼─────────┘
        │                │                 │                  │
   ┌────┴────┐      ┌───┴────┐      ┌─────┴─────┐     ┌─────┴─────┐
   │   RC    │      │  RSU   │      │  Vehicle Vi│     │ Vehicle Vj│
   │(注册中心)│      │(路侧单元)│      │ (事故车辆A) │     │ (事故车辆B) │
   └────┬────┘      └────┬────┘      └─────┬──────┘     └─────┬──────┘
        │                │                 │                   │
        │ ①②③④ 注册阶段  │                 │  ⑨ V2V 相互认证  │
        ├────────────────┼─────────────────┼───────────────────┤
        │                │                 │                   │
        │   ⑤ RSU 注册    │                 │  ⑪ V2R 认证上传   │
        ├────────────────┤◄────────────────┤                   │
        │                │                 │                   │
        └────────────────┴─────────────────┴───────────────────┘

消息流说明:
  ①②③④: 车辆注册流程 (VR1-VR3)
  ⑤: RSU 注册
  ⑥: RC 将注册信息写入区块链
  ⑦⑧: 事故车辆从区块链读取彼此注册信息
  ⑨: V2V 双向认证 + 联合签名生成事故报告
  ⑩: RSU 从区块链读取自身及车辆的注册信息
  ⑪: V2R 认证, 车辆将事故报告提交给 RSU
  ⑫: RSU 将验证通过的事故报告写入区块链
```

## 3.2 参与实体与角色

| 实体 | 缩写 | 职责与权限 |
|------|------|-----------|
| **注册中心** | RC (Registration Center) | 系统初始化的可信第三方；生成全局参数；注册车辆和 RSU；持有主密钥 $K_{TA}$ 用于生成伪身份和溯源；对区块链有**写权限**（注册信息）和**读权限** |
| **车辆** | $V_i, V_j$ | 配备 OBU，存储认证参数和伪身份；发生事故后进行 V2V 相互认证并联合签名；通过 V2R 协议上传事故报告；对区块链仅有**读权限** |
| **路侧单元** | RSU $R_t$ | 部署在道路沿线的固定基础设施；验证车辆提交的事故报告签名；对区块链有**写权限**（事故报告数据）和**读权限** |
| **区块链** | Blockchain | 基于 Hyperledger Fabric 的联盟链；存储车辆/RSU 注册信息和联合签名事故报告；实施访问控制策略（RC 和 RSU 写，车辆只读，外部实体无权限） |
| **交通警察/保险公司** | — | 从区块链**读取**事故报告，用于事故责任认定和理赔；不在协议运行中直接参与 |

### 信任假设

- **RC** 是完全可信的（trusted），持有系统主密钥 $K_{TA}$
- **RSU** 是诚实但好奇的（honest-but-curious），可能被物理捕获但内部 PUF 提供密钥保护
- **车辆** 互不信任，存在恶意车辆可能伪造事故报告或逃避责任
- **区块链** 作为不可篡改的分布式账本，写入的数据不可被单方修改或删除

## 3.3 模块划分与分工

### 模块 1：系统初始化模块（Initialization）

- 由 RC 执行
- 选择椭圆曲线 $E(\mathbb{F}_p)$、生成元 $P$、对称加密方案 $SE(\cdot)$、哈希函数 $h(\cdot)$、模糊提取器 $(Gen, Rep)$
- 生成 RC 的长期主密钥 $K_{TA}$
- 发布全局公共参数

### 模块 2：注册模块（Registration）

- **车辆注册**：RC 验证车辆身份后生成伪身份 $PID_i = E_{K_{TA}}(VID_i, VaI_i, r_i)$，写入区块链；车辆端结合驾驶员生物信息完成双因子安全存储
- **RSU 注册**：RC 分配 RSU 身份和密钥，RSU 端用 PUF 保护私钥

### 模块 3：V2V 认证与事故报告生成模块（V2V Auth & Report Generation）

- 事故车辆双方读取区块链上的对方注册信息
- 驾驶员通过生物认证解锁 OBU 存储的私钥
- 双方交换并验证对方的签名消息（包含事故记录、时间戳、随机数）
- 双方各自计算部分签名 $c_{i2}, c_{j2}$
- 聚合为联合签名 $c_{ij} = c_{i2} + c_{j2}$
- 验证联合签名的正确性

### 模块 4：V2R 认证与事故报告上传模块（V2R Auth & Report Upload）

- 车辆进入 RSU 通信范围后接收 RSU 广播的身份信息
- 车辆发送事故报告数据包（包含联合签名、双方伪身份、事故记录等）
- RSU 从区块链读取相关注册信息
- RSU 验证联合签名并用自己的私钥追加签名
- RSU 将完整的事故报告交易数据写入区块链

### 模块 5：动态身份更新模块（Temporary Identity Update）

- 车辆定期向 RC 请求伪身份更新
- 旧伪身份从区块链删除，新伪身份写入
- 确保伪身份的不可链接性

### 关键步骤说明

**步骤 1 — 车辆注册 (VR1-VR3)**：
1. 车辆发送发动机号 $VID_i$、公钥 $PK_{Vi}$、外观特征 $VaI_i$ 给 RC
2. RC 验证唯一性，生成随机数 $r_i$，计算伪身份 $PID_i = E_{K_{TA}}(VID_i, VaI_i, r_i)$
3. RC 写入 $\{PID_i, PK_{Vi}, VaI_i\}$ 到区块链，返回 $\{PID_i, r_i\}$ 给车辆
4. 车辆结合驾驶员生物信息 $Bio_i$，通过模糊提取器生成生物密钥 $\sigma_i$，加密存储：$S_{i1} = SK_{Vi} \oplus h(VE_i\|\sigma_i)$、$S_{i2} = r_i \oplus h(VID_i\|\sigma_i)$

**步骤 2 — V2V 认证 (VA1-VA3)**：
1. 双方驾驶员输入生物信息解锁 OBU 中的私钥 $SK_{Vi}$
2. 双方从区块链读取对方的公钥注册信息
3. 第一轮消息交换：各自生成临时密钥对 $(d_{i1}, d_{i2})$，计算施诺尔式签名 $c_{i1} = SK_{Vi} + h(AC_1\|D_{i1}\|D_{i2}\|T_1\|PID_i\|VaI_i) \cdot d_{i1}$，附事故记录 $AC_i$ 发送
4. 双方验证对方的第一轮签名
5. 第二轮消息交换：各自计算 $D_{ij} = D_{i2} + D_{j2}$ 和 $c_{i2} = SK_{Vi} + h(AC_1\|AC_2\|D_{ij}\|T_1\|PID_i\|T_2\|PID_j\|VaI_i\|VaI_j) \cdot d_{i2}$
6. 双方分别聚合：$c_{ij} = c_{i2} + c_{j2}$，独立验证联合签名方程

**步骤 3 — V2R 认证 (RA1-RA2)**：
1. 车辆基于 ECDH 密钥 $h(SK_{Vi} \cdot PK_{Rt}\|T_3)$ 认证 RSU
2. RSU 验证联合签名 $c_{ij}$ 的正确性
3. RSU 使用 PUF 恢复私钥 $SK_{Rt}$，追加签名 $c_t$
4. RSU 将完整交易数据写入区块链

## 3.5 安全/威胁模型

### 攻击者能力模型

形式化定义了五类攻击者能力（C1-C5）：

| 能力编号 | 能力描述 | 攻击者类型 |
|----------|---------|-----------|
| **C1** | 窃听公共信道上任意消息 | 被动攻击者 |
| **C2** | 插入、删除、修改或重放公共信道上的任意消息 | 主动攻击者 |
| **C3** | 腐化车辆或 RSU 的私钥 | 内部攻击者 |
| **C4** | 窃取 OBU 中存储的数据 | 物理攻击者 |
| **C5** | 伪造驾驶员的生物特征 | 生物认证攻击者 |

### 信任边界

```
 ┌──── 可信域 ────┐      ┌──── 半可信域 ────┐      ┌─── 不可信域 ───┐
 │      RC         │      │      RSU          │      │   车辆/公共信道  │
 │  (完全可信)      │      │ (PUF 保护密钥)    │      │  (完全不信任)    │
 │  持有 K_TA       │      │  可被物理捕获      │      │  可能恶意行为    │
 └─────────────────┘      └───────────────────┘      └────────────────┘
```

### 安全目标（Design Goals 对应）

1. **基础设施独立的事故报告**：无 RSU/目击车辆时，事故车辆双方可自足生成签名报告
2. **不可否认性与公开验证性**：RSU 和任意第三方可验证签名，报告上链后不可否认
3. **隐私保护与可溯源性**：车辆身份匿名但 RC 可追踪恶意车辆
4. **抵抗已知攻击**：包括 OBU 入侵、RSU 捕获、冒充、重放、中间人等

### 密码学假设

- **ECDLP 假设**（定义 1）：给定 $(P, aP)$，PPT 敌手无法以不可忽略概率求出 $a$
- **对称加密的语义安全性/CCA 安全性**（定义 2）：PPT 敌手在 CCA 游戏中区分加密明文的优势可忽略
