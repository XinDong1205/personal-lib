### 通信方式标注

| 缩写 | 全称 | 说明 |
|------|------|------|
| M2V | Manager to Vehicle | 车辆向 TA 注册真实身份 |
| M2B | Manager to Blockchain | TA 将匿名公钥提交至区块链 |
| M2R | Manager to RSU | TA 与 RSU 之间的通信 |
| V2V | Vehicle to Vehicle | 车辆间无线消息交换 |
| V2R | Vehicle to RSU | 车辆向 RSU 发送交通数据 |
| B2R | Blockchain to RSU | RSU 查询区块链上的匿名公钥 |

## 3.2 参与实体与角色

### TA（Trusted Authority）

- **角色定位**：智能交通服务提供者 + 区块链智能合约的 Manager + 系统审计者
- **信任假设**：所有参与方完全信任 TA（Fully Trusted）
- **计算与存储能力**：充足（服务器级别）
- **核心职责**：
  1. 部署智能合约 PKList，初始化区块链
  2. 为注册车辆生成匿名公钥三元组 `(C1, C2, C3)`
  3. 将匿名公钥通过 Submit 函数上链
  4. 恶意行为检测后，通过 Trace 函数追踪真实身份
  5. 通过 Revoke 函数撤销恶意/注销车辆的匿名公钥
  6. 秘密保存车辆真实身份 RID ↔ 公钥 PK ↔ 索引 cid 的映射表

### Vehicle

- **角色定位**：交通数据的生产者和消费者
- **信任假设**：不可信（可能存在恶意车辆）
- **计算与存储能力**：有限（车载 OBU，嵌入式环境）
- **核心职责**：
  1. 本地生成长期密钥对 `(ski, PKi = ski·P)`
  2. 向 TA 注册真实身份 RID 和公钥 PK
  3. 从智能合约获取自己的匿名公钥（通过 Get）
  4. 使用 SoK.GenProof 对每条交通消息生成签名
  5. 广播消息/签名对给周边车辆和 RSU
  6. 接收并验证其他车辆的消息（通过 SoK.VerifyProof）

### RSU（Roadside Unit）

- **角色定位**：车辆与基础设施之间的网关
- **信任假设**：半可信（Honest-but-Curious）
- **计算与存储能力**：中等（路边部署，有线供电）
- **核心职责**：
  1. 接收周边车辆广播的消息/签名对
  2. 从区块链查询发送方匿名公钥（通过 Get）
  3. 验证消息有效性（通过 SoK.VerifyProof / BVerifyProof）
  4. 将有效交通数据上传至 TCC/TA 供进一步分析
  5. 支持批量验证以提升吞吐量

### Blockchain

- **角色定位**：不可篡改的分布式数据存储 + 自主执行的智能合约平台
- **具体平台**：Ethereum（支持 Solidity 智能合约）
- **核心职责**：
  1. 存储所有车辆的匿名公钥（通过 mapping 结构）
  2. 提供 Get（公开查询）、Submit（仅 TA）、Trace（仅 TA）、Revoke（仅 TA）四个函数
  3. 利用区块哈希链保证已存储的匿名公钥不可被篡改

## 3.3 模块划分与分工

### 模块 A：匿名公钥管理模块（智能合约 PKList）

- **实现方式**：Solidity 智能合约，部署在 Ethereum 上
- **数据结构**：
  ```
  struct APK {
      uint256[2] C1;  // 匿名公钥第一部分: uj·P
      uint256[2] C2;  // 匿名公钥第二部分: uj·PK + PK
      uint256[2] C3;  // 追踪信息: uj·MPK + PK
  }
  mapping(uint256 => APK) apk;  // cid → APK 映射
  ```
- **访问控制**：Submit、Trace、Revoke 均通过 `require(msg.sender == manager)` 限制为 TA 独有权限；Get 为公开函数

### 模块 B：签名生成与验证模块（SoK 协议）

- **实现方式**：链下执行（在 OBU 和 RSU 本地运行）
- **三个核心算法**：
  - `GenProof(ski, xi, msgi, ti)` → 输出 `(msgi, σi={zi, Ri}, ti)`
  - `VerifyProof(xi, msgi, σi, ti)` → 输出 0/1
  - `BVerifyProof({xi, msgi, σi, ti})` → 输出 0/1（批量）

### 模块 C：身份追踪与撤销模块

- **实现方式**：TA 本地计算 + 调用智能合约函数
- **追踪流程**：TA 调用 `Trace(cid)` 获取 `(C1, C3)` → 本地解密 `PK = C3 - msk·C1` → 查表得到 RID
- **撤销流程**：TA 调用 `Revoke(cid)` 将相应 APK 清空

### 模块 D：注册模块

- **实现方式**：车辆与 TA 之间的安全信道（如 TLS）
- **流程**：车辆发送 `(RID, PK)` → TA 生成 `(cid, C1, C2, C3)` → TA 上链 → TA 返回 `cid` 给车辆

## 3.4 整体交互流程

```
车辆 Vi                 TA                   区块链 Smart Contract      RSU / 其他车辆
  │                     │                         │                       │
  │──① 系统初始化 ────►│                         │                       │
  │                     │──① 部署 PKList ────────►│                       │
  │                     │                         │                       │
  │──② 注册 ───────────►│                         │                       │
  │  (RIDi, PKi)        │                         │                       │
  │                     │──② 生成 APK ────────────►│                       │
  │                     │  Submit(cid, C1,C2,C3)  │                       │
  │◄──② 返回 cid ──────│                         │                       │
  │                     │                         │                       │
  │                                    ③ 消息签名（链下 SoK）              │
  │──③ Get(cid) ────────────────────────────────►│                       │
  │◄──③ (C1, C2) ───────────────────────────────│                       │
  │  GenProof(ski, xi, msg, t) → σ={zi, Ri}      │                       │
  │                     │                         │                       │
  │──④ 广播 (cid, msg, σ, t) ──────────────────────────────────────────►│
  │                     │                         │                       │
  │                                    ⑤ 消息验证                          │
  │                     │         ⑤ Get(cid) ───►│                       │
  │                     │         ◄── (C1, C2) ──│                       │
  │                     │       VerifyProof(x, msg, σ, t) → 1/0          │
  │                     │                         │                       │
  │                                    ⑥ 追踪与撤销（恶意行为检测后）      │
  │                     │──⑥ Trace(cid) ─────────►│                       │
  │                     │◄── (C1, C3) ───────────│                       │
  │                     │  PK = C3 - msk·C1      │                       │
  │                     │  PK → RID（查本地表）    │                       │
  │                     │──⑥ Revoke(cid) ────────►│                       │
  │                     │                         │                       │
```

**关键设计要点**：
- 步骤③和⑤中的 `Get(cid)` 调用：因为是 view 函数，在以太坊上 Gas 免费（仅本地节点查询），因此高频调用无经济成本；
- 所有签名/验证计算都在链下完成，区块链仅作为"公告板"存储匿名公钥，避免了链上计算的延迟和 Gas 开销；
- 时间戳 t 用于防重放攻击，验证方首先检查 t 的新鲜度。

## 3.5 安全模型与威胁模型

### 攻击者能力假设

| 维度 | 假设 |
|------|------|
| 计算能力 | 概率多项式时间（PPT）攻击者 |
| 密码学假设 | ECDLP（椭圆曲线离散对数问题）在所使用的群上困难 |
| 随机谕言模型 | 哈希函数被建模为随机谕言（Random Oracle） |
| 网络控制 | 攻击者可窃听、拦截、重放、篡改无线广播消息 |
| 节点妥协 | 攻击者可控制多辆恶意车辆（但 TA 不被妥协） |
| 区块链安全 | 底层区块链的共识机制和哈希链是安全的 |

### 信任边界

```
完全可信（Fully Trusted）    │  半可信（Honest-but-Curious）  │  不可信（Untrusted）
═══════════════════════════╪═══════════════════════════════╪══════════════════════
TA                         │  RSU                          │  车辆（彼此之间）
                           │  （正确执行协议但可能          │  攻击者
                           │   尝试推断隐私信息）          │
```

**信任边界的含义**：
- **TA 知悉一切**：TA 知道所有车辆的真实身份 RID、长期公钥 PK、匿名公钥映射关系。TA 的妥协将导致系统隐私完全崩溃，但不会导致车辆私钥泄露（因为 TA 从未掌握 ski）；
- **RSU 不可追踪**：RSU 能验证消息但不能追踪发送方身份，也不能将同一车辆的多条消息关联起来（跨匿名公钥批次）；
- **车-车零信任**：车辆之间不共享任何信任，完全依赖 SoK 协议的密码学保证彼此认证。

### 安全目标

1. **消息认证与完整性**：伪造签名在计算上不可行
2. **身份匿名**：从广播消息中提取发送方真实身份在计算上不可行
3. **条件可追踪**：TA 能高效（O(1) 时间）追踪到恶意发送方的真实身份
4. **不可链接性**：同一车辆使用不同匿名公钥发送的消息不可被关联
5. **不可否认性**：签名者不能否认曾生成的签名
6. **抗常见攻击**：包括重放、篡改、中间人、冒充、密钥托管、验证表窃取、生日碰撞等

### 关于不可链接性的重要注记

论文声称方案提供不可链接性，但实际上存在**批次内可链接性**：同一车辆在一个"认证周期"内使用同一组 `(C1, C2)` 对多条消息签名。因此，攻击者虽然无法将签名关联到具体车辆身份，但可以关联到同一个 `cid`（或同一组 `(C1, C2)`）。这是该方案在隐私保护方面的一个细微但重要的局限——详见第 6 章讨论。
