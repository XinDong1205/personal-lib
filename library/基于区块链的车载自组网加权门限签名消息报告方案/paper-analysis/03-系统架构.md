## 3.2 参与实体与角色

| 实体 | 缩写 | 信任假设 | 核心职责 |
|------|------|---------|---------|
| **可信权威** | TA | **完全可信** (absolutely trusted) | 系统初始化参数生成；车辆与雾节点注册；三因素声誉评估；恶意车辆身份追踪与撤销 |
| **雾节点** | Fog Node | **半可信** (honest-but-curious) | 接收车辆报告消息；验证身份与签名合法性；车辆组形成与权重分配；上传已验证消息到区块链 |
| **车辆** | Vehicle | **不可信** (untrusted) | 两类角色——消息报告车辆（发起报告并聚合签名）和辅助签名车辆（提供加权门限签名协助） |
| **区块链** | Blockchain | **防篡改** (immutable) | 存储雾节点公钥、车辆通信公钥（匿名）、声誉值；提供去中心化的公钥查询与撤销能力 |

### 信任模型要点

- TA 是唯一被完全信任的实体，负责车辆出厂前注册和恶意行为的最终仲裁。
- 雾节点被假设为**诚实但好奇**——会正确执行协议，但可能尝试从公开信息中推断车辆真实身份。因此通信公钥采用一次性匿名公钥设计。
- 车辆完全不可信——所有车辆消息必须经过接收方验证。
- 区块链提供防篡改的数据存储，不依赖其上的智能合约逻辑正确性来保证安全（仅用于数据查询与管理）。

## 3.3 模块划分与分工

系统按照功能分为**五大阶段**，对应五个核心模块：

```
Phase 1: System Initialization (系统初始化)
  ├── System Setup: TA 生成椭圆曲线参数、系统公私钥、哈希函数
  ├── Fog Node Registration: 雾节点注册真实身份和通信公钥到区块链
  └── Vehicle Registration: 车辆出厂前注册真实身份 + 初始声誉值

Phase 2: Vehicle Group Formation (车辆组形成)
  ├── 车辆加入请求 (Join Request) + 存款 (Deposit)
  ├── 雾节点验证身份、防 Sybil（检查地址不重复）
  ├── 查询区块链获取声誉值
  └── 分配权重 wₘ + CRT 秘密份额 sₘ → 加密分发

Phase 3: Vehicle Message Reporting & Verification (消息报告与验证)
  ├── Pre-signature Generation: 预签名阶段（离线完成）
  │   └── 车辆组内交互生成随机值份额 → 计算预签名中间值 (L, σ⁰ᵢ, σ¹ᵢ)
  ├── Reported Message Signature: 实时签名阶段
  │   └── 报告车广播消息 → 辅助车验证并签名 → 收集至总权重超门限 → 聚合
  └── Reported Message Verification: 雾节点验证
      ├── 单消息验证：时间戳 + 公钥查询 + sigi 验证 + 聚合签名验证
      └── 批量验证：小指数测试 (small-exponent testing)

Phase 4: Weight Determination (权重确定)
  ├── 三因素声誉评估（历史声誉 + 行为反馈 + 群体历史声誉）
  ├── 声誉值衰减公式（快速下降/缓慢上升）
  └── 整数线性规划 (ILP) 分配权重 → CBC 求解器

Phase 5: Tracking & Revocation (追踪与撤销)
  ├── TA 通过公钥 V_PKᵢ → 地址 Addrᵢ → 真实身份 V_IDᵢ
  └── 区块链辅助：撤销地址 → 删除所有注册公钥 → 信誉清零
```

## 3.4 整体交互流程（核心时序图）

以下时序图描述一次完整的消息报告流程（消息报告与验证阶段）：

```
 Vehicle Vᵢ (Reporter)    Aux Vehicles Vₕ    Fog Node      Blockchain
  │                         │                   │              │
  │  [Phase 2 (已提前完成): 车辆组形成、秘密份额分发、预签名]  │
  │  [Vᵢ 持有: (sᵢ, pᵢ, gskfj, pkfj, L, σ⁰ᵢ, σ¹ᵢ)]          │
  │                         │                   │              │
  │  遇到紧急事件 mᵢ         │                   │              │
  │  Tagᵢ = MAC(mᵢ, V_PKᵢ)  │                   │              │
  │──M3={mᵢ,V_PKᵢ,T²ᵢ,Tagᵢ}─▶│                   │              │
  │                         │  (验证 Tagᵢ)       │              │
  │                         │  查询 V_PKᵢ 有效性  │──────────────│
  │                         │◀────────────────────│  ✓有效       │
  │                         │  σₕ = σ⁰ₕ·hₕ+σ¹ₕ   │              │
  │◀─M4={V_PKₕ,Enc(σₕ),Tagₕ}─│                   │              │
  │                         │                   │              │
  │  收集签名直到 Σ|σ| ≥ Wₜ  │                   │              │
  │  聚合: σ = Fopen({σₕ})  │                   │              │
  │  签名: sigᵢ = aᵢ + vskᵢ·hsᵢ │               │              │
  │                         │                   │              │
  │──M5={mᵢ,Aᵢ,V_PKᵢ,σ,L,Tᵢ,sigᵢ}─────────────▶│              │
  │                         │                   │              │
  │                         │   验证 Timestamp   │              │
  │                         │   查询 V_PKᵢ      │──────────────│
  │                         │                   │◀── ✓存在─────│
  │                         │   验证 sigᵢ:      │              │
  │                         │   sigᵢ·P ?= Aᵢ+V_PKᵢ·hsᵢ │    │
  │                         │   验证聚合签名:    │              │
  │                         │   (lx,ly)=σ⁻¹·H₀(mᵢ)×P+σ⁻¹·lx×pkfj │
  │                         │   验证权重: Wₙ≥Wₜ │              │
  │                         │                   │              │
  │                         │  上传消息到区块链   │─────────────▶│
  │◀────────── 奖励分配 ─────│                   │              │
```

### 关键交互说明

1. **M3（报告请求）**：报告车用组会话密钥 gskfj 生成 MAC 标签，防止未授权车辆请求辅助签名
2. **M4（辅助签名响应）**：辅助车辆使用预签名阶段保存的 (σ⁰ₕ, σ¹ₕ) 快速生成签名份额，并用 Diffie-Hellman 派生密钥加密
3. **M5（最终报告）**：报告车将满足门限的聚合签名与自身 ECDSA 签名打包上报

## 3.5 安全/威胁模型

### 攻击者能力假设

论文采用了标准的概率多项式时间（PPT）敌手模型：

1. **网络控制**：攻击者可以监听、拦截、延迟、重放所有公共信道上的消息
2. **密码学能力**：攻击者可以发起选择消息攻击（EU-CMA 模型），但**不能**在多项式时间内解决椭圆曲线离散对数问题（ECDLP）
3. **腐化能力**：攻击者可以腐化最多 $t-1$ 辆车辆（$t$ 为达到门限所需的最小签名数），但不能同时腐化 TA
4. **密钥泄露**：攻击者可能通过侧信道/物理攻击获取部分车辆的存储密钥，但方案通过密钥生命周期限制和门限设计加以缓解

### 安全目标

| 安全属性 | 描述 | 实现手段 |
|---------|------|---------|
| **消息完整性与可认证性** | PPT 敌手无法伪造有效签名 | ECDLP 假设 + EU-CMA 安全归约 |
| **身份隐私保护** | 通信过程不泄露真实身份 | 一次性匿名公钥 + 区块链注册 |
| **可追踪性** | 恶意行为可追溯到真实身份 | TA 维护 V_IDᵢ ↔ Addrᵢ 映射 |
| **有效身份撤销** | 被撤销车辆无法继续签名 | 区块链删除公钥，接收方查不到公钥 |
| **抗共谋攻击** | $t-1$ 辆车合谋无法伪造门限签名 | WTS 秘密份额独立 + 声誉快速下降 |
| **抗 Rogue Key 攻击** | 收集他人公钥无法伪造签名 | 验证只依赖 pkfj 和 V_PKᵢ，不依赖公钥聚合 |
| **抗重放/冒充/篡改/中间人攻击** | 标准安全属性 | 时间戳 + Theorem 1 + ECDSA |

### 安全证明结构

论文采用**随机预言机模型（Random Oracle Model）**进行 EU-CMA 安全归约：

- 将方案安全性归约到 ECDLP 的困难性
- 使用 Forking Lemma（分叉引理）处理随机预言机中的哈希碰撞
- 计算出敌手优势 $\varepsilon'$ 与 ECDLP 求解优势 $\varepsilon$ 之间的具体关系

安全证明的完整拆解见第四章。
